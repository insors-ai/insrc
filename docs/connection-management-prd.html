Connection management in Settings

Product requirements · 21 October 2026 · Draft for review

Make registered data sources easy to find and maintain from insrc Settings in VS Code and JetBrains, so data analysis and the future ontology builder can use them.

1. Scope and current product

Add an insrc → Data Connections settings entry with a clear Manage Connections action. Open a themed connection manager in the editor, retaining the selected repository. Users can view, add, update, test, and remove connections without editing JSON. Repository selection determines data visibility; each connection also has an explicit lifetime scope: Saved repository or Temporary session. Temporary connections support one-off CSV/JSON/Parquet analysis and any other daemon-supported driver; the native User/Workspace settings tabs do not change connection ownership.

Current client scope (user clarification, 29 October 2026): Only the standalone VS Code extension (vscode-plugin/) and JetBrains plugin (jetbrains-plugin/) are delivery targets. The insrc-ide fork is deprecated and is not a compatibility or release dependency. Both live clients have Settings surfaces; S005 adds native connection management and consumes the same daemon protocol. Scope correction.

Visual basis: existing insrc configuration groups, native VS Code Settings search/category layout, and JetBrains native Settings controls. The mocks show shared behavior and proposed additions; they are not screenshots of shipping UI.

2. Required behavior

Product baseline: CM01 discovery/listing; CM02 add; CM03 safe editing/credentials; CM04 draft tests; CM05 save outcomes; CM06 repository/error handling; CM07 saved/temporary lifetimes and filters; CM08 discard/delete. These are required outcomes, not assertions of existing production behavior.

ID Requirement Acceptance
CM01Discover and listSearching “insrc connections” exposes the settings entry. Manage Connections lists the selected registered repository’s connection ID, label, driver, family and lifetime scope. Loading, failed read, and empty are distinct states.
CM02Add a connectionPick a driver returned by the daemon, then supply a unique ID, optional label, and the driver’s URL or file path. Required fields and duplicate IDs show inline errors. An add must never silently update an existing ID.
CM03Update a connectionOpen the selected connection with existing non-secret fields populated. ID and driver are fixed in this release. Populate the endpoint without its password. Credentials have explicit Keep stored / Replace / Clear actions; Keep stored is the edit default and survives endpoint changes, Replace requires a masked new password, and Clear explicitly removes it. Add supports Replace or no password. Test and Save apply the same endpoint and credential patch. Cancel makes no changes. Unknown supported configuration fields survive a basic edit.
CM04Test without savingTest the current form and show success/failure and time. Editing any connection field invalidates the result. Bind each request to its repository, draft revision, and request ID; ignore late results after edits, repository switches, form closure, or a newer request. Show a pending state, disable repeated Test while pending, and time out after 10 seconds with retry. Cancel or ignore obsolete requests and always release transient drivers. “Saved” never means “reachable”; test success does not establish schema completeness or permission for every probe.
CM05Save and refreshFor Saved repository scope, show success only after the daemon confirms persistence. For Temporary session scope, show “Added for this session” only after daemon registration in session memory; do not claim persistence. Refresh the authoritative list and activate the connection for analyzer use. Report persistence, activation, and list refresh separately: if persistence succeeds but activation or refresh fails, show “Saved; activation/refresh failed” with retry of only the failed operation. Never repeat create to recover refresh. Retain the draft on failed or uncertain persistence. A lost save response shows “Save outcome unknown”; reconcile using a stable operation ID before allowing a new mutation. Test is recommended, not mandatory, for saving.
CM06Scope and failure handlingMulti-root workspaces require explicit registered-repository selection. No repository offers registration guidance; unavailable daemon offers retry. A read failure cannot be shown as “no connections.” Switching repository or closing a dirty form offers discard/cancel. A registry read failure blocks all mutations, including direct RPC calls, and leaves registry bytes and credentials unchanged; a missing registry is a valid empty registry.
CM07Choose and filter lifetime scopeAdd offers Saved repository (default) and Temporary session, independently of driver family. Scope is fixed during edit. Temporary connections are bound to the originating workbench session and selected repository, visible to analysis only with that session context; closing the manager or switching repositories does not discard them. Ending the workbench session or restarting the daemon expires them; show this before adding. Store temporary configs and credentials only in daemon memory, never the saved registry or keychain. IDs are unique across both scopes within the session’s repository view; duplicate IDs fail instead of shadowing a saved connection. Filter the panel by All / Saved repository / Temporary session, with scope badges, matching counts, and a distinct “No connections match this filter” state. Adding reveals the new connection even when the previous filter excluded its scope.
CM08Discard and deleteEach temporary row offers Discard; each saved row offers Delete. Confirm the connection ID and scope, state that source files and database data are never deleted, and offer Cancel. Delete removes the saved registry entry and its owned credentials; Discard removes session registration and credentials from memory. Require revision checks, retain the row on failure, and support idempotent retry/reconciliation after an uncertain response. In-use connections return a clear busy error without removal; users retry after analysis completes. Successful removal prevents new analysis from resolving the connection and releases idle driver resources. A dirty form requires discard confirmation before removal.

4. Interaction and implementation contract

Use native Settings for discovery and a themed editor for the rich list/form; a command link in the setting description should open the manager. Do not introduce a plaintext connections array in settings.json . Route Settings and live command/action entry points to the same guarded management behavior. Use VS Code theme tokens and JetBrains native theme controls, spacing, visible focus, labels and keyboard access. The extension adds command/webview wiring; JetBrains adds a native Connections manager backed by a project-owned memory-only session service. Global Settings Apply/reset must not implicitly save connections.

Reuse Required adjustment
db.listConnections, db.listDriverKinds Populate authoritative list and driver choices. The current list returns ID/kind/family/label only and swallows read errors into an empty list; add distinguishable errors and a safe editable-config read contract.
db.saveConnection Retain daemon-owned persistence and secret extraction. Add explicit create/update semantics, conflict detection and credential preservation; existing upsert alone cannot protect duplicate adds or concurrent edits. Use an atomic per-repository mutation with create-if-absent and revision-checked update/delete. A stale update must neither overwrite a newer version nor recreate a deleted connection; preserve the draft, explain the conflict, and offer reload with discard confirmation. Simultaneous creates for one ID yield exactly one success. Check registry readability and revision before changing secrets; failure must preserve both registry and credentials, with rollback or transactional staging. Stable operation IDs make retries/reconciliation idempotent, including lost responses. Never return secret values to the renderer.
db.testConnection Reuse transient driver test; test current draft without persistence. Resolve Keep stored / Replace / Clear server-side without exposing stored secrets. Apply the same merged configuration and revision checks as Save, without persisting draft secrets. Return sanitized errors and support a 10-second deadline and cleanup.
Existing registry and driver pool Retain per-repository ~/.insrc/repos/<repo-id>/db-connections.json and credential references. Re-read after save. Return separate persisted and activated outcomes and provide activation retry plus operation-status reconciliation. Keep saved connections in this registry. Add a daemon- owned ephemeral session overlay, not a second persistent registry; carry session identity through list/read/test/create/update/remove and analyzer resolution. Expire its configs, secrets, and idle resources on session end or daemon restart. Reuse db.deleteConnection for saved deletion with revision and operation-ID support; temporary discard uses the same removal contract against session memory. Session isolation must be enforced by the daemon.

Inspect credential handling for each supported family before release; the current save path extracts URL passwords and is not a blanket guarantee for every secret in arbitrary driver options. Keep credentials out of workspace settings, logs, mock fixtures, telemetry, and error text.

5. Release boundary and verification

In scope: Settings entry, repository-scoped list, add/update forms, driver-specific required inputs, testing, safe saved-config editing, truthful errors, lifetime selection/filtering, and confirmed discard/delete. Existing removal commands share these semantics; automatic application-config discovery, new drivers, ontology generation, and team-shared credentials are outside this small release.

Verify scope filters, empty-filter state, temporary session isolation/expiry, absence of temporary disk/keychain writes, discard/delete cancellation, busy/failure/stale-removal handling, source-file preservation, and ID collisions across scopes. Verify list/add/update across a SQL driver, KV driver, and file source; duplicate IDs; preserved and replaced credentials; unsupported configuration fields; stale/concurrent updates and deletion during edit; simultaneous duplicate creates; registry-read failure during save with byte- for-byte registry and credential preservation; lost save responses and idempotent reconciliation; activation and refresh failure after persistence; late test responses, timeout and repeated clicks; canceled edits; repository switching; daemon outage; invalid registry; and list refresh after save. Confirm the analyzer discovers the saved ID. Validate dark/light themes, keyboard navigation, masked credentials, and client/daemon contract compatibility. No live production data is required for UI testing.
