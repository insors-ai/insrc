Connection management in Settings

Product requirements · 21 October 2026 · Draft for review

Make registered data sources easy to find and maintain from VS Code’s insrc Settings, so data analysis and the future ontology builder can use them.

1. Scope and current product

Add an insrc → Data Connections settings entry with a clear Manage Connections action. Open a themed connection manager in the editor, retaining the selected repository. Users can view, add, update, and test connections without editing JSON. Repository selection determines data scope; the native User/Workspace settings tabs do not change connection ownership.

Existing implementation: The separate insrc IDE fork already registers a Data Sources editor and add/edit/remove/test commands. This work improves Settings discoverability and the management interaction, reusing that surface and the daemon. The standalone VS Code extension has Settings contributions but no equivalent connection management wiring found during inspection.

Visual basis: existing insrc configuration groups, native VS Code Settings search/category layout, and the IDE’s theme-token-based Data Sources editor with repository sections. The mocks show proposed additions; they are not screenshots of shipping UI.

2. Required behavior

IDRequirementAcceptance
CM01Discover and listSearching “insrc connections” exposes the settings entry. Manage Connections lists the selected registered repository’s saved connection ID, label, driver and family. Loading, failed read, and empty are distinct states.
CM02Add a connectionPick a driver returned by the daemon, then supply a unique ID, optional label, and the driver’s URL or file path. Required fields and duplicate IDs show inline errors. An add must never silently update an existing ID.
CM03Update a connectionOpen the selected connection with existing non-secret fields populated. ID and driver are fixed in this release. Unchanged credentials are retained; replacement is explicit and masked. Cancel makes no changes. Unknown supported configuration fields survive a basic edit.
CM04Test without savingTest the current form and show success/failure and time. Editing any field invalidates the result. “Saved” never means “reachable”; test success does not establish schema completeness or permission for every probe.
CM05Save and refreshShow success only after the daemon confirms persistence. Refresh the authoritative list, make the connection available to the analyzer, and retain the form on failure. Test is recommended, not mandatory, for saving.
CM06Scope and failure handlingMulti-root workspaces require explicit registered-repository selection. No repository offers registration guidance; unavailable daemon offers retry. A read failure cannot be shown as “no connections.” Switching repository or closing a dirty form offers discard/cancel.

3. Clickable mock screens

Fictional fixtures. Use the screen picker, Manage Connections, Add Connection, Edit, Test Connection, and Save. No network, daemon, credential storage, or persistent writes are performed. The simulated test result is selectable.

4. Interaction and implementation contract

Use native Settings for discovery and a themed editor for the rich list/form; a command link in the setting description should open the manager. Do not introduce a plaintext connections array in settings.json. Keep existing palette commands and the Data Sources editor routed to the same management behavior. Use VS Code theme tokens, native spacing, visible focus, associated labels, and keyboard-accessible controls. The standalone extension needs equivalent command/webview wiring; the IDE fork should extend its existing pane/service.

ReuseRequired adjustment
db.listConnections, db.listDriverKindsPopulate authoritative list and driver choices. The current list returns ID/kind/family/label only and swallows read errors into an empty list; add distinguishable errors and a safe editable-config read contract.
db.saveConnectionRetain daemon-owned persistence and secret extraction. Add explicit create/update semantics, conflict detection and credential preservation; existing upsert alone cannot protect duplicate adds or concurrent edits. Never return secret values to the renderer.
db.testConnectionReuse transient driver test; test current draft without persistence. Ensure unchanged stored credentials can be used without exposing them to the client.
Existing registry and driver poolRetain per-repository ~/.insrc/repos/<repo-id>/db-connections.json and credential references. Re-read after save. Do not create a second registry or broaden existing connection scope.

Inspect credential handling for each supported family before release; the current save path extracts URL passwords and is not a blanket guarantee for every secret in arbitrary driver options. Keep credentials out of workspace settings, logs, mock fixtures, telemetry, and error text.

5. Release boundary and verification

In scope: Settings entry, repository-scoped list, add/update forms, driver-specific required inputs, testing, safe saved-config editing, and truthful errors. Existing removal commands remain available; a new delete flow, automatic application-config discovery, new drivers, ontology generation, and team-shared credentials are outside this small release.

Verify list/add/update across a SQL driver, KV driver, and file source; duplicate IDs; preserved and replaced credentials; unsupported configuration fields; stale/concurrent updates; canceled edits; repository switching; daemon outage; invalid registry; and list refresh after save. Confirm the analyzer discovers the saved ID. Validate dark/light themes, keyboard navigation, masked credentials, and client/daemon contract compatibility. No live production data is required for UI testing.
