# Epic: e2-delivery-board-vs-code-goal

## Summary

**Flavor:** new-capability

This Epic gives VS Code users a read-only delivery board: one place to see every epic, story, task and issue, the stage each has reached and why, and the separate approval, review and validation evidence behind it. A reader can find work that needs a decision, follow an epic down to a task and the record that supports it, and see contradictory or incomplete evidence plainly instead of having it hidden behind a single status label. The board changes nothing; it only reads what the workflow has already recorded.

## 1. Problem

Developers, reviewers and delivery leads who work in VS Code still cannot see delivery as a whole. The daemon now assembles every epic, story, task and issue, with its stage, its evidence and its approval, review and validation signals, into one coherent view, but nothing in the editor shows it. To learn what is ready, what needs a decision or why an item looks finished, a reader must still open and cross-read individual documents one at a time, and the facts that matter most are the ones that are easiest to miss that way: a build that was approved although some of its task checks failed, a review that blocks an unapproved design, a defect whose parent cannot be found, or a record that could not be read at all. Because the view is reachable only as raw data, its distinctions between workflow progress, human approval, automated review and task validation are lost on the way to the reader, and the only document surface in the editor shows one pending document at a time, so it cannot answer questions that span many items or show completed and in-progress work side by side.

## 2. Functional requirements

- **E202610086a131558:FR001** — The board shows every work item in the delivery view in exactly one stage column, with its approval, review, validation and conflict signals shown as separate facts. _(The PRD's product principle: a convenient status label must not conceal contradictory evidence.)_
- **E202610086a131558:FR002** — The board offers a board view, an epic rollup view and an issue view over the same delivery view, and every count shown agrees with the cards the current selection contains. _(FR-03 and FR-04 / AC-09.)_
- **E202610086a131558:FR003** — A reader can search, scope to one epic or to standalone work, and filter to items that need attention, and clearing a filter restores the previous set. _(FR-04.)_
- **E202610086a131558:FR004** — A reader can open any work item's details, see its tasks and the reason for its stage, and open each supporting record in the editor's existing document viewer, or read it through the daemon when that viewer cannot open it. _(FR-05 and FR-06; the existing viewer reads a record by artifact id through workflow.artifactContent, which finds the record from the insrc:artifact marker in its markdown, and on 2026-10-08 only 24 of the 93 build-record markdown files carried that marker.)_

- **E202610086a131558:FR007** — The board is usable with the keyboard alone, labels every colour-coded state in text, and works in a narrow pane as well as a wide editor tab. _(AC-14 and the PRD's accessibility and responsive-layout rules.)_

## 3. Non-goals

- **Creating, approving, rejecting or editing any work item or record from the board, or moving work between stages.** — The first release is read-only by the PRD's scope (FR-09); controlled actions need their own interaction and workflow design.
- **Deriving stages, routes, identities, attention or conflicts in the editor.** — The daemon owns interpretation (PRD §07); a second derivation in the client would drift from the first and from the JetBrains board that follows.
- **Changing the existing VS Code document review pane.** — That pane belongs to Epic bfe98ff7; the board opens evidence in it but does not alter it.
- **The JetBrains board.** — Deferred to E3, a parity pass after this Epic settles the interaction decisions.
- **Automatic refresh, live agent activity, review annotations or agent handoff.** — The daemon sends nothing unsolicited, live activity cannot be inferred from records, and annotations are an unframed follow-on (PRD §02, §10).
- **Assignees, sprints, due dates, priorities, estimates or external tracker synchronisation.** — Out of scope for the first release per PRD §02.

## 4. Assumptions

- `high` The delivery view published by E1 (workflow.delivery and workflow.deliveryEvidence, schemaVersion 1) is the board's only data source, and later changes to it are additive optional fields. [[c3]]
- `med` A dedicated editor tab is the right primary placement, to be checked against a sidebar entry in the first story. [[c9]]
- `high` Manual refresh is enough for the first release. [[c10]]
- `high` The delivery view does not carry a task's dependencies or acceptance checks, only its validation result, so showing them needs either the plan record read through the daemon or an additive field in the delivery view; which one is a design decision for the HLD. [[c4]]
- `med` "Complete" stays as the final stage's label; whether readers take it for validation success is tested in a usability session that the epics plan assigns to S2, outside this Define's acceptance criteria. [[c11]]

## 6. Stories

### 6.1 E202610086a131558:S001 — Open the board, refresh it, and see why it is empty, unavailable or incomplete

**User value:** `size: M`

A reader can open the delivery board in an editor tab, refresh it when they choose, and always know whether what they see is current, stale, empty or only partly readable, so they never mistake missing data for missing work.

**Extends:** [[c16]]

**Acceptance criteria:**

- **ac1:** Given a workspace whose daemon is running, when the user opens the delivery board, then the board opens in an editor tab showing the work items of one snapshot and the time that snapshot was taken. _(operationalizes `k1`)_
- **ac2:** Given the board is showing a snapshot, when the user refreshes and the refresh fails, then the last successful board stays visible with a notice that names the failure and the time of the last successful refresh. _(operationalizes `k6`)_
- **ac3:** Given a workspace with no recorded work, a daemon that cannot be reached, a read that fails, and a snapshot that reports unreadable records, when the board is opened in each case, then each case shows its own distinct state and message, and the partly readable case still shows every readable item. _(operationalizes `k6`)_
- **ac4:** Given two refreshes are requested in quick succession, when the response to the earlier request arrives after the later one, then only the later snapshot is shown and nothing from the earlier snapshot is mixed into it. _(operationalizes `k5`)_
- **ac5:** Given the user has a filter applied and an item selected, when a refresh succeeds and the item still exists, then the filter and the selection are kept; if the item no longer exists the selection is cleared and the user is told. _(operationalizes `k9`)_
- **ac6:** Given a repository under version control with recorded workflow artifacts, when the user opens the board and refreshes it repeatedly, then no artifact, approval, source file or Git state changes. _(operationalizes `k3`)_

**Local constraints:**

- `lc1` (stakeholder) The editor-tab placement is checked against a sidebar entry point before this Story completes, and the decision is recorded. [[c9]]

### 6.2 E202610086a131558:S002 — See every work item in its stage column, with its signals, and narrow the board

**User value:** `size: L`

A reader can scan the whole delivery picture by stage, see at a glance which items carry an approval, review, validation or conflict signal, and narrow the board to one epic, to standalone work, to a search or to what needs attention, with every count agreeing with what they see.

**Depends on:** `s1`

**Acceptance criteria:**

- **ac1:** Given a snapshot with stories and issues at every stage, when the board renders, then it shows six columns in workflow order, Scoped, Design & plan, Ready · design approved, Ready · plan approved, Build recorded and Complete, and each story or issue appears exactly once, in the column the snapshot assigns it. _(operationalizes `k2`)_
- **ac2:** Given a story whose build record is approved but holds failed task results, when the board renders, then its card sits in Complete and carries a validation-conflict badge with a text label. _(operationalizes `k2`)_
- **ac3:** Given an unapproved design whose review blocks it, when the user turns on the Needs attention filter, then the card shows a review-blocked badge, matches the filter, and stays in its own stage column. _(operationalizes `k2`)_
- **ac4:** Given the user selects one epic and enters a search, when the board updates, then the cards, column counts and totals all agree with each other, including cards hidden behind a show-more control, and clearing the search and the scope restores the previous set. _(operationalizes `k9`)_
- **ac5:** Given the same snapshot loaded twice with the same filters, including items with equal timestamps, when the board renders each time, then the order of cards and every count are identical. _(operationalizes `k9`)_
- **ac6:** Given a work item title or notice that contains markup or script text, when its card renders, then the text is shown literally and nothing in it runs. _(operationalizes `k4`, `k8`)_

### 6.3 E202610086a131558:S003 — See progress per epic and follow defects to the work that fixes them

**User value:** `size: M`

A delivery lead can see how far each epic has progressed with counts that say what they count, keep standalone work separate from epic work, and follow each defect to its fix stories, including defects whose parent cannot be found.

**Depends on:** `s1`, `s2`

**Acceptance criteria:**

- **ac1:** Given an epic with five stories of which two are complete, when the user opens the epic rollup, then the epic shows a completion count that names its denominator, such as 2 of 5 stories complete, and its stories grouped by stage. _(operationalizes `k2`)_
- **ac2:** Given standalone stories and standalone issues alongside epics, when the epic rollup renders, then standalone work is shown in its own group and is not counted towards any epic. _(operationalizes `k2`)_
- **ac3:** Given an issue that links to a story, and another issue whose parent cannot be resolved, when the user opens the issue view, then the first shows a relationship the user can follow to the story, and the second is still listed with an unresolved-parent notice. _(operationalizes `k2`)_
- **ac4:** Given an issue with more than one fix story, when the user opens the issue view, then the issue shows each fix story as a distinct child with its own stage. _(operationalizes `k2`)_
- **ac5:** Given a search or epic scope applied on the board, when the user switches to the epic rollup or the issue view, then the same selection applies and the counts agree with the board. _(operationalizes `k9`)_

### 6.4 E202610086a131558:S004 — Open a work item to see its tasks, why it is in its stage, and the records behind it

**User value:** `size: L`

A developer or reviewer can open any item and see its tasks with their dependencies, checks and recorded results, the reason for its stage, and every supporting record with its approval and review, then open each record to read it, so they can explain an item's state without searching the records by hand.

**Depends on:** `s1`

**Acceptance criteria:**

- **ac1:** Given a story whose plan lists tasks and whose build record has results for some of them, when the user opens the story's details, then each planned task shows its dependencies and acceptance checks and is labelled Passed, Failed or Unrecorded, a task present only in the build record is labelled unplanned, and Unrecorded tasks are not counted as passed or failed. _(operationalizes `k2`)_
- **ac2:** Given any work item, when the user opens its details, then the details show the daemon's stated reason for the item's stage and the records that reason cites. _(operationalizes `k2`)_
- **ac3:** Given a story whose build is approved although some task results failed, when the user opens its details, then the approval and the failed results are shown together with an explanation of the conflict, and neither is hidden. _(operationalizes `k2`)_
- **ac4:** Given a rejected record, a record with a review override, and an approved record with a historical blocking review, when the user reads their evidence entries, then the rejection is labelled rejected, not pending, and the original review verdict is shown together with any override. _(operationalizes `k2`)_
- **ac5:** Given an evidence record the existing document viewer can open, and a build record that viewer cannot open, when the user opens each, then the first opens in the existing review pane and the second is shown read-only from the daemon, with its text rendered as data. _(operationalizes `k1`, `k4`, `k10`)_
- **ac6:** Given a story that has a code review but no build record, when the user opens its details, then its stage is unchanged, a review-without-build notice (the PRD's unledgered code review) explains the situation, and the code review is listed in its evidence. _(operationalizes `k2`)_

**Local constraints:**

- `lc1` (contract) Whether a record opens in the existing review pane or is read through the daemon follows the open-with value the daemon publishes for that record. [[c17]]

### 6.5 E202610086a131558:S005 — Use the board in a narrow pane, with the keyboard alone, and at either density

**User value:** `size: M`

Every reader, including keyboard-only and screen-reader users and those working in a narrow pane, can reach the same work, warnings and evidence, and a large workspace stays responsive.

**Depends on:** `s2`, `s3`, `s4`

**Acceptance criteria:**

- **ac1:** Given the board open in a narrow pane, when it renders, then columns become a grouped list by stage and every card, badge and warning remains available. _(operationalizes `k11`)_
- **ac2:** Given a user who uses only the keyboard, when they move through the views, open an item's details and close them again, then every control and evidence entry is reachable with visible focus, and closing the details returns focus to where they were. _(operationalizes `k11`)_
- **ac3:** Given a screen reader, when the user moves between cards and refreshes, then every colour-coded state has a text label, and card selection and the refresh result are announced once. _(operationalizes `k11`)_
- **ac4:** Given the user switches between compact and comfortable density, when the board re-renders, then no warning, badge or accessibility label is hidden at either density. _(operationalizes `k11`)_
- **ac5:** Given a fixture of 1,000 records forming 500 work items on the reference environment, when the snapshot arrives and the user then changes a filter, then the initial board renders within one second and each filter change responds within 150 ms. _(operationalizes `k7`)_
