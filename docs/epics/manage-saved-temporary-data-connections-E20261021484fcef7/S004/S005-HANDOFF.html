Scope and confirmation

Filter the connection panel by ConnectionKey.scope. The attached workbench list is root-local and can contain saved and temporary registrations; the unbound compatibility path remains saved-only. Keep the full root/scope/id key when selecting an action. There is no bulk-remove or force-delete API.

ScopeActionConfirmation copy
SavedDeleteDelete this saved registration and its obsolete application-owned credentials. Source files, databases, tables and remote data will be preserved.
TemporaryDiscardDiscard this temporary registration and release its application-owned resources. Source files, databases, tables and remote data will be preserved.

Capture the selected revision before confirmation. Cancel issues no ticket, mutation or cleanup request. Confirm obtains a remove ticket and submits that exact key and captured revision. A busy or changed revision preserves the registration.

Temporary connections survive panel close and root switching within the live workbench session. Workbench end, lease loss and daemon restart revoke temporary authority. Both clients must explain this lifetime before adding a temporary connection; this backend story does not establish that client acceptance.

Capability and transport contract

Saved removal requires saved-remove; temporary removal requires temporary-remove plus a live root-bound workbench-ui session. The state and retry features are removal-state and removal-cleanup-retry. Missing features return upgrade-required before removal ticket issuance. Never fall back to legacy delete, infer permission from an unknown method, or strip a presented session to reach a saved channel.

States and reconciliation

StateClient behavior
confirmingLocal captured selection; no live operation exists. Cancel is a no-op.
removingKeep the operation identity stable while the confirmed request is active.
busyCurrent use blocked removal. Retry the same intent after work drains; do not force-close source work.
conflictRefresh the selected revision and ask for confirmation again.
unknownReconcile with the same ticket. Not-seen, lost response or absent row does not prove removal; do not mint a replacement delete automatically.
removed-cleanup-pendingThe registration is already gone. Show credential and resource cleanup independently and retain an operation-level retry entry. Cleanup failure never restores the row.
removedVerified removed receipt and both cleanup phases complete for the current owner’s truth.

Temporary credential cleanup is always complete; its resources can remain pending. Saved credential cleanup and SDK cleanup can fail independently. A retry can join an in-flight close rather than start another attempt. Exact old ownership prevents a retry from closing a recreated same-ID connection. Live temporary cleanup retains its resource slot and ID reservation until completion.

On a rejected temporary session or epoch, stop using its receipt. A fresh owner cannot recover that private history. Saved committed receipts and obsolete credential cleanup can survive restart; runtime handles are never reconstructed from stored configuration.

Migration, drain and downgrade

No data rewrite, credential rotation, source deletion or registry-schema migration is introduced. The existing v2 envelope, signed remove mode, receipts and lease gate remain the contract.

Before a daemon update or downgrade, stop admission, reconcile any ambiguous saved commit, and drain currently owned resources. Unresolved removal ownership is not silently evicted. An older client or daemon without sc6 refuses the new actions. Release enablement remains a separate prerequisite decision.

A user-confirmed saved removal is nonrollbackable as an application operation: deployment rollback does not recreate its row or deleted obsolete application credentials. Re-adding a connection is a new explicit action. Neither restart nor downgrade may resurrect configuration or credentials automatically.

Protected sc2 receipts intentionally retain owned cleanup references for recovery. New sc6 responses, logs and client state do not expose those references, raw SDK/journal errors, endpoints, credential values or session capabilities.
