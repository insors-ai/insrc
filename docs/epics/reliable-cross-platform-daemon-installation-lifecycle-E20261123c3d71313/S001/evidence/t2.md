# s1/t2 — native operation lock and controller snapshots

Implemented a minimal Node-API v8 addon, development/release-only owned compiler stage, lazy loader (never compiles), private control directory, persistent non-renamed lock, bounded read-only inspection, immutable enrollment sentinel, revision-checked atomic snapshot publication, and a publisher admission guard requiring exact-target native plus live evidence. The native publisher invokes the qualification guard before creating target/digest-addressed artifacts; the full bundle publisher composes it in t4. s8 owns live qualification. Application paths/databases and the host daemon were untouched.

POSIX uses nonblocking flock and CLOEXEC/NOFOLLOW; Windows uses non-inheritable CreateFileW handles, nonblocking exclusive LockFileEx, current-user SID/DACL and local fixed/removable NTFS/ReFS probes. Both retain and verify the file anchor. POSIX replacement uses rename, file fsync and directory fsync. Windows uses same-volume MoveFileExW with REPLACE_EXISTING and WRITE_THROUGH for publication, then opens and FlushFileBuffers on the published file. ReplaceFileW has no supported WRITE_THROUGH option and is not used. Portable POSIX-style directory fsync is unavailable there; Windows write-through publication is implemented in the native adapter. A replacement error is uncertain and requires authoritative inspection. No process signals/PID probes/age-based ownership occur in product code.

Enrollment is not an alternate active-release selector: its immutable identity makes a missing controller fail closed. Interruption between sentinel and first snapshot also fails closed, requiring explicit recovery. The selected release and operation are always one schema-validated snapshot.
