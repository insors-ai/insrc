01 / PROBLEM & OUTCOME

See delivery, without reconstructing it from documents.

insrc produces a chain of machine-readable artifacts for planning, design, review, and implementation. The work hierarchy is distributed across those artifacts: an epic defines stories, a plan defines tasks, and build and review records supply execution evidence. Reading files individually makes it hard to answer “What is ready?”, “What needs my decision?”, or “Why does this item look complete?”

The board projects these records into a navigable work view. A reviewer can move from an epic to a story, inspect its tasks and dependencies, and understand the evidence behind its stage without losing the surrounding delivery context.

Product principle: preserve the difference between workflow progress, human approval, automated review, and task validation. A convenient status label must not conceal contradictory evidence.

Desired outcomes

  • Find work requiring review or approval without opening each artifact.
  • Understand the epic → story → task hierarchy and associated defects.
  • Trace every stage and warning to its source record.
  • Recognize missing or conflicting evidence before making a delivery decision.

Evidence from the design snapshot

The 1 October snapshot used for the prototype contained 635 artifact files, 31 epics, 226 story/issue cards, and 795 task or validation entries. The cards included 13 issues. Task/validation entries include build-only records; this is not a count of 795 uniquely planned tasks.

Fourteen approved build records contained at least one task marked failed. This establishes a display requirement, not a diagnosis of those builds: the board must show both approval and validation evidence without choosing one as an implicit correction of the other. A 7 October recount found 730 files and 29 such builds, so the conflict is routine rather than rare. Snapshot counts are illustrative, not fixed product values.

02 / SCOPE & USERS

A read-only first release.

Primary users

  • Developer: inspect the current story, its plan, prerequisites, and validation.
  • Reviewer: find pending decisions and blocking findings.
  • Delivery lead: understand progress across epics and standalone work.

MVP includes

  • Board, epic rollup, and issue views.
  • Search, epic scope, and attention filtering.
  • Story/issue details with nested tasks.
  • Approval, review, validation, and source evidence.
  • Refresh and explicit freshness/error states.

Out of scope

The MVP does not create work items, approve or reject artifacts, launch coding agents, edit JSON, or move work by drag-and-drop. It does not introduce assignees, sprints, due dates, priorities, estimates beyond recorded fields, or Jira synchronization. Live agent activity cannot be inferred from the existence of a plan or build artifact.

Review annotations and agent handoff are a follow-on capability. If added, “request changes” records feedback for impact assessment by the coding agent; it must not mechanically revert a code hunk or silently change workflow state.

A one-story fix chain should not appear as two unrelated cards merely because it has both ISSUE and LLD artifacts. Preserve both identities in a single issue card with its fix story nested. If an issue has multiple fix stories, expose that hierarchy explicitly instead of silently collapsing them.

Resolve identity through the framework’s canonical rules. The prototype found one case variant, S001 versus s001, and joined it. The framework’s canonical identity compares story IDs by number: s1, S1 and S001 all name story 1 (storyIdToOrdinal in src/workflow/id.ts), so case and zero-padding variants are the same story. The product joins them under that rule, retains the source IDs, and flags any collision the rule cannot settle rather than merging it.

Board

Show six stage columns, ordered from scope to completion. The two “Ready” columns are alternatives, not consecutive steps: an item reaches “Ready · design approved” when its route has no plan step, or “Ready · plan approved” when it does, never both. Cards show type, human title, compact stable identifier, epic context, recorded size when present, and task-validation count. High-value badges expose review blocks, pending decisions, and validation conflicts. Avoid duplicating lengthy design text on cards.

The workspace scope starts with all work and offers individual epics and standalone work. Search matches titles, identifiers, and epic names. “Needs attention” filters across the selected scope. Column counts reflect the full filtered set, including cards behind “show more.” Empty columns remain visible.

Epic rollup

List epics with story counts, approved-build completion counts, task counts, and attention counts. Selecting an epic opens its scoped board. Completion is an unweighted count of completed stories, not effort completion or task validation. Standalone work is accessible separately and never assigned to an invented epic.

Issue view

Show defect cards using the same evidence-based stages. Preserve issue title, fix intent, magnitude when recorded, parent reference, feedback, and associated fix work. A missing parent is a visible unresolved link, not grounds for dropping the issue.

Work-item details

Opening a card reveals the full title, purpose, stage explanation, independent gate signals, and source artifacts. Expand tasks to see their descriptions, dependencies, acceptance checks, and recorded results. Story dependencies and linked issues are navigable. Closing details preserves scope, query, and board position.

The design preview uses a detail panel above the board; the IDE implementation may use a side panel when space permits and a full-width detail view when narrow. This placement is flexible. The content hierarchy and preserved selection are requirements.

05 / STATE & EVIDENCE

Derive the stage. Keep the gates separate.

Evaluate the rules in this order; the first match wins: an approved BUILD establishes completion; otherwise an existing BUILD establishes recorded build work; otherwise an approved PLAN on a route that requires one establishes “Ready · plan approved”; otherwise an approved LLD or ISSUE on a route without a plan step establishes “Ready · design approved”; otherwise an LLD or PLAN establishes design/planning; otherwise the work item is scoped.

Which gate makes an item ready depends on the route the framework recorded, not on which artifacts happen to exist:

  • Epic story or feature (full chain, or LLD meta.sizeClass = feature): the approved PLAN → Ready · plan approved.
  • small story (LLD meta.sizeClass = small): the approved LLD → Ready · design approved; no PLAN is expected.
  • Small bugfix (ISSUE meta.magnitude = small): the approved ISSUE → Ready · design approved; no LLD or PLAN is expected.
  • Sized bugfix (ISSUE meta.magnitude = sized): the approved PLAN of its fix story → Ready · plan approved.
  • Trivial: no design gate; the item first appears with its BUILD record.

When the route cannot be determined, do not guess: keep the item in the stage its artifacts establish and attach an “unknown route” data-quality notice.

Code review without a build record. A CR does not change the stage; only BUILD records establish recorded build work or completion. A story that has a CR but no BUILD keeps its design-derived stage and carries an “unledgered code review” notice explaining that code was reviewed before a build record existed. In the 7 October recount, 73 of 148 CR artifacts had no matching BUILD.

These rules are a display projection, not a new workflow state machine. Work that legitimately bypasses a plan reaches “Ready · design approved” through its own route’s gate; it is never shown as having an approved plan, and a missing PLAN on such a route is not reported as a gap. Where the daemon exposes authoritative eligibility or active-run state, show it as an additional fact rather than redefining historical evidence.

Independent signals

  • Approval: show approved (meta.approvedAt), rejected (meta.rejectedAt), or pending. Pending means neither stamp is present. The framework records no “changes requested” state; feedback that asks for changes is shown as review evidence, not as an approval state. Conflicting stamps require an explicit warning or authoritative resolution.
  • Review: preserve the recorded pass/warn/block verdict, its artifact, and an explicit override if one exists. A historical block on an approved artifact is distinguishable from an unresolved block.
  • Validation: a BUILD records each task as { id, passed } with passed true or false; the board shows these as Passed and Failed. Unrecorded is a board label, not a recorded value: it covers a planned task with no BUILD entry and a BUILD entry whose passed is absent. Unrecorded results are never treated as failures or successes. Tasks present only in a BUILD (build-only tasks) are shown and marked as unplanned.
  • Conflict: an approved BUILD with failed task results remains in Complete with a visible validation-conflict badge and explanation.
  • Dependency: show recorded prerequisites and their evidence. Do not infer graph edges from prose or translate every dependency into an execution blocker.
  • Freshness: identify stale plans/designs only when the framework’s revision or gate checks establish that fact.

“Needs attention” includes pending decisions, recorded rejections, unresolved review blocks, failed validation, validation conflicts, confirmed stale evidence, and unresolved references. Review warnings remain visible but do not automatically mean the work is blocked. A block verdict counts as unresolved only when the artifact is unapproved and carries no recorded override; an approved artifact with a historical block, or a block with an override, stays visible in its evidence but does not match “Needs attention.” This matters at scale: the 7 October recount found 31 artifacts with a recorded review override and 28 LLD or PLAN artifacts with a block verdict.

07 / DATA CONTRACT

The daemon owns interpretation.

The persisted source is .insrc/artifacts/. The production IDE client obtains a normalized read model through daemon IPC; it does not open the daemon’s databases or independently interpret artifact files. Reuse existing artifact and workflow read surfaces where they meet the requirements. An additional projection, if needed, remains daemon-owned.

Proposed read-model fields

Each work item needs a stable identity, original source identities, type, title, summary, parent/child relationships, derived stage and reason, gate signals, tasks, artifact references, revision timestamps, and data-quality notices. The response includes snapshot/freshness metadata and enough detail to distinguish “missing” from “not applicable.” This is a product contract, not an approved IPC schema.

Artifact ordering must use authoritative revision information. File modification time alone cannot establish which review applies to which revision. Effective amendments and extensions must be resolved through framework semantics; a stale base document must not overwrite newer accepted work.

Existing review feedback can be displayed read-only. A future annotation model should carry the work-item identity, reviewed revision, target location, concern, and resolution history so feedback remains interpretable after the code or artifact changes.

08 / QUALITY & EDGE CASES

Legible, recoverable, and explicit about uncertainty.

  • Accessibility: keyboard navigation, visible focus, screen-reader labels, and text labels for every color-coded state. Card selection and refresh results are announced without excessive chatter.
  • Responsive layout: wide IDE tabs use columns; narrow panes stack or switch to grouped lists. Titles wrap or reveal fully in details. Essential actions must not depend on hover.
  • Safe rendering: render artifact text as data. Never execute embedded HTML/scripts or follow arbitrary file paths from artifact content. File navigation must use the host’s existing authorized viewer.
  • Performance targets: after data arrives, show the initial board within one second for a fixture of 1,000 artifacts and 500 work items on the agreed reference environment; local filters should respond within 150 ms. These are proposed release targets, not measured prototype results.
  • Freshness: a failed refresh keeps the last successful view with a stale/error notice. An empty workspace, unavailable daemon, and failed read are different states.
  • Partial records: missing plans, build-only task results, absent titles, unknown kinds, and broken parent links remain inspectable. Report incomplete coverage rather than inventing content.
  • Concurrency: apply one coherent snapshot at a time. Drop superseded responses; do not combine half of an old snapshot with half of a newer one.
  • Determinism: the same snapshot and filters produce the same order and counts. Use recorded timestamps with a stable identity tie-breaker.

Evaluation

In a representative usability session, a reviewer should be able to locate a blocked story, explain why an item is Complete despite failed validation, and navigate from an epic to a task and its evidence without manually searching artifact JSON. Validate those tasks on both clean and contradictory fixture data before release.

10 / DELIVERY & DECISIONS

Keep the first increment focused.

  1. Validate the read model: confirm identities, relationships, status precedence, route-specific gates, and revision semantics against framework fixtures, including the observed conflict cases and code reviews without build records.
  2. Deliver the read-only board: board and epic views, issue navigation, task details, evidence, filters, and refresh/error states.
  3. Evaluate in an IDE: validate accessibility, narrow-pane behavior, performance, and the review tasks above.
  4. Consider controlled actions separately: annotations, agent handoff, and existing approval commands require their own interaction and workflow design.

Open decisions before implementation

  • First host: VS Code, JetBrains, or both. Keep projection semantics shared even if the first UI ships on one platform.
  • Placement: a dedicated editor tab is the leading candidate for a wide board; validate against a tool-window entry point.
  • Completion wording: “Complete” with explicit approval evidence versus “Completion approved.” Test whether users mistakenly interpret it as validation success.
  • Refresh strategy: manual refresh is sufficient for the first increment; confirm whether existing daemon events can support later automatic updates.
  • Canonical joins: confirm ID normalization, multi-story issue relationships, and effective amendment/extension handling with the daemon contracts.
  • Attention policy: confirm which historical pending artifacts remain actionable after downstream completion; do not permanently flood the filter with obsolete gates.

Design status: this PRD records the proposed product behavior. It is not an approved insrc workflow artifact and does not authorize implementation or approval-state changes.

11 / BASIS & REFERENCES

Grounding and validation limits.

This PRD builds on an interactive board prototype. It adopts the product direction that requested changes are annotated for an agent to assess, rather than mechanically rejected. Artifact examples and counts come from the local snapshot inspected on 1 October 2026, rechecked on 7 October 2026 where stated.

  • Machine artifacts — source records used for the prototype.
  • Workflow guide — framework context.
  • Daemon guide — daemon and IPC context.
  • Artifact definitions — per-stage types.
  • Build record implementation — build evidence and completion records.
  • Pending artifact logic — approval-state interpretation.

The prototype is a static read-only snapshot, not a live daemon integration. Its initial render and interaction logic were checked programmatically; it has not been verified visually in a browser. Production behavior for rejection, canonical identity, revisions, and refresh must meet this PRD rather than merely reproduce prototype shortcuts.
