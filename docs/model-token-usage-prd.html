01 / PRODUCT INTENT

Know what each model call consumed.

Every model request made for a workflow step contributes a durable record to its canonical root usage ledger, retaining the specific charged artifact identity. The Delivery board turns these records into explainable totals: what an LLD cost to create and review, what its PLAN and child tasks consumed, and what the complete story or epic consumed across all runs.

Confirmed requirements
  • Usage lives outside artifact JSON: one root data file contains append-only records for the root and its descendants.
  • Each model request is attributed to a specific workflow step and appended to that collection.
  • LLD usage includes all design-review rounds and revisions.
  • The Delivery board displays hierarchical totals, including PLAN and TASKS, with drill-down to contributing model calls.
  • The clickable mock extends the current board.

Everything else below is a proposed product contract for discussion. This is a draft PRD and prototype, not approval to implement the feature.

Users

Developers explaining a story’s usage, reviewers tracing review overhead, and delivery leads comparing models and identifying costly or incomplete workflow activity.

Success

A reader can reconcile a story total to its artifact activities and then to immutable model-call records, without guessing whether a review, retry or child task was included twice.

02 / EXISTING PRODUCT

Extend the board that exists today.

The current Delivery board has All work, Epics, Standalone and Issues views, six collapsible stage sections, search and Needs attention filters. An epic opens its stories. A story opens Overview & tasks, Records and Linked work. The proposed Usage tab and token summaries sit within that navigation; they do not replace it with a new dashboard.

Current source provides parent/child work-item identities and artifact evidence through the daemon’s DeliverySnapshot. A PLAN defines tasks; task validation and BUILD records reference those same tasks. These are several views of one activity, not separate billable activities.

Evidence limits: the existing provider interface has optional input/output/cache counters, but that alone is not a durable per-call ledger. CLI output may describe a whole invocation or session rather than a single physical model request. The feature must establish and expose the actual granularity instead of relabeling an invocation total as a model-call count.

Grounded in board-host.ts, board-views.ts, board-details.ts, delivery/types.ts, and LLMResponse.usage. Analyzer symbol lookups were corroborated with direct reads; directory profiles were empty and were not treated as proof of absence.

Coverage boundary: work executed by an external controller may be invisible to the daemon. The controller must submit usage through the same capture contract where its host exposes it. Missing host counters are marked unavailable. No integration may claim complete coverage merely because all daemon calls were measured.

A model attempt has exactly one callId, one charged artifact and one owning work item. A logical request may have multiple attempts; each attempt is a different physical call and counts. invocationId groups a CLI run or provider invocation. It is not a second charge. parentCallId expresses a causal relationship, not an ownership or summation edge.

Workflow stage, exact step ID, run ID, review round, requested model and actual reported model travel with capture context. If a model request is shared and cannot be attributed to one child, charge the nearest explicit common activity once. Do not split a single count by guesswork. An unresolved target is held in a visible unassigned/pending bucket until explicitly reconciled.

Ownership is rooted, single-parent and acyclic. Preserve the owner recorded at dispatch even if a later plan reparents a task. Reparenting must record an explicit attribution transfer/effective mapping, preserve historical provenance and still count each call once. Ambiguous identities, multiple parents or cycles produce notices and conservative partial totals; never recurse indefinitely or join by title.

05 / ROOT USAGE LEDGER CONTRACT

Keep usage outside artifact documents.

Each epic, standalone work item or issue has one canonical root artifact. Store one append-only Avro object container file at <project>/.insrc/usage/<root-artifact-id>/events.avro. All usage for the root and its descendants goes into this file. Individual LLD, PLAN, TASK and BUILD JSON documents contain no usage event arrays. TU1 must implement and validate a usage-root resolver over canonical work-item identities, stored ownership links and explicit dispatch bindings. Existing ArtifactIds.parentOf covers TASK/TASKS/DIAG → STORY and STORY → EPIC; it does not resolve every document kind or establish whether a story is standalone. Do not guess a root from a title, hash prefix or missing link.

.insrc/usage/EPIC-a17c42e69d035b81/events.avro
  root DEF and HLD authoring + reviews
  descendant LLD + PLAN + TASK + BUILD activity
.insrc/usage/ISSUE-<id>/events.avro
  independently rooted issue and descendant activity

Use the actual canonical root ID: EPIC for an epic work item; STORY for an independently rooted standalone story; ISSUE or SPEC only where it is the canonical independent root. DEF and HLD documents charge their epic root. A linked issue remains in its own root ledger when the relationship is only a reference. A non-root issue writes to its existing root. Every record carries rootArtifactId, charged artifactId, event/call identity, schema version and a root-local append sequence. Start records also carry workflow, model and attribution context; outcomes and corrections retain the same root/charged identity. Storage grouping does not change charging: a design review still charges its reviewed LLD.

Avro is the proposed live format because its header/schema and record blocks support an append-oriented writer. Parquet has column chunks and trailing file metadata, so reserve it for optional derived snapshots/exports, not the authoritative live append path. Neither format alone provides transactions, deduplication, locking or durable acknowledgment. TU1 must prove these behaviors.

Logical JSON export schemaExample ledger export

The JSON schema describes decoded events and API/export data, not artifact JSON or Avro bytes. The physical Avro schema and library are finalized and tested in TU1 design. The file header fixes its writer schema; evolve compatible reader contracts and nullable/defaulted fields. Any incompatible writer-schema migration needs an explicit recoverable migration plan before acceptance.

DuckDB reporting over Avro

Use the existing daemon-owned, in-memory DuckDB engine for filtering, grouping, time/model/step summaries and hierarchical reports. DuckDB’s core avro extension supports read_avro for one or multiple files. The current project driver instead decodes Avro into a derived Parquet cache before querying it; its pool disables automatic extension installation/loading. Direct Avro scanning therefore requires explicit trusted extension provisioning, offline/version/platform qualification and setup before pool lockdown.

TU1 exposes committed per-root snapshots and compatible schemas; TU4 owns reporting queries. Do not scan an uncontrolled live append tail or claim that a SQL sequence filter alone provides a physical file snapshot. Use a bounded committed-prefix snapshot or coordinated reader lease, record a watermark per root, then apply the shared effective-event reducer before aggregation. Corrections, duplicate events and overlapping invocation/call observations are not additional usage. Match SQL results against reducer golden fixtures. DuckDB tables, indexes and any Parquet caches are rebuildable; Avro remains authoritative.

Use explicit root allowlists resolved by the daemon for reports, including cross-root reports. Keep clients on IPC; do not expose arbitrary file paths or install extensions from user-supplied SQL. Extension unavailability produces a visible reporting outcome, not a complete zero. See DuckDB Avro documentation.

Append and recovery boundary

The daemon is the only writer. Serialize by repository and root ID, append complete Avro blocks, and acknowledge only after the block and required filesystem metadata are durable. A transient journal or checkpoint in the same root directory may support recovery but cannot become a second final ledger. On restart, validate the completed prefix, detect and isolate an incomplete tail, and recover staged events using stable IDs. Corruption inside committed history is an explicit failure, never silent skipping.

A root can reserve its stable ID and create its usage ledger before a valid artifact body exists. Child events can target reserved stable child IDs under that root. Reconcile pending identities when documents are created without copying usage into them, fabricating design content or rerunning inference. A missing root cannot be guessed: block dispatch/report recovery until a valid root reservation can be established.

Read to an acknowledged root watermark while appends continue. Artifact regeneration, approval and deletion do not rewrite the ledger. Keep all original observations; corrections and attribution transfers append new facts. Cross-root transfers reference the original event and are coordinated recoverably: do not copy a second charged call into the destination ledger. Root deletion/retention and branch imports are explicit ledger operations, not ordinary artifact JSON merges.

One live file per root is the initial contract. Set measurable size/read-recovery limits in TU1; do not silently rotate, truncate, compact or introduce multiple authoritative files. Derived indexes and Parquet exports are disposable and identify the source root watermark. Directory creation and root IDs must be validated against the registered repository; clients cannot supply arbitrary filesystem paths.

06 / TOKEN SEMANTICS

Normalize before adding.

CounterMeaning / arithmetic
inputUncachedTokensInput processed without a cache hit, excluding cache reads and cache writes under this normalized contract.
cacheReadTokensInput served from cache; a separate input bucket. Count once even if native input totals include it.
cacheWriteTokensInput written to cache; separated from both uncached input and cache reads.
outputTokensAll generated output, including reasoning when the native provider includes it.
reasoningTokensInformational subset of output. Never added again to processed tokens. If native output excludes reasoning, the adapter must normalize output to an inclusive value first.
Processed tokens = uncached input + cache read + cache write + output
Reasoning tokens ⊆ output; do not add them a second time.

Adapters must declare and test native semantics. Example: inclusive input 10,000 with 6,000 cached normalizes to 4,000 uncached + 6,000 cache-read. A native report that already excludes cache must not be subtracted again. Unsupported cache metrics are zero only when the provider contract establishes that no such consumption occurred; otherwise they remain unknown. Counts from different tokenizers are useful workload totals, not equivalent effort or monetary units.

Per-call observations are preferred. Session-cumulative counters must be differenced against a durable baseline within the same native session/model; a missing baseline, counter reset or model change makes the delta unknown until reconciled. Never sum successive cumulative snapshots.

If a CLI reveals only per-model totals for one invocation, retain that granularity and model slice with physical call count unavailable. When leaf calls and a CLI aggregate overlap, choose exactly one non-overlapping accounting basis per invocation/model. The aggregate is fallback evidence, not additional usage. A later decomposition must append an explicit reconciliation that excludes the fallback from addition while retaining its provenance. The initial event schema will require a versioned reconciliation extension before supporting mixed overlapping observations; it must not silently ingest both. An aggregate-only integration does not satisfy the product’s complete per-call coverage claim.

Reported / estimated / unknown stay separate. Default totals sum provider-reported values and show ≥ with “Partial” if components are unknown. Estimates are disclosed separately and included only with an explicit control; then use ≈ and label the estimate portion. If unknown usage also remains, show “≈ known + estimates + unknown”; an estimate is not a strict lower bound. Pending means a durably recorded start without a terminal observation; unavailable means a terminal/interrupted attempt whose usable counters are absent. Neither is measured zero. A genuine instrumented zero is 0. Legacy absence is “Not recorded”. A model not confirmed by the response remains “Requested model; actual unavailable”, not an asserted actual model.

07 / HIERARCHICAL AGGREGATION

Sum leaf observations, not displayed totals.

Normalize identities using the framework’s canonical work-item rules, select one valid effective observation per physical call, resolve its charged owner, and compute the owning tree bottom-up. Revisions and superseded artifacts retain their historical usage. Deleting or regenerating a design body must not erase consumed work.

OwnUsage(node) = Σ effective calls charged directly to node’s artifacts
InclusiveUsage(node) = OwnUsage(node) + Σ InclusiveUsage(owned child)
StoryTotal = LLDWithReviews + PLAN + Σ TaskTotal + SharedStoryWork
EpicTotal = DEF/HLDWithReviews + Σ StoryTotal + other explicit owned work

For the story presentation, “LLD + reviews” is its design subtotal; “Follow-on activities” is PLAN + child tasks + shared build/review work. Their sum is “Story total”. A child-task subtotal is already part of follow-on activities; its expanded rows are explanatory partitions, not extra additions.

Model, metric and run/time filters are applied to the same effective-call set before all rollups. They never change work ownership. Search and Needs attention filter cards, not the underlying ancestry: show a separate Matching items subtotal where relevant, and do not present it as the epic’s all-scope total. Querying story + task + epic selections uses a union of call IDs, never a sum of their already-inclusive values. Older model IDs remain distinct unless an explicit stable alias mapping proves equivalence.

Project totals, coverage, data-quality warnings and the usage watermark must come from the same daemon snapshot. The board receives computed aggregates and paged call details through IPC; clients do not open LMDB/Lance or recompute financial-looking totals from incomplete display rows.

08 / DURABILITY & INTEGRITY

Usage history survives independently of artifact writes.

RequirementAcceptance behavior
Append-only, idempotent writerSerialize per-root appends through the daemon-owned usage ledger service. Stable event IDs survive retries. An identical duplicate is acknowledged without another charge; a different payload reusing that ID is a conflict, not last-writer-wins.
Crash recoveryA started event is durable before dispatch. Recover staged Avro appends and pending root/child identity reservations after restart. A crash after dispatch without usable counters leaves an interrupted/unknown attempt; no model re-execution just to collect telemetry.
Preserve on rewrite / revisionArtifact writers and codecs do not own usage bytes. Artifact import/export must explicitly include or disclose missing root-ledger data; regeneration and approval leave ledger bytes intact. Usage-only appends do not change description/body/citations hashes, invalidate approval, or reset content revision. They advance a separate usage sequence/watermark.
Failed recordingSurface the capture failure and retain completed result/recovery evidence. Retry the append, not the model call. If capture cannot durably record a new start, refuse that dispatch with a recoverable accounting error rather than knowingly starting an untraceable call.
Git / concurrent branchesBinary ledger files must not be merged as text. Import branch histories through the daemon, union immutable events by stable ID and validate root/owner/call identity. File offsets and timestamps are not identities. Concurrent edits or forked corrections remain visible conflicts until reconciled; do not discard either branch.
CorrectionsA correction replaces a complete observation; it is not an additive charge. Preserve the original. Use the last unambiguous valid correction chain; cycles, forks, mismatched owners or nonexistent targets produce partial/conflict notices.
Data retentionKeep usage across rejected designs, retried steps, cancelled runs and artifact supersession. An explicit deletion/retention policy must preserve a tombstone/retained accounting owner; silent loss cannot look like reduced historical consumption.

The existing content hash covers description, body and citations. Root-ledger appends leave artifact files intact; implementation must verify independent freshness, root identity and paired import/export behavior.

On first adoption, do not backfill guesses. Allow a source-verified import as explicitly marked provenance, with deduplication against existing native IDs. Store bounded normalized facts, not raw prompt/response transcripts. Existing provider access remains through local CLI OAuth or local Ollama.

Compatibility and quality states are explicit: legacy/not-recorded means work predates usage capture and has no ledger evidence; missing means expected ledger data is absent; unsupported means the writer or record schema cannot be decoded safely; malformed means structurally invalid or conflicting accounting data was encountered. Each retains readable artifact content and produces an accounting notice rather than complete zero. Malformed committed history is never silently skipped. No unaware reader or artifact writer may rewrite unsupported ledger bytes.

Suggested implementation sequence

  1. Contract + store: finalize schema, IDs, charged ownership and normalization; implement durable append/recovery/preservation and reducer fixtures.
  2. Capture: instrument the existing provider and workflow context seams; add native CLI usage extraction and controller reporting with explicit coverage limits.
  3. Read model: compute canonical ownership rollups, quality/coverage and snapshot watermarks in the daemon; expose paged call evidence.
  4. Board: add usage summaries, filters and drill-downs to the existing views; validate arithmetic, accessibility and performance.

Future work must enter the normal tracked triage/design/plan/build/review process. This PRD does not mint an epic, approve implementation, or alter existing usage ledgers.
