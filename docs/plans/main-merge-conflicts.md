So the merge is worth doing for its own sake (these are the codex review paths), but it is not a one-commit fix.

## The shape of the divergence

The two branches rebuilt the same files for different reasons. Reading the conflicts, they fall into six themes:

| Theme | `v2` side | `main` side | Files |
| --- | --- | --- | --- |
| T1 daemon process model | shutdown/lifecycle ownership of the run files and the socket (`DaemonRunFileOwnership`, guard, watchdog), approval IPC (my s3), team settle/park, repo.convert | daemon threads (Epic 86197ac6): the request tables moved out of `index.ts` into `handler-runtime.ts`, `IpcServer` takes a `forward`, workers, router, idle maintenance | `daemon/index.ts`, `daemon/server.ts`, `config/config-catalog.ts` (+ its test) |
| T2 workflow step state | in-memory store, `RunEntryMeta` (owner, upstream revisions), `listStates` | persisted store `getStepStateStore()`, every call async | `workflow-step/state-store.ts`, `state.ts`, `phases/start.ts`, 4 tests |
| T3 review step | persisted through the lifecycle service (`LifecycleService`, `REVIEWER`/`CONTROLLER` actors) | async state-store clear, heartbeat, idle timeouts | `review-step/*`, `workflow-review-rpc.ts`, 3 tests |
| T4 review pipeline | `70e8601e4` last-agent-message | reasons on a rejected answer, stall budget (new tests) | `review-pipeline/driver.ts`, its test |
| T5 build/code review | records and approval through the lifecycle (`approveJson`, `approvalStateOf`) | `approveArtifactByJsonPath`, `REVIEW_CALL_LIMITS`, a Story with no carrying commit is `no-build-record` | `build-step/*`, `build-record.test.ts`, `subject-attribution.test.ts` |
| T6 small independent fixes | two fixes of the same defect on each side | | `rdbms-common.ts`, `shell-helper.ts`, `store-child.ts` |

T1 and T2 are the real merges; T3 to T5 are mostly mechanical once T2 is decided; T6 are choices between two fixes of one defect.

## The 29 files, one by one

"Resolution" is what I propose; none of it is done. Effort is a rough size: S = a minute, M = a careful read, L = a design decision plus a port.

### T1 daemon process model

1. **`src/daemon/index.ts`** (4 hunks; 1640 lines on `v2`'s side, 31 on `main`'s). *Effort L, the hardest file.*
   - Hunk 0 (imports): `v2` imports `handoff-rpc`, `park-offer`, `signoff-registration`, `list-models`, `update-runner`, `installed-commit`; `main` has none of them there.
   - Hunk 1 (1623 lines): on `main` the whole block of request handlers was **moved out** to `./handler-runtime.ts`
     (Epic c2ba6fa6 s11, "buildHandlerRuntime"). `v2` edited that block in place in 17 commits (approval.subscribe/answer from my s3,
     `team.settle`, `team.park/resume`, `repo.convert`, `repo.settings.*`, the feedback and identity services, the tracker attach and Task syncs,
     the shutdown work). Git cannot carry those edits into the new file.
   - Hunk 2: `v2` registers `registerParkOffer()`/`registerSignoff()` and builds `new IpcServer(rpcHandlers, streamHandlers)`; `main` builds the router and
     `new IpcServer(router?.forward ?? local)`.
   - Hunk 3: `v2` keeps `serverClosing = server.close()` and `endForRunFileConflict`; `main` has `void server.close()`.
   - Resolution: take `main`'s structure (the handler tables in `handler-runtime.ts`, the forward-based server), then **re-apply each of `v2`'s 17 commits' handler changes
     into `handler-runtime.ts`**, keep the park/signoff registration, and keep `v2`'s close-with-ownership sequence around `main`'s `server.close()`.
     Find the edits with `git diff 1f4d9b21a HEAD -- src/daemon/index.ts` and replay them by method name.
2. **`src/daemon/server.ts`** (2 hunks). *Effort L (depends on 1).*
   - Imports: `v2` `DaemonRunFileOwnership, daemonRunFiles`; `main` `randomUUID`, `TrustedRpcContext`, `rmSync`. Take both.
   - Constructor: `v2` `(handlers, streamHandlers, now, socketPath, ownership?)`; `main` `(forward: ForwardRequest, now, socketPath)`. The two designs disagree on what the
     server is handed. Proposal: `(forward, now, socketPath, ownership?)`: `main`'s forward, plus `v2`'s ownership argument; `v2`'s `handlers/streamHandlers` fields go away if `forward`
     covers them (check the stream handlers: `main`'s `directDispatch(rpcHandlers, streamHandlers)` takes both).
   - `v2`'s shutdown tests (`server.test`, the shutdown suite) construct `IpcServer` with the old arguments and must be updated to the new constructor.
3. **`src/config/config-catalog.ts`** (1 hunk). *Effort S.* Both sides add rows after `ollama.host`: `v2` `daemonUpdate.repoUrl`, `daemonUpdate.branch`; `main` `daemon.threads.enabled` and four `daemon.maintenance.*`. Keep all.
4. **`src/config/__tests__/config-catalog-contract.test.ts`** (1 hunk). *Effort S.* Row count and its description. Merged catalog = `main`'s 48 rows + `v2`'s `daemonUpdate.repoUrl`, `daemonUpdate.branch`, `tools.commonApproval`, minus `permissions.mode` (see "Clean merges") = recompute after the merge; do not guess, run the test.
