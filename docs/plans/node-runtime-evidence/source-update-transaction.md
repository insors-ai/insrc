# Linux source lifecycle transaction (task t4)

ISSUE/LLD/PLAN `a03e99e17a364550`, story s1, task t4. Public installer, shell, daemon/TUI/MCP and IDE routing remain t5–t7. Production historical/native and retained-data qualification remains t9–t11. No user daemon or live database was stopped or changed by this task.

`LinuxSourceTransaction` composes the existing Linux process identity and retained process-capability APIs with `SourceInstallationStore`. Its platform-effect contract requires actual actor/descendant closure, quiesced format validation and verified runtime bindings. It does not signal numeric PIDs, interpret socket disappearance as exit, or substitute journal metadata for archive verification. The adapter invoking `start` must record the retained actor durably before granting startup/store access. An unrecorded spawn or unavailable child-closure proof leaves the transaction fenced and withholds restoration/start. Binding these effects to independently delivered public entrypoints is the next task; the miniature test host is not a production daemon adapter.

| Relationship | Direction, ownership and recovery |
| --- | --- |
| Source state → active transaction | Zero or one active transaction. One exclusive mutation lease serializes update, selected-release start/restart/stop and recovery. The lease retains root/parent descriptors throughout asynchronous work; replacing a directory fails ownership checks. |
| Transaction → original/candidate/restored actor | Zero or one recorded identity per role. The actor owner retains its kernel capability and supplies independent descendant-closure evidence. A replacement incarnation is a conflict, never a signal target. |
| Transaction → source releases | One staged candidate and one independently qualified prior; the initial selector may be absent. Full immutable selection receipts, pins and monotonic source floors remain retained. Ordinary lifecycle actions require the unchanged selected release; actual updates still require distinct compatible releases. |
| Transaction → execution intent | Optional additive evidence for compatibility, operation, desired running state, actor identities and closure/step receipts. Historical preparation-only state stays readable; records without sufficient execution evidence cannot authorize cutover. |
| Transaction → selector/outcome | Selection and phase share one atomic journal. Terminal phase and outcome publish together. Unknown publication is reread/flushed before another effect; a not-published callback is never replayed. Once committed, a later health failure cannot turn the completed update into rollback. |

Preparation failure leaves incumbent execution and selection unchanged. After pin/runtime revalidation, the owner records the stop intent, proves original/children closure, holds run-file exclusion, validates quiesced stores, and atomically selects the candidate. Readiness failure closes the candidate and its children before restoring the exact previous selector, including the absent legacy sentinel. Prior startup occurs only when `wasRunning` was true. Start on an already-running selected release preserves the process; restart starts a selected release even when it was stopped; stop preserves selection. Interrupted uncommitted operations reconcile toward the saved predecessor, while durable committed/rolled-back outcomes remain final. Recovery checks the old controller's full Linux incarnation/positive exit, not PID age.

## Evidence

Each wrapper ran on actual OrbStack Ubuntu arm64 and emulated x64 using the retained owned Node 22.22.1 distribution. Guest TAP is retained in `.insrc/tmp/source-transaction-linux-SmZazI` and `.insrc/tmp/source-transaction-linux-DiPsEP`.

The transaction fixture compiles the actual Linux process broker, captures real pidfds, and starts separate daemon stand-ins with owned child processes and a single-writer store sentinel. It checks build-before-cutover failure preservation, mutation competition, children-before-selection ordering, failed readiness and exact prior restoration, both selector forms, stopped-update behavior, ordinary lifecycle behavior, unknown child-closure fencing, and parent-directory replacement. Disposable controller processes exit after each of all nine durable phases; a replacement controller recovers them through the journal and real process observations. Before/after-rename faults exercise reconciliation without duplicate startup.

An earlier expanded run exposed that lifecycle actions incorrectly called the distinct-release update predicate. That was corrected by requiring lifecycle actions to use the unchanged selected release; the update predicate and Darwin owner were not weakened. Guest TAP is now retained on failure as well as success. Initial strict-typing errors were fixed before the successful final build. These miniature fixtures establish transaction/process/persistence behavior, not production native-module compatibility or live user-data reopen safety.
