Native Ollama coding harness

Run tracked coding tasks with an Ollama model in an insrc-controlled session. The session can inspect a repository, call MCP tools, make authorized edits, run tests, and return a validated workflow result.

Problem and scope

insrc already has a native OllamaProvider for inference, streaming, tool calls, and structured completions. It also has a daemon tool executor and MCP workflow tools. A coding session needs to connect these pieces through a supervised loop that retains task state, routes tool calls, and returns a result the workflow can trust.

In this PRD, native Ollama means the coding harness uses the Ollama chat protocol through insrc's provider boundary. insrc controls the session contract, repository scope, tool policy, and workflow result. An embedded library can implement the loop if it preserves those controls and supports the native transport.

The first release targets a single user, one registered repository, and one approved build task with a local Ollama model. Ollama Cloud is a later qualification target subject to insrc's existing cloud access policy and the selected model's capabilities. Multi-agent coordination, a new IDE interface, and automatic workflow approval are outside the first release.

User journey

  1. Select a registered repository, an approved coding task, and a configured Ollama model. See the effective model and whether the session has permission to edit files and run tests.
  2. Start the session from insrc. The harness loads the task, repository steering, relevant indexed context, and scoped context from shared project memory. It exposes tools permitted for that task.
  3. Follow progress as the model requests context, proposes edits, and runs approved checks. Handle any existing human permission prompts and cancel the session if needed.
  4. Inspect the resulting diff, test results, and workflow output. A valid result goes back to the existing build and review flow. Failures show which actions completed and what remains to be done.

The shared memory service owns project memory across sessions and agents, including corrections and forgetting. The harness owns execution recovery records such as tool receipts and interrupted actions. The managed adapter owns capture and excludes context it previously delivered from new capture. Structured output

  1. Use the workflow schema. The host supplies the exact JSON Schema for the current workflow phase and validates every final artifact against it with Ajv before handing it back to the workflow. Validate MCP tool arguments against their own schemas before dispatch.
  2. Finalize after tool work. Request one JSON artifact after edits and tests complete. Give the finalization and repair calls only the task context, recorded tool evidence, and the schema. Those calls have no access to action tools. Check claimed test outcomes and other reported actions against host receipts.
  3. Choose an output mode for the model and route. Use Ollama's native schema format on qualified local configurations. For Ollama Cloud, qualify prompt-based JSON over an approved route without a provider-side schema constraint. A JSON mode or dedicated response tool may be used only after the exact model and route pass the same acceptance tests. Ollama structured outputs
  4. Repair invalid responses within a fixed budget. Treat missing output, invalid JSON, and schema violations as validation failures. Return concise validation feedback, including field paths when available, and request a replacement artifact. Keep one overall correction budget across the worker and host. If the budget runs out, report the failure, retain the diff and test evidence, and leave the workflow pending.
  5. Qualify finalization for each prototype. Start with insrc's validateAgainstSchema and withStructuredRetry using OllamaProvider. If a Python worker owns finalization, evaluate Python Instructor with a Pydantic response model. The insors-extraction precedent uses instructor.from_openai with Mode.JSON over Ollama's OpenAI-compatible /v1 endpoint, with tests against local Ollama. Any such adapter must satisfy the PRD's native transport requirement. The original workflow schema remains authoritative at the insrc boundary. insrc validation and retry helpers · Instructor's Ollama integration

Framework decision

Prototype a Vibe fork with a native Ollama backend. Pin an Apache 2.0 release and verify that its Unified Harness provider code is available under terms that permit modification and redistribution. Build that release before changing it. Add native Ollama as a selectable provider in Vibe's existing model and provider configuration. Its endpoint setting selects the server and its API style selects the protocol. The new backend must speak Ollama's native /api/chat protocol. Use insrc's existing Vibe app-server integration for session verification and turn handling. Existing Vibe integration · Vibe configuration · Vibe build guide

  • Map messages, tool definitions, tool calls and their results across the native chat stream. Verify multiple tool calls, cancellation, partial responses, provider errors, and final token counts. Treat absent usage counts as unavailable.
  • Qualify model capabilities for tool use, thinking, context limits, and optional inputs. Check that compaction and other auxiliary inference use the intended model and provider. Verify that local sessions work with internet access disabled and without Mistral credentials.
  • Exercise final artifact generation independently of Vibe's coding turns. Keep insrc's workflow schema, bounded repairs, tool authorization, and shared project memory in force. Qualify local schema formatting and the approved Cloud route separately.

Measure how much code the native adapter would require and where that code would live. Record the Python and Rust build and runtime dependencies, release packaging, and maintenance cost of any changes to upstream Vibe. The prototype must cover authorized edits and tests, cancellation, and an interrupted action with an uncertain result. Vibe license

If Vibe cannot meet those requirements with a maintainable adapter, evaluate the MIT-licensed OpenHands Software Agent SDK or a small TypeScript runner built on the existing provider, executor, and workflow interfaces. OpenHands uses LiteLLM by default, so verify its native provider integration separately. Use the same task, model, tool policy, and schema for each candidate. Non-functional requirements

  • Security. Treat repository and tool output as untrusted input. Keep permissions outside model prompts. Enforce the registered worktree boundary, including paths resolved through symlinks. Keep credentials out of model context and diagnostics. Give subprocesses only the credentials and network access required by approved tools.
  • Reliability. Use stable action identifiers and durable receipts for tool effects. Recovery must distinguish completed, failed, and unknown outcomes. Keep model requests serialized per the repository's existing provider policy.
  • Observability. Record the model, session and task identity, tool decisions, timings, validation failures, and terminal status. Redact secrets from persisted logs. Track completion rate, schema validation success, and time spent in inference and tools during the pilot.
  • Resource limits. Bound context growth, tool output, elapsed time, and repair attempts. Preserve the approved task and unresolved work when reducing context. Show when a configured limit ends the session.
  • Compatibility. Keep a tested list of supported Ollama versions and model configurations. Document the operating systems and prerequisites for any bundled runtime or workspace isolation. Verify offline operation for local inference and local tools after setup.

Acceptance and rollout

Phase 1 · Local vertical slice and framework evaluation

  1. On a small approved task in a registered test repository, a local Ollama session calls an insrc MCP tool, makes an authorized edit, runs a permitted test, and returns a schema-valid artifact through the normal workflow handoff.
  2. A denied write and an out-of-scope path both produce a visible denial and leave the filesystem unchanged. Cancelling a session stops new tool calls and shows any changes already made.
  3. Fixtures cover missing output, malformed JSON, and valid JSON that violates the workflow schema. A valid correction is accepted within the configured budget. Exhausting the budget leaves the workflow pending and preserves edit and test evidence. Verify that repair does not rerun edits or tests.

Phase 2 · Local pilot

Exercise restart recovery, permission prompts, missing model and MCP failures, failed tests, and local operation without internet access. Demonstrate that an interrupted tool call with an uncertain outcome does not trigger a duplicate write or command. Publish the tested model and platform combinations and the pilot metrics before widening availability.

Demonstrate a handoff in both directions between the Ollama harness and another supported managed agent. After the memory service applies an eligible submission, a new session in the same project receives the scoped handoff. A session in a different project receives only its own context. Verify that corrections and forgetting affect subsequent sessions, that replay avoids duplicate capture, and that memory outages are visible.

Phase 3 · Ollama Cloud qualification

On an approved route, repeat the end-to-end acceptance case with the chosen cloud model. Verify prompt-based JSON with a representative workflow schema, one successful repair after an invalid response, and explicit failure when retries are exhausted. Record the model, route, and output mode that passed.

Open decisions

  • Which local model and minimum Ollama version should the pilot support?
  • Can Vibe's Unified Harness use insrc's native Ollama provider and tool policy through a maintainable adapter, and which component should own durable session state?
  • Which approved cloud route, if any, can use the native Ollama protocol while honoring repository policy?
