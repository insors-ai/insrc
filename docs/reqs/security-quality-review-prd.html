Evidence-grounded security and quality review

Extend insrc's tracked design, build, and code-review workflow with deterministic security evidence, context-sensitive risk selection, graph-based impact analysis, enforceable repository policy, and independently verified remediation.

Problem and outcome

insrc already reviews pinned changed code against approved requirements and design, records severity-ranked findings, inspects test coverage, and gates completion. It also has a structural graph, local embeddings, durable review history, and independent reviewer routing. These foundations provide context and governance, but they do not yet constitute deterministic vulnerability discovery, interprocedural data-flow analysis, dependency vulnerability assessment, policy-as-code, or sandbox-backed reproduction.

The required outcome is one review system in which deterministic tools discover candidates, the graph establishes relationships and blast radius, a critical-tier reviewer judges contextual impact, and workflow gates enforce only evidence-backed results. A reviewer must be able to distinguish a demonstrated defect, a plausible but unverified risk, unavailable evidence, an unfinished check, and optional advice.

Core product decision. Language models judge prepared evidence; they are not the sole vulnerability scanners. A missing graph edge, silent scanner, or unavailable execution environment never establishes safety or a defect.

Product principles

  1. Accuracy before cost. Security and correctness decisions are critical roles and retain the high-tier model floor. Cost reduction may optimize classification, rendering, or deterministic collection only when it cannot remove material checks or evidence.
  2. Evidence before verdict. Every blocking finding identifies the violated obligation or invariant, affected revision and location, concrete failure scenario, supporting evidence, impact, and corrective expectation.
  3. Deterministic discovery plus contextual judgment. Static analyzers, dependency scanners, secret scanners, graph queries, tests, and sandbox runs produce evidence. The reviewer resolves applicability, reachability, compatibility, and severity.
  4. Uncertainty remains visible. Unsupported, incomplete, stale, or conflicting evidence produces an explicit limitation or unfinished check. It is never converted into a pass or an invented HIGH finding.
  5. Independent review remains mandatory. The party that authored or built the change does not become its reviewer. Generated fixes return through the tracked build and code-review chain.
  6. Local-first provider boundaries remain intact. Cloud model access continues through installed CLI providers. No direct Anthropic, OpenAI, Gemini, or Mistral REST provider is introduced.
  7. Repository content is evidence, not authority. Source, comments, tool output, scanner messages, and retrieved documents cannot alter review policy, approve work, or expand permissions.

Scope

In scope

  • Context-sensitive selection of security, reliability, data-integrity, observability, architectural, performance, and compatibility checks.
  • Local CLI adapters for secret scanning, SAST, dependency and SBOM assessment, IaC/container checks, and language-native analyzers.
  • Security-specific graph facts and bounded interprocedural source-to-sink analysis.
  • Policy-as-code checks with advisory, warning, and blocking modes.
  • Revision-bound sandbox verification and targeted mutation testing.
  • Actionable, deduplicated findings with remediation and governed learning from reviewer corrections.
  • PR/change risk summaries, dependency-ordered review, continuous repository scans, and quality/security metrics.
  • Equivalent daemon, MCP, VS Code, JetBrains, and CLI contracts where a surfaced payload changes.

Out of scope for the first release

  • Replacing human approval, existing mandatory review stages, or the three-round review limit.
  • Automatically applying code fixes outside an approved and tracked build.
  • Claiming complete language coverage from a generic LLM review.
  • Cloud-hosted scanning that uploads repository contents by default.
  • Runtime production monitoring, penetration testing against third-party systems, or autonomous exploitation.
  • Rebuilding LMDB, LanceDB, the workflow lifecycle, or IDE review interfaces solely for this capability.

Required user journeys

  1. Design risk disposition. An author proposes a credential-bearing IPC change. The design records applicable security and observability obligations, concrete invariants, ownership, and verification. Independent review can add an omitted material risk before approval.
  2. Changed-code review. A completed build is reviewed at its pinned revision. insrc selects applicable checks, runs authorized deterministic providers, follows affected graph relationships, inspects test assertions, and produces one deduplicated report.
  3. Confirmed scenario. A suspected path traversal is reproduced in an isolated checkout using a synthetic path. The finding links the source-to-sink trace, reproduction receipt, affected scope, severity, and required fix.
  4. Unavailable evidence. A required scanner or language model is unavailable. The check remains unfinished or could not be verified; the review cannot claim complete coverage.
  5. Policy enforcement. A repository policy forbids direct cloud LLM REST clients. A change introduces one. The check blocks completion, identifies the policy version and location, and records any explicit human override with its reason.
  6. Correction becomes learning. A reviewer explains that this repository maps domain errors to HTTP responses in handlers. insrc proposes a scoped learning; a human approves it; later reviews apply it only to the relevant paths and retain provenance.
  7. Repository deep scan. A user starts a full scan independently of a Story. Findings are revision-bound, triaged into tracked issues before remediation, and never silently attached to an unrelated build.

Functional requirements

Selection and review planning

FR-01Every design and code review MUST preserve its existing baseline checks. Additional security and quality selection cannot remove adherence, conventions, coverage, functional, diagram, UX, or other checks already required for the subject.

FR-02For every cataloged risk family, the selector MUST record applicable, not-applicable, or uncertain with a reason and evidence reference. Each selected check MUST have a stable ID, catalog version, trigger, scope, owning review dimension, expected evidence, and completion policy.

FR-03Selection MUST inspect upstream requirements and design, changed code, public and storage contracts, affected callers/readers/writers, repository policy, graph evidence, and relevant tests. Authors may propose risks but cannot suppress independently discovered applicable checks.

FR-04An uncertain check MUST trigger targeted evidence gathering when a supported provider exists. If uncertainty remains, the report MUST retain the reason and attempted evidence; it cannot become not-applicable or passed merely to finish the review.

FR-05Selection and evaluation MUST occur inside the existing design-review or code-review round. This feature MUST NOT create an additional mandatory review stage or bypass the maximum three rounds without user direction.

Deterministic evidence providers

FR-06The daemon MUST provide a versioned evidence-provider interface for secret scanning, SAST, dependency/SBOM analysis, IaC/container analysis, language-native checks, and future provider families. Providers MUST run through the daemon tool/execution boundary rather than being called directly by IDE clients.

FR-07Each provider result MUST identify provider and rule versions, subject revision, files or packages actually inspected, exclusions, limits, execution status, and normalized findings. A successful process with partial coverage MUST remain partial.

FR-08A normalized evidence finding MUST support rule ID, category, optional CWE/CVE identifiers, original severity, confidence, location, trace, evidence summary, suggested remediation, scanner identity, and raw-result digest. Raw secrets and unnecessary source bodies MUST NOT enter the normalized record.

FR-09Scanner candidates MUST NOT directly determine the workflow verdict. The reviewer MUST assess applicability, actual reachability, mitigating controls, compatibility impact, and evidence strength. Deterministic, directly enforced repository-policy violations may bypass semantic triage only when the policy explicitly defines that behavior.

FR-10External scanner CLIs MUST be capability-detected, version-qualified, invoked without shell interpolation, bounded by time/output/resource policy, and provided only the minimum repository and environment access required. Missing optional scanners are visible; missing required scanners leave their checks unfinished.

Security graph and impact analysis

FR-11The indexer MUST support security facts for untrusted inputs, trust boundaries, authorization gates, sanitizers, command/query/rendering/deserialization sinks, credential use, persistent stores, network egress, and diagnostic emission. Facts MUST carry language/parser version and source citations.

FR-12The graph layer MUST support bounded interprocedural paths derived from per-function summaries. A path MUST retain its source, transformations, sanitizers, calls, sink, unresolved steps, and completeness limitations.

FR-13Initial source/sink coverage MUST include IPC/HTTP/RPC input, file paths, SQL/query construction, subprocess execution, template rendering, deserialization, logs/errors, credential stores, authorization checks, and network requests for supported languages.

FR-14Impact analysis MUST combine changed symbols with incoming callers, dependency closure, public contracts, persistence readers/writers, tests reaching the symbol, and security paths. It MUST distinguish a structurally reachable path from observed runtime behavior and asserted test behavior.

FR-15Dynamic dispatch, reflection, generated code, unsupported syntax, parse failure, stale indexes, and missing edges MUST be reported as limitations. None alone establishes a vulnerability, absence of impact, or full pass.

Policy-as-code and gates

FR-16A repository MAY define versioned review policies with stable rule IDs, scope/path matching, applicability triggers, evidence providers, severity, enforcement mode, remediation guidance, owner, and override policy. The initial enforcement modes are advice, warning, and blocking.

FR-17Built-in policy templates SHOULD cover direct cloud LLM REST access, client-side database access, IPC contract compatibility, credential-bearing diagnostics, public API compatibility, storage migration and rollback, security-boundary negative tests, and new dependency provenance.

FR-18Policy evaluation MUST bind to the exact reviewed revision and policy version. A policy change MUST invalidate affected reusable results. Repository content from the reviewed change MUST NOT be able to weaken the policy used for the same review unless the policy change itself is explicitly part of the reviewed and authorized subject.

FR-19A blocking policy failure MUST participate in the existing code-review/build completion gate. An override requires explicit human authority, a reason, rule ID, subject revision, actor, and timestamp. Overrides do not rewrite the underlying finding.

FR-20Gate evaluation MUST fail closed on malformed or ambiguous required policy configuration and fail visibly on registry/tool-surface inconsistencies. Startup and build qualification MUST verify that every declared mandatory evidence tool is registered and callable.

Verification, tests, and mutation analysis

FR-21The verifier MUST be able to create an isolated checkout or equivalent immutable workspace at the reviewed revision. Network, credentials, writable paths, CPU, memory, output, and elapsed time MUST be explicitly bounded. Ambient user credentials and production services are denied by default.

FR-22A verification receipt MUST record scenario, revision, tool and version, command or structured action, synthetic inputs, environment policy, start/end time, exit status, timeout, redacted output digest, and retained evidence references. Unknown execution outcomes MUST require reconciliation before repetition.

FR-23The reviewer MAY request bounded failure scenarios for authorization bypass, path traversal, injection, secret disclosure, tenant isolation, unsafe retries, duplicate side effects, cancellation/resource leaks, or another selected obligation. Generated scenarios remain evidence requests, not production edits.

FR-24Targeted mutation analysis SHOULD operate on changed behavior and selected risk obligations. Supported mutations SHOULD include condition negation, boundary changes, removed validation/authorization/redaction/cleanup, swallowed errors, reordered state transitions, and duplicated retryable effects.

FR-25Mutation survival blocks only when it demonstrates failure to verify an approved requirement or material selected risk. Otherwise it is advice. Mutation and test results MUST be tied to the reviewed revision and integrated with, rather than replacing, the existing TESTS and code-review records.

Findings and remediation

FR-26A material finding MUST identify its primary category, associated check IDs, violated requirement/invariant/policy, trigger or failure scenario, affected revision and location, evidence references, impact, severity, confidence, corrective expectation, and fixability. One defect associated with several checks is counted once.

FR-27Reports MUST separate demonstrated blocking findings, other findings, unavailable evidence, unfinished checks, scanner diagnostics, optional advice, and successful verified obligations. Unsupported hypotheses cannot be presented as defects.

FR-28Fix proposals MAY include exact artifact edits, bounded code patches, tests, or 2–4 decision options. Code changes MUST return through the tracked build, independent code review, and approval chain; no one-click action may create an off-ledger production patch.

FR-29Re-review MUST verify each claimed correction against the current pinned subject, retain unresolved finding identities, and record whether a finding was fixed, accepted by explicit override, remains open, or became inapplicable for an evidence-backed reason.

Governed learnings

FR-30A reviewer correction or repeated accepted fix MAY create a proposed learning. It MUST NOT become active until a human approves its text, scope, authority, and enforcement level.

FR-31An active learning MUST carry a stable ID, repository/module/path/language scope, provenance, positive and negative examples where available, owner, approval record, confidence, advisory/enforceable mode, creation version, and expiry or revalidation condition.

FR-32Learning retrieval MUST be scope-filtered and evidence-visible. Conflicting, stale, or superseded learnings MUST be surfaced rather than arbitrarily combined. Repository text and model output cannot promote themselves into policy.

FR-33The system MUST measure whether findings based on a learning are accepted, rejected, corrected, or overridden. Repeated rejection MUST propose review or retirement; it MUST NOT silently rewrite the learning.

Review experience, deep scans, and metrics

FR-34Before detailed review, present a revision-bound change-risk summary containing functional changes, public/storage/security boundaries, dependency blast radius, affected high-centrality modules, mapped tests, selected checks, evidence-provider status, and recommended dependency order.

FR-35Summaries and diagrams MUST link to their evidence and MUST NOT substitute for code inspection. The UI MUST distinguish blocking actions, pending external checks, unavailable evidence, and nonblocking advice.

FR-36Repository-wide deep scans MUST be separate revision-bound jobs with explicit scope, provider coverage, progress, cancellation, resume/recovery, and durable reports. Their findings enter remediation through triage and tracked issues rather than mutating an unrelated Story review.

FR-37Metrics MUST include checks selected/completed/unfinished, provider coverage, findings by severity/category, false-positive or rejected-finding rate, time to remediation, recurrence, override rate, escaped defects where recorded, mutation detection, and review duration. Metrics MUST NOT reward suppressing findings or reducing required coverage.

Controller and daemon review paths MUST validate the same required selection floor, evidence contract, finding fields, and verdict rules. IPC method names and payload changes MUST remain aligned in the VS Code and JetBrains clients.

Non-functional requirements

  • Security and privacy. Never persist raw credentials, credential-bearing URIs, unnecessary source bodies, hidden reasoning, or complete prompts in findings or telemetry. Redact before logging and before model context. Synthetic secrets used for verification must be unmistakably non-production.
  • Isolation. Scanner and verifier processes run with least privilege. The host resolves repository paths, symlinks, environment, executable allowlists, network access, and resource bounds outside model control.
  • Reliability. Evidence collection, verification, and publication use stable operation IDs and durable receipts. Restart recovery distinguishes complete, failed, cancelled, unknown, and stale work and never automatically repeats an uncertain side effect.
  • Completeness. Limits are visible and cannot silently discard a material selected check. Partitioning preserves dependency order, scope accounting, and a final consistency pass. Exhausted limits yield incomplete coverage.
  • Performance. Incremental review reuses evidence only when the provider version, subject identity, policy/catalog version, graph generation, and relevant configuration remain valid. Reuse is an optimization, never a capability downgrade.
  • Storage ownership. The daemon remains the sole owner of graph, vector, registry, review, and scan-record access. CLI, MCP, and IDE clients use IPC.
  • Provider discipline. All model work uses LLMProvider. Cloud access uses installed CLI sessions; embeddings remain local. Calls reaching a model or embedding provider are serialized.
  • Model quality. Risk selection that can omit checks, security judgment, final review, remediation judgment, and verification interpretation are critical roles protected by the core tier floor. Narrow formatting and deterministic collection may use peripheral roles.
  • Auditability. A reader can reconstruct why a check applied, what ran, what was inspected, what was unavailable, why a verdict followed, and who approved any exception without rerunning the model.
  • Extensibility. Provider, rule, risk-family, graph-fact, and finding schemas are versioned. Adding a provider does not change historical meanings or require a new top-level review dimension.

Delivery sequence

  1. Context-sensitive baseline. Implement risk-family disposition, stable check selection, NFR propagation, completion accounting, and controller/daemon parity.
  2. Evidence contract. Define normalized providers and records; add registry qualification plus secret, dependency, and one SAST adapter for the primary languages.
  3. Policy gates. Add repository policy, advisory/warning/blocking modes, revision binding, overrides, and mirrored client presentation.
  4. Security graph. Add initial source/sanitizer/sink facts, interprocedural summaries, impact paths, parser coverage, and limitation handling.
  5. Verification. Add isolated scenario execution, receipts, targeted mutation analysis, and TESTS/code-review integration.
  6. Learning and experience. Add human-approved learnings, change-risk summaries, dependency-ordered views, effectiveness metrics, and retirement workflow.
  7. Deep scans. Add resumable repository-wide scanning and triage integration after PR-scoped evidence and verdict semantics are proven.

No phase may weaken the existing review baseline. Each phase must dogfood its own failure modes, including unavailable tools, stale indexes, malformed results, secret redaction, cancellation, restart, record-size bounds, and inconsistent registry declarations.

Open decisions

  • Which scanner CLIs and minimum versions are qualified and optionally installed for each supported language?
  • Does repository policy extend the existing team-policy document or use a distinct review-policy artifact with independent ownership?
  • Which security graph facts are parser-derived deterministically, which come from framework packs, and which may be model-proposed but require verification?
  • What isolation mechanism is portable across supported platforms, and which verification scenarios require containers, OS sandboxes, or process-only restrictions?
  • How are provider databases updated and provenance recorded when the machine is offline?
  • Which result classes block under degraded diff-only review, and which necessarily require fresh graph evidence?
  • What bounded evidence retention is sufficient to reproduce a finding without retaining sensitive source or scanner payloads?
  • Which metrics are visible locally and which, if any, may be exported only through an explicit user-configured integration?
