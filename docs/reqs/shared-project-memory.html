Product and engineering requirements

Shared project memory across coding agents

A durable, compact and correct memory of project conversations, runtime instructions, decisions and work state—available when switching between Claude, Codex, Vibe and Ollama.

Draft for reviewOne store writerRotating durable queueLanceDB-only memory storageLocal-first

Version 0.1 · Consolidated from the project discussion on 1 November 2026 · No implementation or runtime qualification is asserted.

01Purpose and recorded direction

Agent-native sessions and private memory systems do not establish a common project memory. An instruction issued during a Claude conversation must remain available when the next task starts in Codex; a correction made in Vibe must become the current instruction for Ollama as well. Historical context must remain inspectable without repeatedly injecting verbose conversation transcripts.

This document specifies a daemon-owned memory subsystem. Its core is semantic normalization, scoped deduplication, faithful compression and explicit lifecycle management. Static instruction-file generation remains with insrc setup/update; adding another generator is not the objective.

Recorded architecture: sessions submit events to a separate persisted file queue. One context-builder worker normalizes, reconciles, compresses and embeds those events, then writes the memory store. LanceDB is the sole authoritative store for this new subsystem. Sessions and hooks never mutate it directly.

Document precedence: the earlier cross-session memory specification proposed LMDB authority plus LanceDB indexing. This document records the later LanceDB-only direction for the new memory subsystem. Its capture, provenance and forgetting principles remain useful inputs; conflicting storage recommendations are superseded here. Existing code-graph and conversation storage are not migrated by this requirements document.

Reading convention: MUST identifies a required behavior; SHOULD identifies a default that needs a documented reason to vary; MAY identifies optional scope. Examples, logical schemas and API names are proposals, not existing implementation contracts. Recorded user direction is distinguished from an approved LLD or completed build.

S-01Cross-agent continuity. A project-scoped instruction recorded from one supported agent MUST be available to other supported agents through the common service. Provider identity is provenance and MUST NOT partition shared project memory by default.

S-02Local single-user first delivery. The first release MUST support registered projects on the local machine. Personal/global sharing, multiple users and cross-project transfer require separate explicit scope and authorization designs.

S-03Current clients. Applicable UI integration covers VS Code and JetBrains plus standalone CLI/MCP clients. The deprecated insrc-ide fork is excluded. Ollama participates through insrc's provider boundary.

S-04Source-of-truth boundaries. Approved workflow artifacts continue to own scope and sign-off. The code graph owns structural knowledge. Memory MUST link to those sources and MUST NOT approve artifacts, create standing authorization from “go ahead,” or present recalled work status as current execution proof.

Required user journeys

  1. Give Claude a project instruction, then start Codex and receive the same applicable instruction without copying text.
  2. Repeat the instruction with different wording; inspect one canonical record with additional supporting evidence.
  3. Expand or correct it in Vibe; a subsequent Ollama invocation receives the current revision and its conditions.
  4. Switch agents during a story and retrieve a concise handoff with links to original decisions and pending work.
  5. Inspect why a memory was included, correct its scope, or forget it; see the operation's actual processing state.
  6. Restart after acceptance, normalization or store commit and recover without lost submissions or duplicate memory effects.

Initial exclusions: importing all private agent memory automatically; storing hidden reasoning; general personal profiling; automatic cross-user synchronization; automatic skill generation; multimodal extraction; rebuilding workflow or code-graph systems; and replacing native provider authentication or execution loops.

O-01The sole-writer constraint MUST apply to the complete new memory subsystem, not just canonical text. Hook processes, MCP handlers, sessions and maintenance timers MUST submit commands rather than write storage themselves. It does not serialize unrelated existing LanceDB tables used by other insrc subsystems.

O-02Store reads MUST be side-effect-free. Delivery receipts or usage measurements that require persistence MUST be queued as typed control events. They MUST NOT enter the semantic-extraction pipeline recursively.

O-03All inference MUST use insrc's provider abstraction and model-role policy. Cloud access remains through installed CLI providers; embeddings remain local. Model and embedding calls MUST follow insrc's sequential-execution rule, including calls made by memory extraction, reranking and maintenance.

04End-to-end processing flow

  1. Capture an attributed deltaAdmit a new source message, selected outcome or explicit memory operation. Attach project/session identity, event time, source references and execution origin.
  2. Persist the submissionIngress validates the envelope and writes a complete queue frame. Acknowledge acceptance after the required durability boundary.
  3. Resolve bounded contextThe worker reads enough preceding conversation and current scoped memory to interpret references. Missing context becomes an explicit incomplete/conflicted outcome.
  4. Extract and normalizeProduce atomic, typed candidates while preserving polarity, conditions, scope, identifiers and source authority.
  5. Find and reconcile existing memoryCombine exact identity/hash lookup with scoped lexical and semantic candidates. Classify equivalence, expansion, correction, conflict, related evidence or new information.
  6. Compress and validatePrepare the canonical concise text and structured fields. Validate preserved meaning, evidence and complete candidate accounting.
  7. Embed changed content and commitPrepare vectors where content changed. Apply the event's memory effects, revisions, source references, generation change and processing receipt as a qualified atomic table mutation.
  8. Acknowledge and publishPersist queue completion, invalidate affected context caches and expose committed operation status. Eligible sealed queue segments can then be recycled.

Acceptance is not activation. Submission returns an operation receipt in a pending state. An instruction becomes active only after its canonical mutation is committed. Callers may wait for an operation to commit when correctness depends on that update.

05Capture, context and source retention

C-01Capture MUST submit newly admitted material, not the full accumulated transcript on every turn. Every source event MUST have a stable replay identity based on adapter, native session, turn/event or durable transcript cursor. Wall-clock timestamps alone are insufficient.

C-02The envelope MUST distinguish occurredAt, capturedAt and, after processing, processedAt. Preserve timezone or an explicitly known offset where needed. Resolve “today,” “next week” and other relative references against source event time, not delayed worker time.

C-03The worker MUST have a bounded source-context window for references such as “override that” and “same for JetBrains.” Context may be carried as admitted text or resolved from durable references. References required for processing MUST remain available until the event has a terminal outcome.

C-04Context used to interpret an event MUST NOT become an independent new source merely because it is replayed into the normalizer. Assistant echoes, injected briefings, resumed output, permission continuations and hook-generated control messages MUST be distinguished from original user statements.

C-05Capture eligibility MUST use a project-memory policy with positive and negative examples. Initial eligible types are explicit scoped directives, decisions, qualified environment facts, verified lessons and useful handoff facts. Greetings, routine narration and unsupported speculation are not active memory by default.

C-06Original visible messages MUST remain separate from injected memory in transcript storage. Preserve required supporting source spans once, either in durable source records or through pinned existing transcript references. A source-retention policy MUST specify what happens when the original provider transcript is rotated or removed.

C-07Capture MUST account for a detached UI, reconnect, permission retry, interrupted turn and absent daemon. No hook or session may report durable acceptance before the queue is durable. If ingress is unavailable, use a qualified local durable spool or return a visible not-captured result; an in-memory buffer alone is insufficient.

C-08Choose one authoritative capture owner per execution: insrc turn adapter for managed sessions, or the native adapter for independent sessions. Hooks observing an insrc-managed run MUST avoid duplicate submission. Historical import MUST be explicit, scoped, resumable and deduplicated.

A provider-native transcript is evidence, not the memory database. The system must remain understandable when that provider's private memory implementation changes. Hidden reasoning and unrelated private agent files are excluded.

06Separate, durable file queue

A proposed layout is ~/.insrc/memory/queue/ containing numbered active/sealed segments and a recovery manifest. The location and framing are implementation choices to qualify; no queue file is stored inside a Lance table.

PropertyRequired behavior
Physical separationQueue files and the memory store have separate paths, retention and recovery procedures.
Append formatUse a versioned, framed append-only journal with length, sequence and checksum. Plain line breaks alone do not establish a complete durable record.
AcceptanceReturn accepted after the complete frame meets the configured crash-durability boundary. Creation/rename durability includes directory synchronization where required by the filesystem.
RotationSeal the active segment at the configured byte threshold and open a new segment. Define maximum event/frame size and bounded decoding limits.
RecyclingDelete a sealed segment only when every event has a durable terminal disposition, including explicitly quarantined/resolved failures or a durably verified transfer.
BackpressureWhen unprocessed data exhausts the queue budget, reject/defer new submissions visibly. Never drop old pending events to stay below a size cap.
RetriesPersist attempt state and next retry time. Transient failures are retryable; poison events require inspection/quarantine rather than silent success.
OrderingAssign a durable ingress sequence. Preserve causal ordering of directives, corrections and deletion commands. Any later scheduling optimization must retain explicit dependency/order guarantees.

Q-01Ingress MUST serialize writes from multiple producers. A read-only queue status request must not open a competing append writer or memory-store writer.

Q-02Startup MUST recover complete accepted frames. An incomplete final frame may be isolated using the qualified recovery procedure. Mid-segment corruption MUST be reported and quarantined; recovery must not skip unknown accepted content silently.

Q-03Processing is at least once. Exactly-once store effects MUST be implemented through stable event identity and durable processing receipts, not claimed from the file queue itself. A reused event ID with a different payload hash MUST be rejected or quarantined.

Q-04Queue acknowledgement MUST follow the store commit. If the process crashes between those operations, replay checks the store receipt and repairs acknowledgement without repeating the memory mutation.

Q-05Journal rotation, acknowledgement checkpointing and manifest replacement MUST have documented crash points and recovery behavior. Retain the prior valid checkpoint until its replacement is durable.

Q-06Queued payloads remain input evidence and cannot be used as active memory merely because normalization is pending. Status must distinguish queue acceptance, processing and canonical activation.

No segment-size, disk-capacity or retry-count value is approved by this document. These are configurable operational settings to select using payload measurements and recovery tests. Failed-event handling must avoid indefinitely blocking all unrelated project work while preserving same-subject ordering.

08Semantic normalization and deduplication

Deduplication is a meaning-preservation operation. Relatedness alone is insufficient. The worker must preserve conditions, polarity, source authority and the difference between a current directive and a historical event.

Equivalent instructions

“Run the full sweep after all tasks are built.”
“Finish every implementation task before the complete test sweep.”

One canonical directive; two evidence references if independently stated.

Different meanings

“SQL Server is unavailable here.”
“Defer SQL Server validation.”
“Do not support SQL Server.”

Environment fact, scoped instruction and product decision. Do not merge.

N-01Normalize into atomic assertions with explicit subject, action/value, scope, polarity and conditions. Preserve dependencies between split assertions. A compound instruction may yield several linked records, but splitting must not discard their ordering or exception relationships.

N-02Use stable identity dimensions such as subject, rule category and scope to locate competing assertions. Assertion values and conditions are compared separately so an override can find its predecessor. A fingerprint for exact equivalence MUST include meaning-bearing qualifiers.

N-03Exact identity/hash lookup MUST cover the relevant store scope independently of nearest-neighbor limits. Scoped semantic and lexical candidates extend recall; similarity scores nominate candidates and never authorize a merge by themselves.

N-04Canonicalization MUST preserve case-sensitive paths, identifiers, quoted strings, units, negation and limits. Whitespace or Unicode normalization must not change technical meaning. A changed condition is not an exact duplicate.

RelationshipRequired outcome

Explicit correctionCommit a replacement revision and supersession transition together. Do not leave contradictory active versions.

N-05Output MUST validate against a bounded typed schema. An empty valid extraction, failed parsing, incomplete extraction and partial persistence are distinct outcomes. Every candidate must be accounted for before an event is acknowledged as processed.

N-06The worker MUST produce an inspectable reconciliation reason. Confidence cannot upgrade source authority. An inferred assistant preference cannot override an explicit user instruction or an approved artifact.

N-07Support pre-normalized structured submissions from qualified sources, such as explicit corrections or canonical workflow references. They may skip LLM extraction, but MUST still pass scope, replay, schema and reconciliation checks.

Periodic scoped duplicate audits MAY identify paraphrases missed by initial candidate retrieval. They must use the same evidence and mutation rules; perfect global semantic deduplication is not asserted from an ANN top-k search.

09Compression, growth and context budgets

There are three separate representations: source evidence, canonical memory and compiled context. Their sizes and retention policies must be measured independently. An expanding audit history does not justify an expanding prompt.

B-01Apply structural compression first: remove duplicate assertions, select current state, reference canonical artifacts and retain only applicable records in the briefing. Do not repeatedly summarize an already shortened summary as the sole source of truth.

B-02Semantic compression MUST preserve assertion, negation, scope, conditions, exceptions and time applicability. Check structured-slot coverage and source support. Ambiguous compression stays unresolved rather than becoming a broader active rule.

B-03Twenty paraphrases of one instruction SHOULD leave its canonical record count and normal briefing footprint unchanged. Additional evidence is linked and deduplicated outside the briefing. Evidence lists and source excerpts require their own retention limits.

B-04Set separate configurable budgets for queue frames, source-context windows, extraction input/output, candidate pools, stored canonical text and final provider context. Count supplied memory, history, schemas, tools and framing within the actual invocation budget.

B-05Mandatory applicable directives MUST NOT disappear solely because they rank poorly semantically or a briefing budget is exhausted. Expose an overflow/narrowing outcome and use an explicit handling policy; do not silently truncate obligations.

B-06Bound the compiled context by selecting relevant current memories and a small handoff. Detailed evidence, reconciliation diagnostics, duplicate references and historical revisions stay outside the normal prompt and remain available through inspection/search.

B-07Measure source-to-canonical and canonical-to-delivered compression separately, together with qualifier preservation and omission rates. No target compression ratio or latency figure is established without representative evaluation data.

Accuracy governs compression. Reducing tokens is useful only while preserving correctness. Low access frequency does not make a still-active directive false or obsolete. Automatic decay must not silently revoke project instructions.

10LanceDB as the sole memory store

Canonical text and its vector are stored together. A semantic query returns the authoritative row, avoiding a second store lookup. Direct instructions and handoffs use scalar lookup or cached snapshots, rather than vector search on every turn.

Physical store separation is required. Memory uses its own LanceDB connection and database directory, not another table in the existing index database. This separates stored tables, indexes and lifecycle operations; both stores may still share daemon CPU, memory and disk resources.

~/.insrc/
  lance/                 existing index database
  memory/
    lance/               proposed dedicated memory database
    queue/               separate rotating ingestion journal

The existing index path is shown for context. The new memory paths are proposed locations, not an implemented configuration. Their resolved directories must be distinct from the index database, and neither database cleanup path may encompass the other or the queue.

L-01The new subsystem MUST use a dedicated daemon-owned LanceDB database directory and separately managed connection/table handles. It MUST NOT place memory tables in the existing index store or reuse its connection singleton. No LMDB shadow authority or separate SQLite history database is required by this design. Existing insrc storage outside the subsystem remains unchanged.

L-02Qualify an atomic commit representation for an event's complete effects. A proposed single typed table holds current-memory, revision, source, receipt, tombstone, delivery and control rows, using stable row IDs and nullable vector fields where appropriate. A context query filters to active current-memory rows.

L-03A qualified single-table batch mutation MUST commit memory transitions and the processing receipt together. Lance table operations are not assumed to provide a general multi-table transaction. If implementation splits the commit unit, it requires a documented, tested recovery protocol before acceptance.

L-04Single-writer ownership does not create uniqueness constraints automatically. The worker MUST validate IDs, expected revisions and duplicate batch keys. Canonical text/vector updates, logical deletion and generation publication must not expose an intermediate inconsistent state.

L-05Persist embedding model identity, dimension and normalization version. Embed changed canonical content; do not recompute embeddings merely because another evidence reference was attached. Model/dimension migration must have an explicit compatibility and rebuild plan.

L-06Readers MUST observe the qualified current committed table state. Verify table-handle consistency across updates, deletes and maintenance. Avoid long-lived stale checkouts in session context reads.

L-07Small-update performance, scalar indexes, FTS/vector visibility, nullable-vector behavior, compaction and old-version cleanup MUST be verified against the installed LanceDB version before choosing the physical schema. Batch writes through the sole worker where useful without violating operation latency or ordering requirements.

L-08Store configuration, ownership checks, migrations, maintenance, reset, backup and cleanup MUST distinguish the memory database from the index database. Index rebuild/reset must preserve memory; memory cleanup/reset must preserve index data and pending queue events. Validate resolved paths and cleanup boundaries to prevent accidental cross-store deletion. Memory-store ownership and its sole-writer guard apply to the new connection as well.

11Updates, overrides, expiry and forgetting

U-01Explicit corrections MUST name the target or resolve it unambiguously and include an expected revision when supplied by an inspector/API client. A stale correction returns a conflict; it must not silently overwrite newer context.

U-02Expansion preserves additional conditions and evidence. Supersession creates a replacement revision and deactivates the prior meaning atomically. Distinct conditional assertions may coexist; unrelated records are not merged merely to reduce count.

U-03Validity supports explicit time intervals and named conditions. Establishing that a condition ended requires trusted evidence or explicit user action. Merely mentioning “the service is fixed” in quoted or hypothetical text is insufficient.

U-04Expired, conflicted, superseded and deleted records MUST be excluded from ordinary context reads. Inspection may request historical states explicitly and must label them clearly.

U-05All forget operations are queued commands. Acceptance remains pending until the writer commits. After commit, subsequent context acquisition and dispatch validation MUST exclude the target and affected derived records, and invalidate relevant prepared/cached bundles.

U-06Forget targets MUST distinguish one assertion, a source conversation with its derived memories, a session or all project memory. Supporting evidence and derived handoffs must be included in the deletion plan, not left as an accidental route to re-extraction.

U-07Replay, pending extraction and index rebuilding MUST honor tombstones and source invalidation. An event queued before deletion must not recreate the deleted assertion after a restart. Retain minimal replay-prevention metadata without retaining forgotten content.

U-08Differentiate logical exclusion from physical purge. Lance table versions, historical revisions, source excerpts, caches, queue payloads, logs and backups need explicit cleanup/retention policies. Report physical cleanup as pending until its guarantee is met.

U-09Memory already delivered into a provider-native session cannot be retroactively erased by a local store deletion. Provide a clear correction notice where supported and a fresh-session path; provider-side history removal is a separate capability.

U-10Processing receipts and tombstones may be compacted only after a proven replay boundary—for example, acknowledged producer cursors plus rejection of older submissions. Queue segment deletion alone does not prove an external producer will never retry an old event.

R-01Retrieval MUST filter by trusted project and applicability before exposing content. Agent/provider identity is optional provenance filtering, not the default partition for shared memory. Caller SQL or unvalidated metadata filters MUST NOT bypass scope.

R-02Historical retrieval SHOULD combine vector similarity with keyword/exact matches for paths, symbols, issue IDs, configuration names and quoted terms. Lexical candidates must not be discarded solely because they were absent from the ANN top-k pool. Configure candidate limits, relevance thresholds and final context budgets separately.

R-03A read MUST distinguish ready, empty, partial, unavailable and relevant stale/overflow conditions. A failed read is not an empty project history. Reranking failure may use an explicitly reported fallback if underlying results remain valid.

R-04Return the current canonical memory with its revision, scope, source references and generation. Explanations can include match type and scoring components, but normal briefings exclude verbose diagnostics and raw evidence lists.

R-05Cache compact project snapshots and query-specific bundles. Keys MUST include memory generation, applicability, query/task context and relevant model/schema versions. A correction, deletion or expiry invalidates affected entries; time-based expiry cannot rely only on a write-driven generation change.

R-06Before dispatch, validate that a prepared bundle remains eligible. A cached generation alone is insufficient if scope, time or execution privacy changed. Resumed sessions receive concise revision deltas; rehydrate current context after compaction through supported integration mechanisms.

R-07Do not claim synchronous visibility of a queued correction. A caller needing the new state may request context after an operation receipt, waiting within a bounded deadline or receiving a pending/degraded result.

R-08Measure cache hits, scalar reads, vector/lexical search, assembly time and provider delivery separately. Optional rerankers must use existing provider policy and serial calls. Benchmarks must report cold/warm state and actual memory corpus size.

A-01All mutation APIs MUST enqueue. Operation IDs must survive restart. Reads/status may be served by the daemon without opening a new writer. Maintain compatible payload semantics for VS Code, JetBrains and MCP clients.

A-02Context and operation results MUST expose structured state plus fixed safe error codes. Include source/normalizer versions for diagnostics without dumping private prompts or unrestricted payloads into logs.

A-03Human-facing controls SHOULD support inspect, correct, resolve conflict, forget, disable capture and view pending work. Capture opt-out stops new ingestion; it does not silently delete existing memories.

15Failure and crash-recovery contract

Crash / failure pointRequired recovery
Before complete durable queue appendNo accepted acknowledgement. Caller retries using the same source/event identity.
After append, before worker startsRecover pending entry and process it after restart.
During model normalization or embeddingLeave event unacknowledged; persist retry disposition. No partially active canonical result.
Valid extraction contains no eligible memoryCommit an explicit no-memory processing receipt, then acknowledge. Do not confuse this with a parser/model failure.
One candidate in a batch failsDo not silently acknowledge the parent event as completely applied. Retry the atomic unit or use a qualified per-candidate accounting/recovery protocol.
During atomic store mutationRecover either the prior committed state or the complete new event effect. Reject a design that exposes partial receipt/memory state without recovery evidence.
After store commit, before queue acknowledgementRead the committed processing receipt, skip duplicate inference/mutation and repair the queue acknowledgement.
After commit, before cache publicationReaders/dispatch validation detect the committed generation; restart discards volatile caches. No stale bundle may bypass revision/expiry checks.
During segment rotation/checkpoint replacementRecover from complete frames and the last durable manifest/checkpoint without losing accepted entries.
After deletion, before an old event is replayedApply receipt/tombstone/source-invalidation checks; old evidence cannot revive the forgotten assertion.
Retrieval/index unavailableReturn unavailable/partial state. Apply the documented degraded-memory policy; do not substitute unchecked stale memory or report a valid empty result.
Worker model call fails repeatedlyShow retry or quarantine state and retain recoverable input. An operator can inspect/retry/resolve it without silently dropping ordered dependent work.

F-01Recovery MUST be driven by durable identity and receipts. A “processing” marker, queue cursor or in-memory lease alone cannot prove a memory mutation committed.

F-02Define retry ownership and deadlines across the memory worker and CLI-provider retry layers. Avoid uncontrolled retry multiplication, and preserve cancellation and model-role admission on every attempt.

F-03Backup restore and index rebuild MUST preserve deletion and replay boundaries. Retained queue backups cannot override newer tombstones. Physical backup deletion limitations must be documented.

16Privacy, authority and execution policy

P-01Use trusted repository/session binding from the daemon. Per-project filters are local scoping, not a claim of future multi-tenant authorization. Unregistered or ambiguous roots require an explicit refusal/selection path.

P-02Exclude credentials, private capabilities, unrelated files, hidden reasoning and unrestricted tool dumps. Attachments and multimodal content are not automatically admitted. Extraction input is already sensitive persisted data; privacy controls must run before durable enqueue.

P-03Respect insrc's existing temporary/session-memory execution restrictions. Data that is prohibited from durable persistence MUST NOT enter the durable memory queue, source records or cloud memory processing. A later redaction pass is too late to establish that boundary.

P-04Memory is subordinate context, not a new authority channel. Quoted text, fetched documents and tool output MUST NOT become active user instructions automatically. A recalled approval cannot authorize a new unrelated action.

P-05Mark briefing text as prior project context with provenance and current applicability. Hook transports that inject developer/system-level text must not silently promote lower-authority memories. Keep authoritative host instructions separate from recalled evidence.

P-06Logging and diagnostics MUST use bounded identifiers, states and hashes by default. Raw queue payloads, source text and compiled memory context require explicit inspection rather than routine telemetry.

The system must explain both “what is remembered?” and “why did this agent receive it?” A memory inspector should show pending events, current records, source lineage, revisions, conflicts and the latest delivery status.

M-01Publish measured latency and quality separately. A faster pipeline with dropped instructions or false merges is not an acceptable optimization. Cost reduction is subordinate to accuracy.

M-02Maintenance actions must be inspectable and cancellable where appropriate. Source/record/prompt schema changes need explicit migration or reprocessing policy with versioned lineage.
