### `reconcileConfig`

```typescript
export function reconcileConfig(existing: unknown, catalog?: readonly ConfigOption[]): ConfigReconcileResult
```

**Parameters:**
- `existing: unknown` — The whole parsed ~/.insrc/config.json document, read once by the caller. Typed `unknown` rather than a config interface because the on-disk document may predate any current shape — that is the case the Story exists to handle. Also accepts undefined/null (no file yet, i.e. the daemon first-boot path in src/daemon/index.ts).
- `catalog: readonly ConfigOption[]` _(optional)_ — Authoritative key→type→default list; defaults to CONFIG_CATALOG. Injectable so the reconciler's tests drive it from fixtures rather than the live catalog (extends the existing fixture pattern in src/config/__tests__/repo-shaper-override.test.ts:27-32).

**Returns:** `ConfigReconcileResult` — The normalized document plus the derived `changed` flag and per-key provenance lists. `changed` falls out of the same comparison that built the document — it is never recomputed by the caller, which is what makes "write back only when it changed" a property of the contract rather than of caller discipline.

**Errors:**
- `Error` when A catalog entry declares a `type` outside the discriminant domain of ConfigOption. This is a programmer error in the catalog, not a user-config condition, and must throw rather than be silently degraded to "type mismatch → fill default", which would overwrite a legitimate user value.

**Preconditions:**
- Net-new code. capability.reuse-check graded 0 of 5 candidates clear-match; no reconcile/normalize/default-fill entrypoint exists anywhere in the explored surface. src/config (partial-match, conceptScore 0.193) and src/cli/config-catalog.ts (partial-match, 0.159) are the two halves this bridges, not things it extends.
- PURE: no fs, no IPC, no daemon socket, no clock. This is load-bearing — the daemon-boot call site runs before the socket exists, so the reconcile cannot be an IPC round-trip.
- The caller has already read the WHOLE document. The reconciler must NOT be reached through `writeConfig(path, value)` (src/cli/services/config.ts:18-20): that seam is a per-key, single-path IPC forwarder, so N fixed keys = N round-trips and "write once only if changed" becomes unexpressible. symbol.locate found NO hit for `getByPath` / `setByPath` / `readConfig`, so the Story's premise of reusing existing dot-path get/set helpers is NOT evidenced — the dot-path get/set the catalog's `path` field implies must be located (read the config.write handler) or written inside this module.
- ConfigOption's field set {path,type,default,desc} is the Story's own description, not graph-evidenced. The interface is anchored at src/cli/config-catalog.ts:23-28 (entityId 3ef0c85af2cd4247530de06874accb58) and MUST be read before the type-match predicate is written — that predicate is the whole accept-existing-vs-fill-default decision. Likewise CONFIG_CATALOG itself returned NO symbol.locate hit (coverage-gap 1): its existence, shape and entry count are unverified.

**Postconditions:**
- `existing` is never mutated; `result.config` is a fresh document built by merging catalog outcomes over a deep clone of `existing`. It is a MERGE, never a rebuild from catalog entries — a catalog-driven rebuild is the single failure mode that silently drops the dynamic namespaces.
- For every catalog key present in `existing` whose value satisfies the type predicate: the value is carried over unchanged (referentially preserved for objects/arrays) and its path appears in `carried`.
- For every catalog key missing from `existing`: the catalog `default` is written and the path appears in `filled`. For every catalog key present but type-invalid: the catalog `default` replaces it and the path appears in `repaired`.
- Every key NOT enumerable by the catalog survives verbatim, including the dynamic subtrees models.analyze.roleTiers.<roleId>, models.analyze.byRepo.<path>.*, and models.agents. This holds WITHOUT the reconciler knowing those namespaces exist, which is required: no exploration touched their on-disk shape (coverage-gap 4), so any design that must declare them would be resting on un-evidenced ground.
- `changed === (filled.length + repaired.length > 0)`, and `changed === false` implies `result.config` deep-equals `existing`. Callers MUST NOT write when `changed` is false.
- Idempotent: `reconcileConfig(reconcileConfig(x).config).changed === false` for all x.
- Non-object / unparseable `existing` (null, undefined, array, scalar) is treated as `{}` — every catalog key lands in `filled`, nothing is thrown, and the first-boot path reduces to the existing write-defaults behaviour.

## Data model changes

### `ConfigReconcileResult` — new

The reconciler's return shape and the Story's only new type. `{ config: Record<string, unknown>; changed: boolean; carried: string[]; filled: string[]; repaired: string[] }` — config is the normalized document; carried = catalog dot-paths whose existing value type-matched and was kept; filled = catalog dot-paths absent from the existing document; repaired = catalog dot-paths present but type-invalid, replaced by the catalog default. INVARIANT: `changed === (filled.length + repaired.length > 0)`. `changed` is derived from the same comparison that produced `config`, so a no-op cannot write — the caller has no independent way to compute it wrong. ## Error paths

### Error cases

- **~/.insrc/config.json exists but cannot be read (EACCES, EISDIR, EIO — anything other than ENOENT).** (recoverable)
  - Detection: The I/O side awaits `fs.readFile` inside a try/catch and branches on `err.code`: `ENOENT` is NOT an error (it is the first-boot path and degrades to `reconcileConfig(undefined)`); every other errno code falls through to the failure branch. The pure `reconcileConfig` never sees this — it has no fs.
  - Response: On the maintenance.update path: git-pull + build have already succeeded, so the update is NOT failed. The error is captured into `MaintenanceResult.configReconcile.error` (the `error`-present/`changed:false` shape) and one `onLog` line names the file and the errno. Nothing is written. On the daemon-boot path: log at warn, boot continues on in-memory catalog defaults, and the next boot retries.
  - User impact: The update reports success with an explicit "config not reconciled: <errno>" line rather than a silent no-op; the user's existing config is untouched. If the permission problem persists, every subsequent boot repeats the warning, so the condition is visible rather than latent.
- **The config file is readable but its contents are not valid JSON (truncated by a previous crashed write, hand-edited with a trailing comma, or zero bytes).** (terminal)
  - Detection: `JSON.parse` throws `SyntaxError` inside the same try/catch that wraps the read, at the I/O boundary before `reconcileConfig` is called.
  - Response: Do NOT pass the raw text through and do NOT fall back to `reconcileConfig(undefined)` — that would treat a corrupt-but-recoverable document as absent and fill every catalog default over it, destroying the dynamic namespaces the Story exists to preserve. Instead: abort the reconcile, write nothing, record `configReconcile.error` with the parse message and byte offset, and emit an `onLog` line telling the user the file must be fixed or removed by hand.
  - User impact: The user is told exactly which file failed to parse and where, and that their config was left alone. The alternative (silent default-fill) would look like a successful update while having discarded models.analyze.roleTiers / byRepo / models.agents.
- **A CONFIG_CATALOG entry declares a `type` value outside the ConfigOption discriminant domain (a catalog row added later with a typo'd or newly-introduced type name).** (terminal)
  - Detection: The reconciler's type-match predicate is an exhaustive `switch` over the discriminant; the unknown value reaches the `default:` arm, which is written as a throw rather than a fall-through. TypeScript makes a statically-known new discriminant a compile error at that same switch (postcondition on ConfigOption); the throw catches the case where the catalog is data the compiler cannot narrow.
  - Response: Throw `Error` naming the offending catalog path and the unrecognized type — this is the one error `reconcileConfig` itself raises, per the s4 contract. It must NOT degrade to "unknown type → type mismatch → fill default", which would overwrite a legitimate user value on the strength of a catalog typo.
  - User impact: A developer-facing crash during update or boot, with the bad catalog row named. This is a programmer error in our own shipped catalog, never something a user's config can trigger — no user config content can reach this branch.
- **A catalog dot-path's ancestor segment collides with a non-object value in the existing document (catalog declares `models.analyze.timeout`, but the on-disk `models.analyze` is a string or a number).** (recoverable)
  - Detection: The merge walk descends the dot-path segment by segment over the deep clone; before descending it checks the current node with a plain-object predicate (`typeof === 'object' && !== null && !Array.isArray`). A non-object at an intermediate segment is the collision — it is found structurally during the walk, not by pre-validating the document.
  - Response: Treat the whole subtree at the colliding segment as type-invalid: replace the scalar/array with an object, fill the catalog default beneath it, and record the CATALOG path in `repaired` (not the ancestor). Every sibling key that was under a *valid* ancestor is unaffected. The replaced scalar is named in the `onLog` line so the loss is stated, not hidden.
  - User impact: One malformed branch of the config is repaired and the user sees which value was discarded; the rest of the document, including the dynamic namespaces, survives untouched.
- **The write-back fails after `changed === true` (disk full, EACCES, read-only home, ENOSPC mid-write).** (recoverable)
  - Detection: The single `fs.writeFile` (write-temp-then-rename) rejects; the I/O wrapper awaits it inside try/catch. Because the write is the only one performed per reconcile, there is exactly one place to detect it.
  - Response: Capture into `MaintenanceResult.configReconcile.error` with the filled/repaired counts that were computed but not persisted, and emit the failure through `onLog`. The temp file is unlinked on failure so no partial document can be renamed into place. Do not retry in-process — daemon boot reconciles again on next start and the operation is idempotent, so a later successful run produces the identical document.
  - User impact: The update is still reported successful (git-pull + build did succeed) with an explicit line saying the config could not be written; the on-disk config remains exactly as it was — never half-written, because rename is atomic.
- **The config file is modified by another process (the TUI's config.write IPC path, a second daemon, a hand edit) between this reconcile's read and its write.** (recoverable)
  - Detection: `fs.stat` at read time records `mtimeMs` + `size`; the I/O wrapper re-stats immediately before the rename and compares. A difference means the snapshot `reconcileConfig` operated on is stale.
  - Response: Abandon the write (do not clobber the newer document), record it as a non-fatal `configReconcile.error` ("config changed during reconcile"), and log it. Because the reconcile is pure and idempotent, the correct response is to let the next trigger — daemon boot, or the next update — re-run it against the newer document rather than re-looping here.
  - User impact: A concurrent edit made from the TUI while an update is running is never silently reverted. The reconcile is deferred, not lost.
- **STALE-CATALOG HAZARD (s4 precondition on `update`): the reconcile inside maintenance.update runs against the CONFIG_CATALOG the CLI process imported at startup — i.e. the PRE-update schema — making it a no-op for exactly the shape change the Story targets.** (recoverable)
  - Detection: Not detectable by the reconciler itself: a reconcile against the old catalog returns a perfectly well-formed `changed: false`, which is indistinguishable from "already normalized". It is only detectable at the call site, by whether the post-build reconcile loads the catalog from the freshly built output rather than from the module graph already resident in memory. If the design resolves this via a dynamic `import()` of the newly built catalog module, THAT import rejecting (build output missing, path moved) is the detectable signal.
  - Response: This must be settled before implementation and is not resolvable from the s1 passes. Two acceptable resolutions: (a) `await import()` the freshly built catalog module after the build step and pass it as the `catalog` argument — the injectable second parameter exists for exactly this; on import rejection, fall back to (b). (b) Leave the authoritative reconcile to daemon boot after restart, with the update path reporting only. Either way the update path must NOT silently reconcile against the stale in-memory catalog and report a confident no-change.
  - User impact: If unresolved, the user gets an update that logs "config already up to date" while their config is missing every key the update introduced — the exact breakage the Story was written to prevent, now wearing a success message. Under resolution (b) the daemon reconciles on the next start, so the user sees a deferred, not absent, migration.
- **Daemon boot's reconcile throws for any reason (catalog error, unreadable config, write failure) while the daemon is starting up.** (recoverable)
  - Detection: The boot call site wraps the whole read/reconcile/write-if-changed sequence in a single try/catch. NOTE: the insertion point in src/daemon/index.ts is UNVERIFIED — no s1 exploration covered that file (coverage-gap 3) — so whether boot currently short-circuits on an existing config file must be read before this handler is placed.
  - Response: Never abort boot on a reconcile failure. Log at warn with the reason, continue startup with the catalog defaults applied in memory only, and leave the on-disk file untouched. The daemon owning all DB access means a daemon that refuses to start takes the CLI, MCP, and the IDE workbench down with it — a config normalization failure must not have that blast radius.
  - User impact: The daemon starts and the system stays usable; the user sees one warning line and the config is reconciled on a later boot or update once the underlying cause is fixed.
- **A catalog row's own `default` value does not satisfy the row's declared `type` (a `boolean` row shipping `"false"`).** (terminal)
  - Detection: After the merge, the filled/repaired values are re-run through the SAME type-match predicate used for existing values. A default failing its own predicate is a self-inconsistent catalog row. Detected by the predicate, not by an ad-hoc second validator, so the two can never disagree.
  - Response: Throw with the catalog path named, in the same class as the unknown-discriminant error — a shipped catalog that cannot satisfy its own schema would otherwise make the reconcile non-idempotent (each run would see the freshly-written default as type-invalid and "repair" it again, so `changed` would be true forever and the file would be rewritten on every boot).
  - User impact: Caught in our own test suite, not by users — the reconciler's tests drive the catalog from fixtures via the injectable `catalog` parameter and can assert this holds for the real CONFIG_CATALOG.

**Backward compat:** Four existing surfaces are touched, each kept compatible by construction. Neither symbol changes shape: no ConfigOption field is added, removed or retyped, and no catalog entry value changes. (2) MaintenanceResult: the configReconcile field is additive and optional, so existing readers of the result — including any IDE-side consumer — are untouched and no current field changes meaning. The git-pull + build behaviour of maintenance.update is otherwise unchanged, and a reconcile failure does not turn a successful update into a failed one. (3) The daemon boot contract: an absent config file still produces exactly today's written defaults; only the previously-unhandled existing-file case gains behaviour. (4) The on-disk ~/.insrc/config.json is forward- and backward-tolerable across the change. A normalized document differs from its predecessor only by keys the new catalog declares, carrying values an older build would have resolved to its own defaults anyway, and every key an older build wrote — catalog-known or dynamic — survives verbatim. A user who reverts to a pre-change build after normalization therefore reads a config it understands; no data rollback accompanies a code rollback. The reconcile is deliberately NOT routed through writeConfig(path, value) at src/cli/services/config.ts:18-20: that per-key IPC forwarder would make N fixed keys N round-trips and would make "write once only if changed" unexpressible, and it is unusable from daemon boot, which runs before the socket exists. ## Alternatives considered

### a1: Pure reconcile function over the whole document (catalog relocated to src/config) — **CHOSEN**

CONFIG_CATALOG moves to src/config; a pure `reconcileConfig(doc, catalog) -> { config, report }` does all schema work in memory, and each caller owns its own read/write-if-changed.

Relocate the key→type→default catalog from src/cli/config-catalog.ts to a daemon-safe shared module under src/config (src/cli re-exports it so existing CLI imports keep compiling), and add a sibling pure module exposing one function: `reconcileConfig(current: unknown, catalog: readonly ConfigOption[]): ReconcileResult`. `ReconcileResult` is `{ config: ConfigDocument; changed: boolean; report: { filled: string[]; retyped: string[]; carriedOver: number; preservedUnknown: string[] } }`. The function is a MERGE over a structural clone of the existing document — never a rebuild from catalog entries — so any key the catalog cannot enumerate (models.analyze.roleTiers.<roleId>, models.analyze.byRepo.<path>.*, models.agents) survives untouched by construction rather than by an explicit allow-list. It performs no I/O and touches no IPC: dot-path get/set are internal helpers, `changed` is computed inside, and the two wiring targets (maintenance.update, daemon boot) each do read-whole → reconcile → write-once-only-if `changed`. maintenance.update reports through its existing `onLog: LogFn` channel and folds the report into `MaintenanceResult`; boot reuses the same call in place of its current write-if-absent.

### a3: Reconcile as a method on the existing ConfigStore (file owner keeps the read-modify-write)

Add `reconcile(catalog): Promise<ReconcileReport>` to the existing ConfigStore in src/config/store.ts, so the component that already owns the config file also owns the atomic read → normalize → conditional write.

Rather than exposing a free function and leaving I/O to callers, extend the existing on-disk owner. ConfigStore (src/config/store.ts, the highest-ranked near-miss in s1's concept.resolve) gains one method: `reconcile(catalog: readonly ConfigOption[]): Promise<ReconcileReport>`, where `ReconcileReport = { changed: boolean; filled: string[]; retyped: string[]; preservedUnknown: string[] }`. The pure merge logic still lives in its own module so it stays unit-testable, but the public contract callers see is the store method — one call, one atomic read-modify-write, no way to reconcile without going through the file's owner. The catalog still relocates to src/config (the store must import it without reaching into src/cli). maintenance.update and daemon boot both become a single `await store.reconcile(CONFIG_CATALOG)` plus report rendering.

**Rejected because:** Meets the same three properties as a1 and is strictly better on the one axis a1 loses: the file's owner performs the read-modify-write, so idempotence and atomicity live in one place and cannot drift between the CLI update path and daemon boot, and a future third caller is correct by construction. It also has the smallest public surface — one method plus one report type. It ranks second only because it rests on an unconfirmed premise: ConfigStore's read/write primitives are a near-miss inference from s1's concept.resolve, not verified, so the method may not fit the store's current shape. It also couples the persistence component to the schema catalog, mixing 'how the file is persisted' with 'what it should contain', and pushes the shipped contract behind I/O so only the inner merge module keeps the fast pure-fixture test path. If reading src/config/store.ts confirms the store already owns a whole-document read and write, this becomes the better choice and the delta from a1 is small — a1's pure function moves inside the method unchanged.

### a4: Daemon-owned `config.reconcile` IPC operation

Expose reconciliation as a new daemon IPC method returning a report, keeping every config write inside the daemon and making the CLI update path a thin caller.

Treat reconciliation as a daemon capability rather than a shared library. Add a `config.reconcile` JSON-RPC method whose result is `{ changed: boolean; filled: string[]; retyped: string[]; preservedUnknown: string[] }`. The handler does the read-whole / merge / write-once-if-changed in-process; the catalog relocates to src/config so the daemon can import it without depending on src/cli. Daemon boot invokes the handler function directly (no socket hop); maintenance.update calls the IPC and renders the returned report through its existing `onLog` channel into `MaintenanceResult`. This keeps the repo's stated rule that the daemon owns persistent state and that CLI/MCP reach it only over IPC, and gives the reconcile outcome a stable wire shape any client (CLI, MCP, IDE) can consume.

**Rejected because:** Correct on ownership philosophy — the daemon owning on-disk state and clients reaching it over IPC matches the repo's architectural rule, and a versioned wire report would serve the IDE as well as the CLI. It fails on sequencing, which is decisive here. maintenance.update git-pulls and rebuilds, so the daemon is plausibly stopped, mid-restart, or running pre-update code at precisely the moment the CLI needs to reconcile — the least reliable moment for the socket. Worse, boot reconciliation cannot wait on the socket at all, so the handler must be directly callable in-process regardless; the IPC layer is therefore additive surface over a function that has to exist either way, and a1/a3 ship that function without the extra contract. It also converts internal behaviour into a wire shape with mirrored types, raising the cost of later report-shape changes, and forces an IPC harness to test the shipped contract instead of plain fixtures. Ranked above a2 because its risks are cost and operational ordering, not the possibility of corrupting user config.

### a2: Catalog extended to declare dynamic namespaces (schema covers both enumerable and open-ended keys)

Widen the catalog data model with a `ConfigNamespace { prefix, valueType }` declaration alongside `ConfigOption`, so dynamic subtrees are schema-described and validated rather than merely preserved.

Keep a1's pure-function seam but change the authoritative data model. The schema becomes a pair: `ConfigOption { path, type, default, desc }` for enumerable keys plus `ConfigNamespace { prefix, keyKind, valueType, desc }` for open-ended ones — `models.analyze.roleTiers.*`, `models.analyze.byRepo.*`, `models.agents.*` become declared entries rather than an unenumerable residue. `reconcileConfig` then classifies every leaf into exactly three buckets: catalog-known (carry over if type-matches, else fill default), namespace-known (carry over if the value matches the namespace's declared valueType, else record as invalid), and genuinely-unrecognized (preserve verbatim, report). The report gains a `namespaceEntries` count and an `invalidNamespaceValues` list. The schema thereby describes the entire config surface, and "unknown" narrows to only truly foreign keys.

**Rejected because:** The most ambitious and the worst fit for this Story's bar. It depends on knowing the on-disk shape of models.analyze.roleTiers.*, models.analyze.byRepo.*, and models.agents — the one surface s1 identifies as entirely un-evidenced — so the design cannot be finalized without a verification pass that none of the other options require. That dependency inverts the acceptance property: a wrong or incomplete ConfigNamespace declaration can reject a legitimate existing value that a1's blind merge would have preserved, so the mechanism intended to strengthen the schema is the one mechanism that can actively break an existing installation on a shape change. It also widens the blast radius by changing a shared catalog type other config surfaces read, well beyond the Story's stated internal scope, at the highest cost estimate (L) for a bar a1 already clears at M. The idea has genuine long-term value — validating inside dynamic subtrees, and reusable namespace declarations for the CLI config surface and docs — but it belongs in a follow-up once those namespaces are actually characterized, layered on top of a1's or a3's merge, not as this Story's first move.
