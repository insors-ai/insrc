# One work item scatters its artifacts across several docs folders because the folder label is re-derived at each stage

## Reproduction

Run a bugfix chain end to end (issue, design.story, plan, build) for a single standalone work item, then list its docs folders. Observed for work item 792f9324fc43d95c (identity segment E20261002792f9324): four sibling folders, each holding exactly one artifact. docs/standalone/regression-hierarchical-label-resolver-listepichashes-src-E20261002792f9324/ISSUE.md; docs/standalone/lld-revision-supersedes-earlier-pass-whose-E20261002792f9324/S001/LLD.md; docs/epics/lld-revision-supersedes-earlier-pass-whose-E20261002792f9324/S001/PLAN.md; docs/epics/792f9324fc43d95c-E20261002792f9324/S001/BUILD.md. Expected one folder holding all four, since all four share the same identity segment. The two fields that select the folder diverge stage by stage in the stored metadata: ISSUE has epicSlug 'regression-hierarchical-label-resolver-listepichashes-src' and standalone true; LLD has epicSlug 'lld-revision-supersedes-earlier-pass-whose' and standalone true; PLAN keeps that same slug but standalone is absent; BUILD has both absent. Two further symptoms follow from the same divergence: the build record for this standalone story is written under docs/epics/ instead of docs/standalone/, and its rendered heading reads '# Build (plan-driven) - Story S001' with '**Standalone:** no' even though the work item is standalone.

## Root cause

A work item's docs folder is named label-plus-identity-segment (workItemRoot, path-scheme.ts:104). The identity segment was identical across all four artifacts, so identity is not at fault; the mutable label is, along with the docs/epics vs docs/standalone split. Neither of the two fields that produce those is inherited from the work item's definition artifact, so each stage recomputes them and any difference forks a new folder. Three distinct contributors, each read directly from the code. First, finalizeStandaloneLld (orchestrator.ts:2260) computes the slug as safeDeriveSlug(intent.focus) unconditionally, so a standalone LLD coins a label from its own focus prose instead of taking the slug its ISSUE already carries; three sibling finalizers at orchestrator.ts:1751, :2082 and :2529 already use the inherit-then-fallback form (meta.epicSlug first, derive only as a fallback), so the correct pattern exists in the same file and this one site omits it. Three further unconditional derivations in the same file, at :686, :858 and :1152, are NOT defects and must stay as they are: they belong to the SPEC, ISSUE and DEF heads, which legitimately mint a work item's label because no earlier artifact exists to inherit from. Only :2260 derives a label for a work item that already carries one. Second, only two sites write standalone:true into persisted artifact metadata (orchestrator.ts:872 for the ISSUE, :2303 for the standalone LLD); the other standalone:true occurrences across src are triage route objects, build-step prompt payloads, a type declaration and log lines rather than metadata writes, so no stage after the LLD re-asserts the flag and the plan and build records store it absent, and standalone-record.ts:241 passes merged.meta.standalone === true into buildRecordFolderArgs, which collapses absent to false; buildRecordFolderArgs (storage.ts:232) then returns workItemKind 'epic', placing a standalone story under docs/epics/. The same absence makes renderBuildRecordMd (standalone-record.ts:149) pick the plan-driven title and render 'Standalone: no'. Third, that false value also selects the epic branch of buildRecordFolderArgs, which reads defineArtifactId(epicHash) only; this work item's definition artifact is an ISSUE, not a DEF, so the read finds nothing and upstream.epicSlug is undefined. That branch has exactly one upstream read (storage.ts:241) and storage.ts performs no ISSUE read anywhere, even though the helper it would need already exists in the same file (issueArtifactId, storage.ts:169) - so this is an omission at a known call site, not a missing capability. The label then falls back to the raw hash via the epicSlug ?? epicHash default, which recurs at seven sites in storage.ts (for example :301, :361, :382), producing the folder named 792f9324fc43d95c-E20261002792f9324. That third contributor is a second instance of the same DEF-only read pattern already recorded against resolveByIssue in tracker/resolve.ts:337: an epic-level read that honours DEF but not the equivalent ISSUE.

## Fix intent

Make a work item keep exactly one docs folder for its whole lifetime. The label and the epics-versus-standalone placement should be properties of the work item, established once by its definition artifact (DEF or ISSUE alike) and inherited unchanged by every later stage, rather than recomputed per stage from whatever prose that stage happened to receive. Every epic-level lookup involved must treat an ISSUE as the definition artifact exactly as it treats a DEF, so a bugfix work item is never left without a label and never falls back to the raw hash. A standalone story's build record must be placed and rendered as standalone. The design stage also has to settle two questions this record deliberately leaves open: whether to prevent drift only at the source or additionally make it harmless by locating an existing folder through its stable identity segment regardless of label, and what to do about folders already written to the wrong location on disk, including the four belonging to this work item.
