# Stop the MCP server process from opening the live graph store

## Reproduction

1. Start an insrc MCP server (src/bin/insrc-mcp.ts), e.g. by opening a Claude Code or Codex session that has the insrc MCP configured.
2. Use it until a call runs an in-process graph tool (code_class_locate / code_class_references, reached through the analyze freeform.probe tool surface).
3. `lsof ~/.insrc/graph.lmdb` now lists the MCP's node process holding graph.lmdb and graph.lmdb-lock, beside the daemon.

Observed (2026-10-12): `lsof` listed the MCP spawned by the Codex extension (node ~/.insrc/daemon/out/bin/insrc-mcp.js, running since 2026-10-11 20:13, parent the Codex app-server) holding graph.lmdb and graph.lmdb-lock while no daemon was running.

Expected: no process other than the daemon ever opens graph.lmdb; an MCP server reaches the store only through the daemon over IPC.

Related, NOT established as caused by this: during the same window every daemon start exited with code 134 (ISSUE-f442f10bd21284a5). After the MCP was killed the next start succeeded, but that start also ran a newer build and a different launch command, and a two-process reproduction on a temp store (a second process opening an LMDB env another process holds, with getGraphStore's default open options: a 1024 GiB map and 32 sub-DBs) succeeded with exit 0. So a second holder does not, on its own, stop the daemon from starting.

## Root cause

runInsrcMcpStdio (src/mcp/server.ts:1254) registers the daemon's whole builtin tool set in the MCP process: registerBuiltinTools() (:1272), registerBuiltinDataDrivers() (:1273) and registerWorkflowRunners() (:1274). The comment at :1261 says it mirrors the daemon boot. It does this so the analyze driver's read-only tool surface is populated in that process: src/analyze/context/driver.ts imports getReadOnlyTools (:86) and calls it in its tool loop (:773), and getReadOnlyTools (src/analyze/context/tool-surface.ts) throws ReadOnlyToolRegistryMismatch if the registry is empty. Two of those builtins read the graph by calling getGraphStore() directly, and both are on the analyze allowlist: code_class_locate (src/daemon/tools/builtins/code/class-locate.ts:214) and code_class_references (src/daemon/tools/builtins/code/class-references.ts:184). getGraphStore (src/db/graph/store.ts:416) lazily opens the LMDB environment in whatever process calls it and keeps it open, so the MCP process becomes a second long-lived owner of the store. Nothing in getGraphStore checks which process is calling, so the breach of rule #1 (the daemon owns all DB access) goes unnoticed until the daemon fails to start.

A grep scoped to src/daemon/tools/builtins finds exactly these two direct callers of getGraphStore(). They are the openers confirmed on the MCP runtime path, but the full list of openers is not provably complete. Other code in the MCP's import closure can also open the store but is not confirmed to run there: src/workflow/code-review/grounding.ts is loaded through src/mcp/server.ts:50 -> src/mcp/code-review-step/handler.ts:38, but the MCP handler only calls the diff-based grounding, and realGroundingDeps (:104, which imports getGraphStore at :105) is called from the daemon and the code-review runner. src/workflow/code-review/freshness.ts:92 does the same import and is called only from the daemon (src/daemon/index.ts:770). Modules that wrap getGraphStore, such as src/config/store.ts, can also open it indirectly.

## Fix intent

The MCP server process must never open graph.lmdb, whichever code path asks for it. Any graph read it needs must go to the daemon over IPC, or the graph-reading tools must not be offered in the MCP process. Because the set of openers cannot be listed completely, the protection must hold at the store boundary: opening the store from any process other than the daemon fails loudly and says why, instead of silently taking a second hold. A test must enforce that the MCP binary's runtime path cannot open the store, so the regression cannot come back unseen. Check afterwards whether this resolves or narrows ISSUE-0d577569 and ISSUE-f442f10bd21284a5 (daemon loses its LMDB locks when another process closes the store).
