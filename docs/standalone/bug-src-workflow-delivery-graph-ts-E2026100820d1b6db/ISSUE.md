# Attach a seeded SPEC to its story, never a task, and flag an item that names two specs

## Reproduction

Build the delivery work-item graph over a store where a story's PLAN (or BUILD) record carries meta.seededFromSpec = <specHash> and lists tasks, plus the SPEC-<specHash> record. Observed: the SPEC attaches to the LAST task draft that holds that PLAN as evidence. The task gets seededFromSpecId and the SPEC in its evidence, while the story gets neither. Expected: the story holds the SPEC. Second case: one story whose LLD names spec A and whose DEF/LLD sibling names spec B. Observed: seededFromSpecId is whichever record is read last, with no notice. Expected: a notice naming both specs. This is latent today because only DEF and LLD records are stamped with seededFromSpec, so the first case cannot occur in a real store yet.

## Root cause

attachSpecs (src/workflow/delivery/graph.ts) builds itemOfRecord by walking every draft and setting itemOfRecord[artifactId] = draft for each evidence id, so the last draft to list an id wins. addTasks gives each task draft the story's PLAN and BUILD artifact ids as its own evidence, and task drafts are inserted into the drafts map after their story, so for a PLAN or BUILD id the task, not the story, is the recorded holder. The seeding loop then overwrites item.seededFromSpecId on every record that names a spec, without checking whether the item already names a different one.

## Fix intent

When deciding which item a record seeds, consider only story, epic and issue items, never tasks, so a spec named by a PLAN or BUILD attaches to its story. When one item's records name two or more different specs, raise a notice naming the item and the specs instead of silently keeping the last one. No other graph behaviour or notice changes. Which notice code to raise is the fix's choice; if it needs a new NoticeCode (with its attention entry), that is the one published type change.
