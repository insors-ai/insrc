# Make a failed daemon start leave a diagnosis instead of aborting silently

## Reproduction

Observed on 2026-10-12 (not yet reliably reproducible):

1. At 12:19:17 the running daemon received a `daemon.shutdown` RPC and logged 'shutdown signal received; draining...'. It never logged 'bye', and no later daemon process wrote anything to /tmp/.insrc. At 12:23 no daemon was running and ~/.insrc/daemon.sock did not exist.
2. Starting the installed build (88db0f22, an ancestor of 01ca9641 in the installed clone ~/.insrc/daemon) by hand, `node ~/.insrc/daemon/out/daemon/index.js` under Node 22, exited at once with code 134 (SIGABRT), twice. It wrote 0 bytes to stdout and stderr and added nothing to the /tmp/.insrc logs. At that time an insrc MCP process (ISSUE-e980ffbb6dd346e7) held graph.lmdb and graph.lmdb-lock.
3. After that MCP process was killed, `daemon-ctl.sh start` fast-forwarded the install to 01ca9641, rebuilt it, and started a daemon that came up normally.

Step 3 differs from step 2 in three ways at once: the holder was gone, the build was newer, and the launch was the production one (`INSRC_MODE=daemon node --import tsx/esm`, scripts/daemon-ctl.sh:142) rather than plain `node`. A two-process reproduction on a temp store showed that a second process opening an LMDB env another process holds, with getGraphStore's default options (a 1024 GiB map and 32 sub-DBs), succeeds. So the abort is not explained by a second holder alone.

Expected: whatever makes startup fail, the daemon leaves a diagnosis: a non-zero exit with a message saying what failed and at which boot step, on stderr and in the daemon log. A held store additionally names its holder (pid and command). Whatever launched the daemon shows that message. The symptoms a reproduction should assert: exit code 134 with no output; ~/.insrc/daemon.sock never bound (src/daemon/server.ts:123); no 'listening on' log line (server.ts:124); and no ~/.insrc/daemon.pid, which boot writes only after the store opens (writePid at src/daemon/index.ts:275, after getGraphStore at :236). In the CLI, isRunning() checks only that the pid file names a live process (src/cli/services/lifecycle.ts:36-38), while the start wait requires a live pid and the socket together (lifecycle.ts:63).

## Root cause

Diagnosed: a failed start leaves no diagnosis. The daemon's crash reporting is JavaScript-only: the only fatal hooks are the uncaughtException and unhandledRejection handlers in src/daemon/index.ts (:32, :33), which call reportFatal (src/daemon/fatal.ts). Nothing registers for a native abort, and no process.report diagnostic is configured. A native abort ends a Node process without running JavaScript handlers, which fits the observed exit 134 with no reportFatal output. Daemon logging goes through a pino worker-thread transport (target 'pino-roll' in src/shared/logger.ts), and nothing in the logger, the boot path or the fatal handler flushes it. The leading explanation for the missing boot lines is that lines still buffered in the worker are lost when the process aborts; this has not been reproduced. Boot also has no check for another holder before its native opens: step 3 (src/daemon/index.ts:223) opens LanceDB with getDb() (:224) and then the LMDB env with getGraphStore() (:236, open({ path, mapSize, maxDbs }) at src/db/graph/store.ts:439), and a grep of both files for a holder, lsof, EBUSY or lock-holder check finds none.

Not diagnosed: what aborted. Candidates the build stage must separate: the plain-`node` launch without INSRC_MODE=daemon and the tsx loader; the 88db0f22 build; a native open (LanceDB or LMDB) in the store's lock state at the time, which may be the lock-loss state described in ISSUE-0d577569; and the earlier shutdown that never finished.

## Fix intent

Pin what aborted, with a reproduction, before choosing the remedy. Whatever the cause, a daemon whose start fails must leave a diagnosis that survives a native abort: the boot step reached is durably recorded before each native open, and a failure exits non-zero with a message on stderr and in the daemon log. When the store is held by another process, the message names the holder (pid and command). The daemon entry itself must do this, so every launcher benefits, including direct spawns and manual runs. The in-repo launchers must show that message to the user instead of a bare 'not running': scripts/daemon-ctl.sh cmd_start, which cmd_restart also runs (cmd_restart = cmd_stop then cmd_start; cmd_update only syncs and builds and does not start the daemon), and the CLI startDaemon (src/cli/services/daemon.ts:60), which serves the maintenance restart (src/cli/services/maintenance.ts:299), src/cli/command.ts:82 and the TUI DaemonPane (src/cli/panes/DaemonPane.tsx:51). Plugin and update callers that shell out to daemon-ctl.sh are covered through those two commands.
