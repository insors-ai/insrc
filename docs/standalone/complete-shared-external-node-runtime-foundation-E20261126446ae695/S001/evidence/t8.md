`resolveControlRuntime` calls the real shared resolver from explicit location and
manifest/policy identity, then checks the actual process executable, version,
platform and architecture. Manager entry additionally requires its own canonical
release directory and verifies bound control files. Terminal entry binds normal
install, Retry and service/dev-worker roles before control mutations. The separate
T5 publication helper retains its authenticated execution-stage handoff.

Production composition receives the resolver result within that launch. It checks
canonical paths, independent profile inventory identity and exact target before
constructing dependency/delivery ports. Dependency readiness consumes that verified
context within its three-second presence-probe budget, rather than inventing trust
from an ambient Node directory. No JS capability is persisted as a wire flag.

`resolveInstalledControl` is the common installed reader for both formats. It
checks strict canonical receipts, the exact bound application inventory digest,
bounded inventory-listed control entrypoints/native files/hooks and the external
runtime. Application data is not walked or read. The dev inventory's canonical
encoding remains enforced; bundle inventory retains its existing byte encoding.
Preparation still verifies complete application membership/content before immutable
publication; installed opening is a separate, bounded operation.

TUI selection uses this reader and its resolved executable, rechecking controller
selection and lifecycle readiness. Retry and owned-launcher publication are async
because they resolve real runtime/control evidence. Launcher template ownership,
private regular-file checks, bounded same-fd reads, native lease and exact-byte
comparison remain; an owned file is rechecked after asynchronous predecessor
verification. A broken control file suppresses an unchecked Retry command, while
the completed selection and duplicate-completion result survive. A normal failed
TUI process still receives its verified Retry command.

Ollama already avoided installed-content rehashing before this task. Its remaining
full tree/layout metadata walk was still used during readiness reconciliation.
`readPreparedOllamaRecords` now supplies bounded canonical inventory/receipt and
policy facts to that read-only path, preserving closure/admission cross-bindings.
Preparation and service launch retain full bounded layout/metadata and executable/
library-header checks. This does not add installed-content hashing, a service-start
authority, implicit retry, or cleanup permission. The actual retained worker is
launched with resolved Node and checks its own canonical runtime before control
work. The existing standalone qualification driver was adapted to the same API.
