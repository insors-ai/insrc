# Daemon update always fails on an unmanaged macOS install, across the CLI, VS Code and JetBrains alike: cmd_update forces every unmanaged checkout through an unprovisioned signing gate

## Reproduction

On any Mac whose ~/.insrc/daemon is a plain git checkout (no ~/.insrc/managed-lifecycle/installation.json): (1) run `scripts/daemon-ctl.sh update` directly from a terminal, (2) click Update in the VS Code extension, or (3) click Update in the JetBrains plugin. All three fail identically with 'preparing the macOS upgrade bridge beside the installed release' then 'FATAL: production source release signing key is not provisioned 4' (reproduced 3 times via the VS Code path: /tmp/insrc/daemon-install-20261118-095256-588.log, /tmp/insrc/daemon-install-20261118-101207-22731.log, /tmp/insrc/daemon-install-20261118-101214-22884.log). Expected: the daemon updates via a plain git-fetch-and-rebuild, exactly as start/stop/restart already do for an unmanaged install on the same machine, and exactly as update already does on Linux.

## Root cause

scripts/daemon-ctl.sh's cmd_update (lines 396-416) is the only one of the four lifecycle verbs (start/stop/restart/update) that special-cases an unmanaged install on Darwin: when supervised_lifecycle returns rc=10 (no managed-lifecycle state) and the OS is Darwin, cmd_update re-execs scripts/insrc-daemon-install.sh --target "$DAEMON_ROOT" -y (lines 402-408) instead of falling through to the plain sync_repo/npm_install_if_needed/npm_build sequence its own non-Darwin branch uses (lines 409-415). cmd_start/cmd_stop/cmd_restart (lines 368-394) all fall through to their plain unmanaged logic identically on Darwin and Linux -- only update diverges. The re-exec'd insrc-daemon-install.sh then requires the env var INSRC_RELEASE_BOOTSTRAP_B64 to be non-empty before it will stage the 'verified macOS upgrade bridge' (scripts/insrc-daemon-install.sh:226), and that key has never been provisioned into any distributed installer: not scripts/insrc-daemon-install.sh as committed, not vscode-plugin/assets/insrc-daemon-install.sh, and no CI secret exists for it. Because cmd_update's plain fallback explicitly does not restart the daemon ('update complete (daemon NOT restarted)', line 415), it cannot retrigger the errno-1 restart failure that the managed-lifecycle epic (ISSUE-5d5478c61a25ac8f, docs/standalone/enable-managed-daemon-lifecycle-macos-install-E202611115d5478c6/S001/LLD.md) was built to fix -- that failure was specifically about RESTART through the old broker, not about update's git-fetch-and-rebuild step. Both IDE plugins independently special-case this same unmanaged-install detection to pre-empt daemon-ctl.sh's dead end, and both land on the identical wall by a different route: vscode-plugin/src/daemon/controller.ts's run('update') (lines 107-108) detects an unmanaged install with an existing daemon entry/ctl script and calls install(true), which runs the extension's own bundled assets/insrc-daemon-install.sh --target ... -y -- the same unprovisioned gate. jetbrains-plugin/src/main/kotlin/ai/insors/insrc/jetbrains/lifecycle/DaemonLifecycleService.kt's existingUpgradeTarget() (lines 231-233) is a line-for-line equivalent condition (macOS && no managed install && ctl script or daemon entry exists), consumed by ScriptDaemonProvisioner.kt's run(kind) (lines 58-73) to route UPDATE through its own bundled insrc-daemon-install.sh -y --target instead of daemon-ctl.sh update -- the identical dead end, reached independently.

## Fix intent

Establish two explicit, always-working update paths. (1) A managed/signed install (one with ~/.insrc/managed-lifecycle/installation.json) keeps using the existing signed, transactional migration-and-update machinery exactly as today -- unchanged. (2) An unmanaged git-clone install's update always completes via the same plain git-fetch + npm install + npm build sequence cmd_update already runs on non-Darwin, with no signing requirement at all, bringing Darwin's unmanaged update path in line with how start/stop/restart already behave unmanaged on Darwin today. Concretely: stop scripts/daemon-ctl.sh's cmd_update from re-execing the signed installer bridge for the unmanaged case. Once daemon-ctl.sh update itself safely routes either way (managed -> signed migration, unmanaged -> plain update), remove the now-redundant pre-emptive special-cases in vscode-plugin/src/daemon/controller.ts (install(true) on detecting an unmanaged-but-present install) and in jetbrains-plugin's ScriptDaemonProvisioner.kt/DaemonLifecycleService.kt (existingUpgradeTarget()), so both clients simply call daemon-ctl.sh update unconditionally. Update the existing tests that encode the old auto-migrate-on-first-update expectation -- vscode-plugin/src/daemon/__tests__/controller.test.ts and jetbrains-plugin/src/test/kotlin/ai/insors/insrc/jetbrains/lifecycle/DaemonProvisionerTest.kt, DefaultDaemonScriptLocatorTest.kt and DaemonLifecycleCommandRunnerTest.kt -- to assert the corrected two-path behavior instead.
