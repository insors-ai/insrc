# Verify signed development daemon bundles on macOS

Use a disposable Apple Silicon macOS 15 or later VM, Node 22.22.1, and independently authenticated development bootstrap and policy files. The signed policy identifies the repository, the allowed full development refs, and the fingerprint of the development qualification public key. Keep private builder, issuer, and qualification keys outside the guest. Only the bootstrap runtime, public keys, signed policy, and artifacts belong in the VM.

1. Build the exact approved branch commit with `package-daemon-development.mjs POLICY FULL_REF COMMIT VERSION OUTPUT COMPATIBILITY`. Attest the candidate using `sign-daemon-development.mjs attest-handoff OUTPUT BUILDER_KEY`, then sign the first release with `sign-daemon-development.mjs OUTPUT SEQUENCE ISSUER_KEY BUILDER_PUB POLICY COMPATIBILITY`. The signed policy signature lives beside the policy with a `.sig` suffix.
2. Create the guest marker with `(umask 077; touch "$HOME/.insrc-development-guest")`. In the authenticated bootstrap, place `development.pem`, `development-policy.json`, and `development-policy.sig` under `trust/`. Use the pinned bootstrap Node to run `install-daemon-development-bundle.mjs VERSION MANIFEST SIGNATURE ARCHIVE`. Verify `daemon-ctl.sh status`, MCP initialization, and `daemon-ctl.sh restart` from the selected release. Record the installed receipt and the old and new generation or PID. Use `~/.insrc/managed-lifecycle/installation.json` to locate the selected release.
3. Prepare a distinct candidate on a second approved ref. Run `sign-daemon-development.mjs prepare-qualification OUTPUT SEQUENCE ISSUER_KEY BUILDER_PUB POLICY COMPATIBILITY`. In a disposable copy with the exact installed predecessor running, install the resulting qualification-only manifest using `install-daemon-development-bundle.mjs ... --qualify`. Capture its managed rollback receipt. Verify it records the candidate write, the interrupted candidate, the restored predecessor, and the state hash served in the reopened predecessor. Run this trial with the VM disconnected from external networks.
4. Sign the observed qualification record with the separate qualifier key using the bytes returned by `developmentQualificationSigningBytes` in `sign-daemon-development.mjs`. Save its detached signature next to the evidence file with a `.sig` suffix. Sign the candidate with `sign-daemon-development.mjs OUTPUT SEQUENCE ISSUER_KEY BUILDER_PUB POLICY COMPATIBILITY PRIOR_DIR EVIDENCE QUALIFIER_PUB`. Use a sequence above the target guest's admission floor. On the unmodified target with the exact predecessor installed, install the ordinary signed development manifest without `--qualify`. Check that the selected release changed and the representative state, CLI, and MCP still work. Repeat against an incompatible predecessor and check that the installed receipt and active service stay intact.
5. For interrupted installs, retry the authenticated bootstrap in the same guest using the original release arguments. Recovery uses the existing authenticated transaction and admission floor. Keep the VM offline while testing rollback, and preserve the journal when ownership cannot be established.

Collect build logs, signed manifest digests, CLI and MCP results, qualification evidence, and the final journal outcome before deleting the test VMs and their downloaded image cache. The local path uses configured development refs. Hosted development candidate publication is a separate rollout.
