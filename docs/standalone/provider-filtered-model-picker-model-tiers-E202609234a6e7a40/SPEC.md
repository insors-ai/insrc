# Spec: Add a provider-filtered model picker for the three GLOBAL model tiers (models.tiers.core/mid/cheap) on BOTH the VS Code and JetBrains plugins.

**Category:** requirements

## Intent

Add a provider-filtered model picker for the three GLOBAL model tiers (models.tiers.core/mid/cheap) on BOTH the VS Code and JetBrains plugins. The existing runner enum (ollama | cli-claude | cli-codex) stays as-is. Once a runner is picked, the tier's model field — today free text — becomes a DROPDOWN populated from a NEW read-only daemon capability that lists the models available for the selected provider (replacing the stale offline-stubbed providers.listModels). The daemon is the single proxy for the model list; both plugins stay dumb dropdowns with no per-provider logic. Source per provider: ollama = a live local query (ollama list / API), always current; cli-claude and cli-codex = a curated catalog shipped IN the daemon repo (per the confirmed d3 refinement, as a JSON asset file loaded by the daemon — not a hardcoded TS literal and not a user-editable ~/.insrc/ file — maintainer-curated in git and picked up via `daemon-ctl.sh update`), consistent with the hard no-direct-cloud-REST rule (cloud goes only through the CLIs). The dropdown is authoritative for all three providers — no free-text override. When the list call fails or is empty the dropdown hard-blocks ('no models available', disabled) with a manual Refresh button (per d2) to re-query, leaving the saved value untouched; when the list succeeds but omits the tier's saved model it is shown as a disabled '(current, not in catalog)' entry; switching a tier's provider mid-edit clears the model field. UI surfaces: JetBrains = an inline editable combo/dropdown per tier on the existing Settings page; VS Code = a new `insrc: Set model tier` QuickPick command (native VS Code Settings cannot render a provider-filtered live dropdown inline).

## Scope boundary

Scoped to the three GLOBAL model tiers only, on both plugins, plus the one new read-only daemon list-models capability + its curated cloud JSON catalog asset. It deliberately does NOT touch per-role model tiers, does NOT add per-repo tier overrides (per-repo config keeps just referencing a globally-defined tier), does NOT change or extend the provider/runner allowlist (the existing enum is reused unchanged), and does NOT add any free-text/manual model-entry override for any provider (the dropdown — live for ollama, curated catalog for cli-claude/cli-codex — is authoritative everywhere). All model-list freshness/resilience logic lives in the daemon capability, not in the plugins.

## Non-goals

- Per-role model tiers (only the 3 global tiers are in scope)
- Per-repo tier overrides (per-repo config continues to just reference a globally-defined tier)
- Changing or extending the provider/runner allowlist itself
- Free-text/manual model entry override for any provider — the dropdown (live for ollama, curated catalog for cli-claude/cli-codex) is authoritative everywhere
- Dropdown + explicit 'custom model...' escape hatch that reveals a free-text field, for all three providers
- Dropdown + escape hatch, but ONLY for cli-claude/cli-codex (ollama's live query never goes stale, so it stays strict dropdown-only)
- Degraded free-text fallback: only when the list call is currently failing, allow typing/keeping a raw model string for that tier; auto-reverts to dropdown-only the moment the call next succeeds
- Daemon caches the last-known-good list per provider and serves that on a fresh failure, only showing the empty/error state if there's no cache yet
- Editable static JSON/config file under ~/.insrc/ that ships with a default catalog but can be hand-edited by the user/admin without touching daemon source
- Fold the catalog into the existing CONFIG_CATALOG-driven config system alongside models.tiers, reusing the schema-driven reconcile pipeline
- Drop it from the dropdown silently; the control shows unselected/placeholder until the user picks a real entry, though the underlying config value is untouched until they do
- Treat a stale saved value the same as d2's empty/error case: block with a warning and require the user to resolve it before the tier is considered configured
- Treat like d4's stale entry — keep the old model visible, greyed/disabled and appended to the new list as e.g. "(from ollama, switch to update)", until a real entry is picked
- Keep the old value visible un-greyed and just block Save until a model from the CURRENTLY selected provider's list is chosen

## Decisions

- **Strict dropdown-only, no override — catalog is authoritative for cli-claude/cli-codex; ollama stays free (live-queried, always current)** — The focus explicitly says the claude/codex list is a 'curated static catalog maintained in the daemon' (inherently lag-prone) while ollama is a 'live local query' (inherently current) — so the staleness risk is asymmetric across providers, making this the first fork the rest of the validation/UI design hangs off. User reframed: freshness is proxied entirely through the daemon (dumb dropdown UI, no escape hatch); the cloud catalog's staleness is fixed daemon-side, not surfaced in the UI.
  - Ruled out: _Dropdown + explicit 'custom model...' escape hatch that reveals a free-text field, for all three providers_, _Dropdown + escape hatch, but ONLY for cli-claude/cli-codex (ollama's live query never goes stale, so it stays strict dropdown-only)_
- **Hard block: dropdown shows "no models available" and is disabled; the tier's existing saved value (if any) is left untouched until the call succeeds again** — The catalog-only decision means a tier's model can only be set from what the new daemon capability returns. What should the picker do when that call comes back empty or errors — most realistically an ollama instance that's down or unreachable for a live query? User chose hard-block PLUS a manual Refresh button on both plugins to re-invoke the daemon list-models capability on demand (VS Code: a 'Refresh models' item in the QuickPick flow; JetBrains: a Refresh icon-button beside the combo), so a transient ollama outage is recoverable without any free-text override or daemon-side cache.
  - Ruled out: _Degraded free-text fallback: only when the list call is currently failing, allow typing/keeping a raw model string for that tier; auto-reverts to dropdown-only the moment the call next succeeds_, _Daemon caches the last-known-good list per provider and serves that on a fresh failure, only showing the empty/error state if there's no cache yet_
- **Hardcoded literal in daemon source (e.g. a CLI_MODEL_CATALOG constant), shipped through ordinary daemon code changes and picked up on `daemon-ctl.sh update`** — The cli-claude/cli-codex catalog is now authoritative and strict (d1) — a model won't be selectable until it's added to the catalog. Where should that curated catalog live, and how does it get updated when a provider ships a new model? User REFINEMENT: keep the recommended lifecycle (in the daemon codebase, maintainer-curated in git, shipped via `daemon-ctl.sh update`) but store the catalog as a JSON ASSET FILE (loaded by the daemon's copy-assets pipeline + validated at boot), NOT a hardcoded TS literal and NOT a user-editable ~/.insrc/ file — easier to review/edit while keeping the curated/authoritative guarantee.
  - Ruled out: _Editable static JSON/config file under ~/.insrc/ that ships with a default catalog but can be hand-edited by the user/admin without touching daemon source_, _Fold the catalog into the existing CONFIG_CATALOG-driven config system alongside models.tiers, reusing the schema-driven reconcile pipeline_
- **Show it as a disabled/greyed entry appended to the dropdown, labeled e.g. "(current, not in catalog)", so the user sees exactly what's configured; picking any other entry replaces it** — A tier's currently saved model can go stale relative to the freshly fetched list — not the d2 empty/error case, but the list succeeds and simply no longer contains the saved value (e.g. a curated catalog entry was retired, or an ollama model was deleted locally). What should the picker do with that mismatched saved value?
  - Ruled out: _Drop it from the dropdown silently; the control shows unselected/placeholder until the user picks a real entry, though the underlying config value is untouched until they do_, _Treat a stale saved value the same as d2's empty/error case: block with a warning and require the user to resolve it before the tier is considered configured_
- **Clear immediately — switching provider blanks the model field, forcing an explicit pick from the new provider's list before the tier can be saved** — d1 made cli-claude/cli-codex catalog-only, and d4 defined how a stale SAVED model displays when a freshly-fetched list no longer contains it. That leaves an in-session edit case: the user changes a tier's provider/runner (e.g. ollama → cli-claude) before saving, and the model currently shown in the field belongs to the OLD provider's list — it won't appear in the new provider's dropdown. What should the picker do to that model selection the instant the provider changes?
  - Ruled out: _Treat like d4's stale entry — keep the old model visible, greyed/disabled and appended to the new list as e.g. "(from ollama, switch to update)", until a real entry is picked_, _Keep the old value visible un-greyed and just block Save until a model from the CURRENTLY selected provider's list is chosen_
