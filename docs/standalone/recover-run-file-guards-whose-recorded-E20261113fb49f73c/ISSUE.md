# Recover run-file guards whose recorded owner is conclusively dead instead of withholding daemon restart

## Reproduction

Update or restart the daemon after a previous daemon exit that died while holding the run-file guard. Observed: the new start refuses ~/.insrc/daemon.run-files.guard with `run-file ownership conflict ... state=gone ... Restart is withheld. An operator must verify the original owner has ended and quarantine this exact guard before retrying; it was not reclaimed automatically`, and startup proceeds only after the operator manually moves the guard directory aside. Confirmed initiating sequence (/tmp/.insrc/daemon.log, 2026-11-13 05:01:14–34 UTC) (c10): a daemon.shutdown RPC whose queue drain exceeded the 20-second hard-exit backstop; at the deadline the in-process fallback ran failClosed, whose cleanup (clearPid → clearRunFiles, c4) re-creates the guard directory and owner.json just to remove daemon.pid and daemon.sock, while the independent native shutdown-watchdog process (c6) — armed at the same deadline — independently SIGKILLed the daemon from outside. The SIGKILL can land inside clearRunFiles' guard window, leaving a complete owner.json naming a now-dead process: exactly `state=gone`. Frequency: six manually quarantined guards under ~/.insrc since 2026-11-02 (2026-11-02, 11-04, 11-08, 11-09, 11-11, 11-13) (c11); the 11-02 incident quarantined a guard with owner.json missing (unverifiable-owner variant, an interrupted release). Expected: a routine update/restart succeeds without operator filesystem surgery when the recorded owner is provably dead, while live or unverifiable owners remain protected.

## Root cause

The run-file guard is a mkdir-mutex whose owner record is only removed by an orderly release (unlink owner.json, then rmdir). Any process death between acquire and release leaves the directory behind with a dead recorded owner, and startup classifies every existing guard as a conflict it must not reclaim — even when its own liveness probe (`processIdentityState`, c3) has already established that the recorded owner is positively absent (`state=gone`). The liveness verdict is computed and then discarded instead of driving recovery. Concretely, the daemon dies holding the guard in three code-supported windows: (1) the shutdown-deadline race — the in-process failClosed path (c5) re-creates the guard inside clearRunFiles (c4) at the same moment the native watchdog (c6) independently SIGKILLs the process, so the kill can land inside the re-created guard window; (2) an external SIGKILL while the startup lease is held; (3) an interrupted publication or release, which the acquisition path documents as a deliberate fail-closed orphan (c2) and which yields the unverifiable-owner variant. Because reclamation is withheld for all of these (c1), each one blocks the next restart until an operator quarantines the guard by hand.

## Fix intent

Daemon startup automatically recovers a run-file guard whose recorded owner is conclusively dead, replacing the manual operator quarantine with a supported, self-healing path. Liveness is decided by the existing full process identity (pid plus boot-id plus start-ticks plus command line, so a reused PID cannot fake liveness), and a guard recorded under a previous boot is treated as conclusively dead even when its PID now reads as replaced. The recovery is recorded with a log entry and retains the previous owner record as inspectable evidence, and it stays atomic with respect to competing daemon starters so concurrent startups remain serialized. Live owners keep full protection: a guard whose owner is alive, or whose owner record is missing, corrupt or otherwise unverifiable, still withholds restart, and an unreadable identity is never silently treated as dead. With conclusively-dead guards self-healing at startup, the known orphan windows — the shutdown-deadline race between the in-process fail-closed cleanup and the native shutdown watchdog, an external SIGKILL while the startup lease is held, and interrupted publication or release — become benign and are not separately fixed. This replaces the recovery stance of the prior record (docs/standalone/prevent-orphaned-daemon-run-file-guards-E20261108350bdba6/ISSUE.md), whose diagnosis this record extends with the confirmed initiating sequence.
