# Spec: Rebuild the review framework's PROCESS layer on top of the ReviewContext data model from the companion data-model spec (round, scopeType/scopeLevel Scope, submitter-populated ReviewTargets, Comments) — itself amended by two cross-cutting facts discovered in this session and carried back into it: (a) the review id (the `.insrc/tmp/<reviewId>/` temp folder's own name, one identity not two) must be a HEADER-LEVEL field on ReviewContext alongside `round`, so a re-attempt can recover/resume by reading the id straight off the artifact/context rather than depending solely on caller-side bookkeeping — without the caller supplying that same id back on resume, the system cannot find prior state and starts a brand-new review from scratch; (b) a Correction-and-Re-review round's ReviewContext also carries a submitter-populated `corrections: { feedback: Feedback, pointers: Pointer[], reason: string }[]` array, one entry per prior-round Feedback item naming what was changed (via the same Pointer/Locator shape used elsewhere) or rejecting it with a reason — this corrections list is ordinary submitted content the reviewer evaluates like anything else, never a trusted resolution log.

**Category:** requirements

## Intent

Rebuild the review framework's PROCESS layer on top of the ReviewContext data model from the companion data-model spec (round, scopeType/scopeLevel Scope, submitter-populated ReviewTargets, Comments) — itself amended by two cross-cutting facts discovered in this session and carried back into it: (a) the review id (the `.insrc/tmp/<reviewId>/` temp folder's own name, one identity not two) must be a HEADER-LEVEL field on ReviewContext alongside `round`, so a re-attempt can recover/resume by reading the id straight off the artifact/context rather than depending solely on caller-side bookkeeping — without the caller supplying that same id back on resume, the system cannot find prior state and starts a brand-new review from scratch; (b) a Correction-and-Re-review round's ReviewContext also carries a submitter-populated `corrections: { feedback: Feedback, pointers: Pointer[], reason: string }[]` array, one entry per prior-round Feedback item naming what was changed (via the same Pointer/Locator shape used elsewhere) or rejecting it with a reason — this corrections list is ordinary submitted content the reviewer evaluates like anything else, never a trusted resolution log. There are two review kinds, Initial Review and Correction-and-Re-review, sharing one execution process and distinguished purely by round number (round 1 vs round > 1), with no divergent steering/checklist logic beyond what reconciliation provides. Steering is revised so the reviewer always performs its own independent grounding against real source: enforcement is POLICY-ONLY — the reviewer is handed the full artifact including any submitter rationale (e.g. in Comments) and instructed via steering to re-derive independently and disregard the narrative; a structural claim-extraction step was deliberately rejected because it was observed, in the prior implementation, to itself cause tunnel vision by anchoring the reviewer on the submitter's framing of what matters. Each round performs FULL re-grounding over the entire ReviewTargets scope, ignoring prior findings as input, producing a self-contained finding set. Findings use a new design-review-specific taxonomy (correctness, functional-completeness, security, quality, maintainability) with a HIGH/MED severity scale by default — matching the existing gate vocabulary — though, consistent with `Feedback` being an abstract base type with per-review-type implementations, the severity scale itself is controller-configured per review type rather than hardcoded globally forever. A separate, dedicated LLM-judged reconciliation pass runs after each round's findings are finalized (no re-grounding), given the two adjacent rounds' finding sets plus, if needed, the full audit trail already retained in the temp folder, to classify each prior HIGH/MED as confirmed/still-open, contradicted, or no-longer-surfaced; this reconciliation is informational/presentational only — the round N approval gate reads ONLY the current round's own HIGH/MED findings to decide block vs. pass, because full independent re-grounding already re-catches any defect that is genuinely still present, and reconciliation (itself another fallible LLM judgment over a narrower prior subset) is not a reliable substitute safety net for a miss the fresh pass should have caught. A new public `insrc_docgen` docType ('review-report') renders one MD artifact per round, explicitly invoked by the agent with the review id/round after findings+reconciliation finish; this per-round MD stays focused on the current round's own findings, with inline resolved/still-open/contradicted annotations only for whichever prior Feedback the submitter's `corrections` entries actually addressed or rejected THIS round — not a running audit of all history — and is presented to the user via `insrc_present` every round, with no response required from the user until the existing 3-round cap is reached. Recovery/checkpointing is minimal and round-level: a crash before a round's full cycle (grounding -> findings -> reconciliation -> MD render -> present) completes re-runs that entire round from scratch; the checkpoint itself is a generic 'review checkpoint' JSON side-record, independent of ReviewContext's own fields, written and read automatically and invisibly by the review process (never an agent-driven step), and its GRANULARITY is defined PER REVIEW TYPE rather than by one universal rule — design review (DEF/HLD/LLD) has no natural sub-unit so checkpoints at the round level, while code review's natural unit is already modeled in Scope as `tasks: Pointer[]`, so its checkpoint can be per-Task within a round (a crash only re-runs the in-flight Task, not already-completed ones). Everything — the per-round input/output JSON, the checkpoint JSON, the rendered MD — lives inside the `.insrc/tmp/<reviewId>/` folder for the review's duration; the folder is deleted once the review reaches a terminal state, but BEFORE deletion the FINAL round's review-output JSON (findings + reconciliation) is copied into the review's durable artifact storage alongside the other persisted artifacts (DEF/HLD/LLD/PLAN/BUILD), so the completed result remains recoverable and referenceable later even after the temp working folder is gone — only the scratch/intermediate-round material is ephemeral. This rebuild deliberately avoids the retired design-review checkpoint model's heavy attempts/chunks/admission/migration-guard machinery.

## Scope boundary

This spec covers the review PROCESS only: the two review kinds and how they share one execution flow, the policy-only grounding-independence enforcement, the round-level (per-type-granular) checkpoint/recovery mechanism and its temp-folder storage/lifecycle, the finding taxonomy/severity/reconciliation mechanics, and the per-round docgen 'review-report' presentation flow. It builds on, and in two specific points (header-level reviewId, the corrections array) amends, the companion ReviewContext data-model spec from the prior brainstorm session — those amendments should be folded into that data model before either is implemented. It explicitly does not change the existing 3-round review cap policy, does not let reconciliation influence the gate's block-vs-pass decision, does not introduce a technical/structural mechanism to enforce independent grounding (policy/steering only), and does not cover extending this process to new review dimensions (e.g. security/quality) beyond what is already pinned here — that is separate follow-on work.

## Non-goals

- Reinstating the retired checkpoint model's attempts/chunks/admission/migration-guard machinery
- Changing the existing ReviewContext data model (round, Scope, ReviewTargets, Comments) — already converged and out of scope
- Changing the existing 3-round review cap policy itself
- Mid-round resume of in-flight grounding/analysis state — round-level checkpointing means recovery is always a full round restart, never a partial resume
- Diverging the steering/checklist logic for Correction-and-Re-review from Initial Review beyond what reconciliation already provides
- Letting reconciliation (confirmed/contradicted/no-longer-surfaced annotations) influence the round N gate's block-vs-pass decision — gate reads only the current round's own findings
- Mechanically enforcing independent grounding (e.g. stripping or withholding submitter narrative from the reviewer) — enforcement is policy/instruction-only via steering, not a technical isolation mechanism
- Automatic triggering of the docgen 'review-report' render or the checkpoint write being exposed as a separate agent-driven step — docgen render is an explicit agent-invoked call, while checkpoint read/write stays internal to the review process
- Scoped re-review: re-ground and re-analyze only the ReviewTargets/Comments marked as corrected since the last round, independently, plus a check that prior unresolved findings weren't newly addressed
- Hybrid: full independent re-grounding of the whole target, but the steering explicitly prioritizes verifying prior-round findings first before surfacing new ones
- Reuse the existing code-review dimension taxonomy as-is: adherence, conventions, coverage, quality
- Two-level taxonomy: fixed top-level categories (correctness, functional, security, quality) with a free-text subcategory per finding
- No fixed taxonomy — category is a free-text label per finding
- Inline chat summary per round; only the final round's findings get rendered to MD via docgen
- Single cumulative MD artifact per review (not per round), appended/updated each round and re-presented
- Three-level: HIGH / MED / LOW, where only HIGH/MED block (LOW is informational, never blocks)
- Five-level: CRITICAL / HIGH / MEDIUM / LOW / INFO
- Binary flag only: blocking / non-blocking (no severity label at all)
- Structural: strip submitter narrative from the reviewer's input — the process hands the reviewer only the artifact's extracted claims and scope pointers (files/symbols), never the submitter's prose rationale; the reviewer must independently probe each claim against source (via the analyzer) before rendering a verdict
- Two-pass: the reviewer first grounds blind with no artifact at all, forming its own independent understanding of the target, then is given the submitter's artifact and diffs its own findings against it
- Config-gated: support both the structural and policy-only modes, selected per repo/config, defaulting to policy-only
- Fully independent — no linkage
- Reviewer self-attests resolution inline
- Deterministic matching by (category, file, symbol/location): a prior HIGH/MED with no new finding at the same category+location is resolved; one that reappears is unresolved
- Submitter-asserted resolution: the submitter records, per prior finding, how it was addressed (via ReviewTargets/Comments); reconciliation just checks the new round's independent findings for contradiction of that claim
- Findings-only MD: each round's MD shows only that round's own categorized findings; reconciliation status is computed and used solely to decide block-vs-warn at the gate, never rendered
- Findings + separate reconciliation summary table: current findings rendered as in option 1, plus a distinct table at the end of round>1 MDs summarizing prior-round disposition
- Union gate: block iff current round has a HIGH/MED OR reconciliation marks any prior HIGH/MED as still-open (not resolved, not contradicted)
- Contradiction-aware union: block iff current round has a HIGH/MED OR reconciliation marks a prior HIGH/MED still-open, but a prior finding reconciliation marks contradicted is dropped from the gate
- Folded into the reviewer pass: the same pass that does independent grounding + produces this round's findings is also given the prior round's findings and asked to annotate reconciliation inline as part of its single output
- Internal-only renderer invoked automatically by insrc_review_step/insrc_code_review_step the moment a round's cycle completes; not exposed as a docgen docType
- Both: the review step auto-renders the MD internally on round completion for guaranteed presentation, and the same renderer is also exposed as a docgen docType for on-demand regeneration/viewing later
- Agent-managed: the driving agent explicitly calls a checkpoint-write step after presenting each round's MD, and a checkpoint-read/recover step before starting a round
- Hybrid: the tool auto-writes the checkpoint on round completion, but the agent must explicitly invoke a 'recover' phase/call when resuming after a crash to decide whether to use it
- New field(s) on the existing ReviewContext record itself (e.g. lastCompletedRound, status), persisted in place
- Derive recovery state implicitly from the persisted per-round MD artifacts (decision 4) — the latest MD artifact's round number IS the checkpoint, no separate record
- Round + dimension-level checkpoint: persist after each completed finding dimension (correctness, security, etc.) within a round
- Fine-grained per-probe/per-finding checkpoint matching the retired model's resolution
- One universal round-level-only checkpoint rule with no per-review-type distinction (superseded by the per-review-type granularity table)

## Decisions

- **Full re-grounding: re-run independent grounding/analysis over the entire ReviewTarget scope every round, ignoring prior findings as input** — When a Correction-and-Re-review round runs, how much of the target does the reviewer re-ground and re-analyze — since grounding must stay independent (not consuming submitter analysis) but round-level checkpointing means a round is the unit of rework?
  - Ruled out: _Scoped re-review: re-ground and re-analyze only the ReviewTargets/Comments marked as corrected since the last round, independently, plus a check that prior unresolved findings weren't newly addressed_, _Hybrid: full independent re-grounding of the whole target, but the steering explicitly prioritizes verifying prior-round findings first before surfacing new ones_
- **New design-review-specific taxonomy: correctness, functional-completeness, security, quality, maintainability** — Findings must be categorized — what fixed taxonomy does every finding get classified against?
  - Ruled out: _Reuse the existing code-review dimension taxonomy as-is: adherence, conventions, coverage, quality_, _Two-level taxonomy: fixed top-level categories (correctness, functional, security, quality) with a free-text subcategory per finding_, _No fixed taxonomy — category is a free-text label per finding_
- **Persist one MD artifact per round (via docgen renderer), presented through insrc_present every round** — Each review round must be presented to the user. Is the per-round output a persisted MD artifact (via the new docgen 'review to MD' renderer) that gets declared/presented each round, or just an inline chat summary the agent composes from in-memory findings, with the MD renderer reserved for the final/approved review only?
  - Ruled out: _Inline chat summary per round; only the final round's findings get rendered to MD via docgen_, _Single cumulative MD artifact per review (not per round), appended/updated each round and re-presented_
- **Two-level: HIGH / MED (matches the existing gate language 'unresolved HIGH/MED findings' blocks approval) — anything below is narrative, not a finding** — Each finding is categorized (correctness/functional-completeness/security/quality/maintainability) — what severity scale does it also carry, since that scale drives block-vs-warn and round-cap behavior?
  - Ruled out: _Three-level: HIGH / MED / LOW, where only HIGH/MED block (LOW is informational, never blocks)_, _Five-level: CRITICAL / HIGH / MEDIUM / LOW / INFO_, _Binary flag only: blocking / non-blocking (no severity label at all)_
- **Policy-only: hand the reviewer the full artifact (including submitter analysis/rationale) and rely on steering instructions telling it to re-derive independently and disregard the narrative** — Builds on decision 2 (full re-grounding every round) — this decision is about what the reviewer is actually handed to ground against, which the earlier answers assumed but never pinned down.
  - Ruled out: _Structural: strip submitter narrative from the reviewer's input — the process hands the reviewer only the artifact's extracted claims and scope pointers (files/symbols), never the submitter's prose rationale; the reviewer must independently probe each claim against source (via the analyzer) before rendering a verdict_, _Two-pass: the reviewer first grounds blind with no artifact at all, forming its own independent understanding of the target, then is given the submitter's artifact and diffs its own findings against it_, _Config-gated: support both the structural and policy-only modes, selected per repo/config, defaulting to policy-only_
- **Post-hoc reconciliation step** — A Correction-and-Re-review round re-grounds fully and independently, ignoring prior findings as input (decision 2). But the gate language is 'unresolved HIGH/MED findings' — does a correction round's output track resolution of the PREVIOUS round's findings, or is each round's finding set entirely self-contained with no linkage back?
  - Ruled out: _Fully independent — no linkage_, _Reviewer self-attests resolution inline_
- **LLM-judged reconciliation: a dedicated pass (or the reviewer itself) is given both rounds' finding sets and judges which prior findings the new, independently-grounded round confirms, contradicts, or no longer surfaces** — Decision 7 pinned that a post-hoc reconciliation step links each round's self-contained findings back to the previous round's (since full re-grounding ignores prior findings as input, but the gate blocks on 'unresolved HIGH/MED'). What actually performs that reconciliation, and how does it decide a prior finding is resolved?
  - Ruled out: _Deterministic matching by (category, file, symbol/location): a prior HIGH/MED with no new finding at the same category+location is resolved; one that reappears is unresolved_, _Submitter-asserted resolution: the submitter records, per prior finding, how it was addressed (via ReviewTargets/Comments); reconciliation just checks the new round's independent findings for contradiction of that claim_
- **Findings + reconciliation annotations: each round's MD lists current findings and, for round > 1, annotates each prior HIGH/MED as resolved / still-open / contradicted inline** — The per-round MD artifact (decision 4) is presented to the user every round. Besides the current round's self-contained findings, does it also surface the LLM-judged reconciliation against the previous round (decision 9) — or is reconciliation kept purely backend/gate logic, invisible in what the user sees each round?
  - Ruled out: _Findings-only MD: each round's MD shows only that round's own categorized findings; reconciliation status is computed and used solely to decide block-vs-warn at the gate, never rendered_, _Findings + separate reconciliation summary table: current findings rendered as in option 1, plus a distinct table at the end of round>1 MDs summarizing prior-round disposition_
- **Current-round-only gate: block iff this round's own findings include a HIGH/MED; reconciliation stays purely informational/presentational, never feeding the gate** — At round N's approval gate, which findings actually determine block vs. pass — the round's own self-contained HIGH/MED findings only, or does a reconciliation-flagged prior finding also factor in, given round N's full re-grounding (decision 2/7) ignores prior findings as input and reconciliation (decision 9/10) is a separate post-hoc annotation layer?
  - Ruled out: _Union gate: block iff current round has a HIGH/MED OR reconciliation marks any prior HIGH/MED as still-open (not resolved, not contradicted)_, _Contradiction-aware union: block iff current round has a HIGH/MED OR reconciliation marks a prior HIGH/MED still-open, but a prior finding reconciliation marks contradicted is dropped from the gate_
- **Dedicated reconciliation pass: a separate LLM call, run after this round's findings are finalized, given only the two finding sets (no re-grounding) to judge confirmed/contradicted/no-longer-surfaced** — Decision 9 pinned LLM-judged reconciliation but left open who performs it: 'a dedicated pass (or the reviewer itself)'. Given each round already runs independent grounding + findings generation, does reconciliation run as a separate dedicated LLM call after findings are produced, or is it folded into the same reviewer pass that already produces this round's findings?
  - Ruled out: _Folded into the reviewer pass: the same pass that does independent grounding + produces this round's findings is also given the prior round's findings and asked to annotate reconciliation inline as part of its single output_
- **New public insrc_docgen docType (e.g. 'review-report'): the agent explicitly calls docgen with the review id/round after each round's findings+reconciliation finish** — The new docgen 'review to MD' renderer must produce the per-round MD artifact that gets presented every round (decision 4/10). How does this renderer actually get invoked — as a manual docgen call the agent must remember to make, or wired automatically into the review process itself?
  - Ruled out: _Internal-only renderer invoked automatically by insrc_review_step/insrc_code_review_step the moment a round's cycle completes; not exposed as a docgen docType_, _Both: the review step auto-renders the MD internally on round completion for guaranteed presentation, and the same renderer is also exposed as a docgen docType for on-demand regeneration/viewing later_
- **Automatic: the review tool/process writes the checkpoint internally right after a round's cycle (grounding→findings→reconciliation→MD render→present) completes, and reads it internally at round start to detect a prior crash — invisible to the driving agent** — The round-level checkpoint record (decision 8) must get written on round completion and read on recovery. Who actually drives that — is it automatic plumbing inside the review process itself, or something the orchestrating agent has to remember to call?
  - Ruled out: _Agent-managed: the driving agent explicitly calls a checkpoint-write step after presenting each round's MD, and a checkpoint-read/recover step before starting a round_, _Hybrid: the tool auto-writes the checkpoint on round completion, but the agent must explicitly invoke a 'recover' phase/call when resuming after a crash to decide whether to use it_
- **A separate, generic 'review checkpoint' side-record keyed by the review's id, independent of ReviewContext's own fields — concretely, a JSON file inside the `.insrc/tmp/<reviewId>/` folder (the same folder as the per-round input/output), where `reviewId` is both the folder name AND a header-level field on ReviewContext itself (alongside `round`), so a resume attempt can recover by reading the id off the artifact/context rather than depending solely on caller-side bookkeeping — without the caller supplying that same id back, the system cannot find prior state and starts a brand-new review from scratch. The folder is deleted once the review reaches a terminal state, but BEFORE deletion the final round's review-output JSON is copied into the review's durable artifact storage alongside the other persisted artifacts, so the completed result stays recoverable after the temp folder is gone** — The round-level checkpoint must persist at minimum the last-completed round number/status so a crash recovers with minimal rework and the mechanism generalizes to code-review later. Where and as what shape does this checkpoint live?
  - Ruled out: _New field(s) on the existing ReviewContext record itself (e.g. lastCompletedRound, status), persisted in place_, _Derive recovery state implicitly from the persisted per-round MD artifacts (decision 4) — the latest MD artifact's round number IS the checkpoint, no separate record_
- **Round-level checkpoint as the base unit; GRANULARITY IS DEFINED PER REVIEW TYPE, not by one universal rule — design review (DEF/HLD/LLD) has no natural sub-unit, so it checkpoints at the round level; code review's natural unit is already modeled in Scope as `tasks: Pointer[]`, so its checkpoint can be per-Task within a round (a crash only re-runs the in-flight Task, not already-completed ones)** — What unit of work does a review checkpoint capture, so recovery stays minimal and still generalizes to code-review?
  - Ruled out: _Round + dimension-level checkpoint: persist after each completed finding dimension (correctness, security, etc.) within a round_, _Fine-grained per-probe/per-finding checkpoint matching the retired model's resolution_, _One universal round-level-only rule with no per-review-type distinction (superseded by the per-review-type granularity table)_
