# Spec: Define a shared base `ReviewContext` type used by both design review (DEF/HLD/LLD) and code review.

**Category:** design

## Intent

Define a shared base `ReviewContext` type used by both design review (DEF/HLD/LLD) and code review. It carries a root-level `round: number` (which attempt this instance is, for the 3-round cap) plus three sections. `Scope` is identified by two small orthogonal fields — `scopeType: 'epic' | 'standalone' | 'issue'` and `scopeLevel: 'def' | 'design' | 'lld' | 'plan' | 'task' | ...'` — rather than one combined depth enum; the (scopeType, scopeLevel) pair selects a dedicated validator function (one per review type) that encodes exactly which fields must/must-not be populated for that combination. Scope's artifact-kind fields are `def`/`hld`/`lld`/`plan` (each a single optional `Pointer`) and `tasks` (an array of `Pointer`, since one code-review round can cover several Tasks of the same Story but never spans multiple Stories), plus named, typed, singular optional pointer fields for other artifact kinds as relevant — e.g. `extension` (an EXT-… artifact from a define 'extend' path) and `amendment` (an AMD-… HLD amendment) — added by name as new kinds arise, never folded into or widening an existing kind's field, and never genericized into a map. The deepest-populated field at a given depth IS the artifact under review itself (self-inclusive), not just ancestor context — e.g. an HLD review's `hld` field names the HLD being reviewed, not just `def` as ancestor. A `Pointer` is `{ path, section?, contentHash? }`: `path` references the existing authored file directly (DEF.md/HLD.md/source files) with no generated extract; `section` is an open/extensible `Locator` (symbol name, line range, doc-section id, and future kinds) used to pin an exact changed region, which is how independent agents running in parallel each identify their own exact changes so the reviewer can correlate overlapping change impacts; `contentHash` lets staleness be detected, but staleness is always the reviewer's own judgment call during its independent grounding, never a framework-level block — it only becomes review feedback when it actually affects the current review, so two independent, non-overlapping concurrent changes must never stop or distort review feedback. The second section, `ReviewTargets` (renamed from the working label 'Analysis'), is the actual content to be reviewed: a list of `file:[section]` entries each carrying the same `{ file, section, contentHash }` shape with no origin metadata (no `addedBy`), because the ENTIRE ReviewContext (Scope, ReviewTargets, Comments) is populated by the submitter/controller alone — the reviewer never adds entries to it, and is always free to fetch/dig into anything it deems necessary beyond this list (including unchanged files); the submitter's pointer set is a floor, never a bias or ceiling on the reviewer's actual investigation. ReviewTargets is fully reset (not merged or carried forward) on every new review round on the same artifact, because the real set of targets legitimately changes between rounds (a correction round's edits may touch different files, roll back earlier changes, or add new files). The third section, `Comments`, is a freeform catchall block the submitter adds as additional context for the reviewer, covering edge cases the rest of the model doesn't structurally handle; it is a flat list of entries with first-class top-level fields `{ round, party: 'controller' | 'daemon', timestamp, text }` — no verdict/severity/dimension field, since any verdict is always re-formed fresh by the reviewer rather than trusted from a prior round's label. This per-entry `round` records which PAST round a historical comment came from, distinct from the root-level `round` field that states the CURRENT round. Comments is scoped same-artifact-only across the chain (a DEF review's comments do not carry into the HLD review that follows it), but within repeated rounds on the SAME artifact, later rounds' Comments can include relevant feedback from earlier rounds (e.g. round 3 referencing rounds 1 and 2). Validation of a populated ReviewContext against its declared (scopeType, scopeLevel) is performed by the controller/caller BEFORE sending it for review, using one dedicated validator function per review type; the reviewer may optionally re-run a validation round itself, but is not required to.

## Scope boundary

This spec covers the ReviewContext TypeScript data model only — the type/schema for Scope, ReviewTargets, and Comments, the Pointer/Locator shapes, the scopeType/scopeLevel fields, and the per-review-type validator contract. It explicitly excludes building the per-depth construction/population logic and excludes wiring ReviewContext into insrc_review_step / insrc_code_review_step — both are deferred, tracked follow-on work, but are intended to land in the SAME eventual DEF/epic as this data model, not as a separately split tracked unit.

## Non-goals

- Context sections are NOT pre-digested analysis — the reviewer must re-derive findings from the referenced source itself
- Building the populators and wiring ReviewContext into insrc_review_step/insrc_code_review_step is out of scope for this brainstorm
- Comments entries will not carry structured verdict/severity fields re-derived by the framework — any verdict is re-formed fresh by the reviewer, not trusted from a prior round's label
- Data model + construction logic: also design the per-artifact-type builder that assembles a ReviewContext at each review depth (DEF-only, DEF+HLD, DEF+HLD+LLD+PLAN+Task), but leave review-tool integration out of scope.
- Full vertical slice: data model, construction logic, AND the integration points in insrc_review_step / insrc_code_review_step that will consume ReviewContext.
- Analysis starts empty; the reviewing agent populates it itself during its own grounding pass, and the finished ReviewContext becomes a record of what it actually looked at
- Split: a separate, framework-owned 'suggestedRefs' list is pre-populated for orientation, while the canonical Analysis section stays reviewer-authored output
- Single flat type: all pointer fields (def, hld, lld, plan, tasks) are optional on one `ScopeSection`; convention (not the type) decides which are populated per review kind
- Discriminated union on `reviewKind` ('def'|'hld'|'lld'|'code'), each variant declaring exactly the pointer fields valid at that depth
- Path only (`artifactPath` / `file` string)
- Path + version/revision id (`{ path, version }`)
- Path + mtime/timestamp
- Symbol name (matches existing entity graph: SHA256(repo+file+kind+name))
- Line range (startLine-endLine)
- Free-text label (e.g. "the retry-backoff loop")
- Structured entries that add typed fields alongside the verbatim text — e.g. `verdict`/`severity`/`dimension` for code review, `holds`/`does-not-hold`/`could-not-verify` for design review — carried over from the prior round's own output.
- Comments is itself a pointer, not inlined text — `{ path, contentHash }` to a prior comments file/log, consistent with how Scope and Analysis are pointer-only.
- Every artifact field is uniformly an array (`def: Pointer[]`, `hld: Pointer[]`, ... `tasks: Pointer[]`), even though most hold at most one entry
- Keep all fields singular `Pointer`; represent multiple in-scope tasks as multiple separate ReviewContext instances (one per task) instead of one context with many tasks
- Ancestor-only: the existing def/hld/lld/plan/tasks fields hold only context ABOVE the artifact under review (e.g. HLD review populates only `def`); the artifact under review is identified separately, outside Scope's pointer fields, by the tool call that invoked the review (e.g. `insrc_review_step`'s own artifactPath arg) — ReviewContext never names it
- Explicit separate field: add a dedicated `subject: Pointer` field (the artifact under review) alongside the existing ancestor-context fields (def/hld/lld/plan/tasks), which stay pure ancestor context at every depth
- Bare locator only: `{ file, section }` with no contentHash and no origin metadata — identical shape whether framework-seeded or reviewer-added
- Add only `addedBy: 'framework' | 'reviewer'`, no contentHash
- Add both `contentHash` and `addedBy`
- Pointer targets a separate generated JSON extract/summary file, distinct from the authored artifact, that the framework produces and maintains as a side-output
- Mixed: DEF/HLD/LLD point at their authored markdown directly, while Plan/Task point at the already-structured JSON the plan workflow produces natively
- Cross-artifact carryover: Comments also includes prior rounds from ancestor artifacts in the same chain (DEF, then DEF+HLD, then DEF+HLD+LLD, ...)
- Full carry-forward: round N's Analysis list starts as round N-1's final list (seed + reviewer extensions) untouched, with no reseed
- Merge: framework reseeds the diff/link-derived entries fresh each round, then unions in the reviewer's prior-round extensions (dedup by file+section)
- Enum pairs depth with chain shape explicitly (`def-hld`, `def-hld-lld`, `def-hld-lld-plan-task`, plus standalone variants `hld-standalone`, `lld-standalone`, `lld-plan-task-standalone`)
- Enum stays full-chain-only (`def-hld`, `def-hld-lld`, `def-hld-lld-plan-task`) and a standalone review reuses the deepest-matching value with its absent ancestor fields simply left undefined
- Treat DEF review as depth `hld` with the `hld` field left unset
- DEF review doesn't use ReviewContext at all — it gets its own lightweight context shape outside this model
- Implicit: current round = comments.length + 1, no separate field
- No round concept in ReviewContext at all — round tracking lives entirely in workflow/session state outside this type
- Single flat type plus a single combined `scopeDepth` enum field checked by one shared validator (superseded by the two-axis scopeType/scopeLevel + per-review-type validator design)
- Closed union of exactly symbol name OR line range, author's choice per entry, with no further kinds (superseded by the open/extensible Locator)
- Provenance (round/party/timestamp) nested under a generic metadata object rather than first-class top-level fields
- Path + contentHash alone with no section/locator for pinning the exact changed region
- Single combined `scopeDepth` enum naming the deepest artifact only (superseded by the two-axis scopeType/scopeLevel design)

## Decisions

- **Data model only: define the ReviewContext TypeScript type/schema (Scope/Analysis/Comments shapes, pointer formats) as a standalone contract; building the populators and wiring it into insrc_review_step/insrc_code_review_step is separate follow-on work.** — What is the scope of THIS brainstorm/design effort — just the ReviewContext data model, or also how it gets built and consumed?
  - Ruled out: _Data model + construction logic: also design the per-artifact-type builder that assembles a ReviewContext at each review depth (DEF-only, DEF+HLD, DEF+HLD+LLD+PLAN+Task), but leave review-tool integration out of scope._, _Full vertical slice: data model, construction logic, AND the integration points in insrc_review_step / insrc_code_review_step that will consume ReviewContext._
- **Submitter/controller pre-populates ReviewTargets before the review starts (e.g. files touched by the diff, or files linked from the in-scope LLD/Plan), as a starting pointer list; the reviewer never adds to it but is free to dig into anything beyond it** — Who fills in the ReviewTargets section's references (originally drafted as "Analysis"), and when — is ReviewContext a fully pre-populated input handed to the reviewer, or does the reviewer build it itself as it works?
  - Ruled out: _Analysis starts empty; the reviewing agent populates it itself during its own grounding pass, and the finished ReviewContext becomes a record of what it actually looked at_, _Split: a separate, framework-owned 'suggestedRefs' list is pre-populated for orientation, while the canonical Analysis section stays reviewer-authored output_
- **Two orthogonal fields, `scopeType: 'epic' | 'standalone' | 'issue'` and `scopeLevel: 'def' | 'design' | 'lld' | 'plan' | 'task' | ...'`, rather than one combined depth enum; the (scopeType, scopeLevel) pair selects a dedicated validator function per review type that encodes exactly which fields must/must-not be populated for that combination** — How should the Scope section's structure encode which artifact depth (DEF-only vs DEF+HLD+LLD+PLAN+Task) applies for a given review — a single flat optional-fields type, or a type that varies by review kind?
  - Ruled out: _Single flat type: all pointer fields (def, hld, lld, plan, tasks) are optional on one `ScopeSection`; convention (not the type) decides which are populated per review kind_, _Discriminated union on `reviewKind` ('def'|'hld'|'lld'|'code'), each variant declaring exactly the pointer fields valid at that depth_, _Single flat type plus a single combined `scopeDepth` enum field checked by one shared validator (superseded by the two-axis scopeType/scopeLevel + per-review-type validator design)_
- **Path + content hash (`{ path, contentHash }`), refined via decision 5 into `{ path, section, contentHash }` — `section` (the same open Locator from decision 5) identifies the exact changed region, which is how independent agents running in parallel each identify their own exact changes so the reviewer can correlate overlapping change impacts** — What does a Scope/ReviewTargets pointer actually carry — just a path to the artifact/file, or path plus enough to detect that it's gone stale since the pointer was recorded?
  - Ruled out: _Path only (`artifactPath` / `file` string)_, _Path + version/revision id (`{ path, version }`)_, _Path + mtime/timestamp_, _Path + contentHash alone with no section/locator for pinning the exact changed region_
- **Open/extensible `Locator` type: symbol name, line range, doc-section id, or further kinds added later — not a closed 2-member union** — A ReviewTargets entry is `file:[section]` — what does `section` actually identify inside the file?
  - Ruled out: _Symbol name (matches existing entity graph: SHA256(repo+file+kind+name))_, _Line range (startLine-endLine)_, _Free-text label (e.g. "the retry-backoff loop")_, _Closed union of exactly symbol name OR line range, author's choice per entry, with no further kinds (superseded by the open/extensible Locator)_
- **Flat list of entries, each with first-class top-level fields `{ round, party: 'controller' | 'daemon', timestamp, text }` — not a nested metadata bag. No verdict/severity/dimension fields — just the raw comment text plus who-said-it-when.** — Comments is primarily a freeform catchall block the submitter adds as additional context, covering edge cases the rest of the model (Scope/ReviewTargets) doesn't structurally handle; it may incidentally also carry forward prior-round feedback. What does a Comments entry actually consist of structurally?
  - Ruled out: _Structured entries that add typed fields alongside the verbatim text — e.g. `verdict`/`severity`/`dimension` for code review, `holds`/`does-not-hold`/`could-not-verify` for design review — carried over from the prior round's own output._, _Comments is itself a pointer, not inlined text — `{ path, contentHash }` to a prior comments file/log, consistent with how Scope and ReviewTargets are pointer-only._, _Provenance (round/party/timestamp) nested under a generic metadata object rather than first-class top-level fields_
- **Only the task field is an array (`tasks: Pointer[]`); def/hld/lld/plan remain single optional `Pointer` fields — challenged and confirmed: a code-review round can legitimately span multiple Tasks of the SAME Story but never multiple Stories, matching the plural `tasks`. Other artifact kinds (e.g. `extension` for an EXT-… artifact, `amendment` for an AMD-… HLD amendment) are added as their own named, typed, singular optional pointer fields as they become relevant — never folded into or widening an existing kind's field, and never genericized into a map** — The deepest scope depth is DEF+HLD+LLD+Plan+Task(s) — Task is explicitly plural (a Plan can name several Tasks in scope for one code review round). Should the Scope type's `task` field be a single pointer or an array, while DEF/HLD/LLD/Plan stay singular, and how does Scope accommodate artifact kinds beyond DEF/HLD/LLD/PLAN/Task (e.g. EXT/AMD)?
  - Ruled out: _Every artifact field is uniformly an array (`def: Pointer[]`, `hld: Pointer[]`, ... `tasks: Pointer[]`), even though most hold at most one entry_, _Keep all fields singular `Pointer`; represent multiple in-scope tasks as multiple separate ReviewContext instances (one per task) instead of one context with many tasks_
- **Self-inclusive: the same depth's deepest-populated field IS the artifact under review (e.g. HLD review sets `hld` to the HLD being reviewed, not `def` alone; code review's `tasks` are the tasks being reviewed, with lld/plan as ancestor context)** — Does the Scope section's pointer set include a pointer to the artifact actually being reviewed this round (e.g. the HLD itself, during an HLD review), or only its ancestor context (e.g. DEF only)?
  - Ruled out: _Ancestor-only: the existing def/hld/lld/plan/tasks fields hold only context ABOVE the artifact under review (e.g. HLD review populates only `def`); the artifact under review is identified separately, outside Scope's pointer fields, by the tool call that invoked the review (e.g. `insrc_review_step`'s own artifactPath arg) — ReviewContext never names it_, _Explicit separate field: add a dedicated `subject: Pointer` field (the artifact under review) alongside the existing ancestor-context fields (def/hld/lld/plan/tasks), which stay pure ancestor context at every depth_
- **Add `contentHash` to match Scope pointers (`{ file, section, contentHash }`), no origin metadata (no `addedBy`)** — Scope pointers already settled on { path, contentHash } (decision 4); Comments already carry provenance (decision 6). ReviewTargets (drafted as "Analysis") is the one section whose entry shape hadn't been pinned past the `file:[section]` locator. No `addedBy` field is needed anywhere: ReviewTargets is entirely submitter/controller-populated, not reviewer-extended — staleness (via contentHash) is always the reviewer's own judgment call during independent grounding, never a framework-level block, and never becomes feedback unless it actually affects the current review.
  - Ruled out: _Bare locator only: `{ file, section }` with no contentHash and no origin metadata — identical shape whether framework-seeded or reviewer-added_, _Add only `addedBy: 'framework' | 'reviewer'`, no contentHash_, _Add both `contentHash` and `addedBy`_
- **Pointer targets the existing authored file directly (DEF.md, HLD.md, source files, etc.) — no new generation step; `{path, contentHash}` already keeps the reference minimal regardless of the target's own format** — A Scope/ReviewTargets pointer's `path` field — does it reference the artifact's existing authored file directly (DEF.md/HLD.md/LLD.md/PLAN.md, or a source file), or a separate generated JSON extract/summary produced alongside it specifically for review consumption?
  - Ruled out: _Pointer targets a separate generated JSON extract/summary file, distinct from the authored artifact, that the framework produces and maintains as a side-output_, _Mixed: DEF/HLD/LLD point at their authored markdown directly, while Plan/Task point at the already-structured JSON the plan workflow produces natively_
- **Same-artifact only: Comments holds only prior rounds' comments for the artifact under review in this cycle (e.g. HLD review sees only prior HLD-review-round comments, not DEF-review comments)** — Decisions 6 and 8 fixed what a Comments entry contains (text + round/party/timestamp) and that Scope is self-inclusive per depth, but neither pinned which rounds' comments populate the list when the review moves to a deeper artifact in the same chain — this is the last structural gap in the three sections.
  - Ruled out: _Cross-artifact carryover: Comments also includes prior rounds from ancestor artifacts in the same chain (DEF, then DEF+HLD, then DEF+HLD+LLD, ...)_
- **Full reset: framework reseeds ReviewTargets from scratch each round (current diff-touched/linked files only)** — This mirrors decision 11 (Comments cross-artifact scope) but for round-to-round persistence within the same artifact's review cycle, which hasn't been pinned yet. Since ReviewTargets is entirely submitter-populated (not reviewer-extended — see decision 9), there is nothing reviewer-added to discard or merge; the real set of targets legitimately changes between rounds (a correction round's edits may touch different files, roll back changes, or add new ones), so each round's ReviewTargets must reflect the current real set, not an accumulated history.
  - Ruled out: _Full carry-forward: round N's Analysis list starts as round N-1's final list (seed + reviewer extensions) untouched, with no reseed_, _Merge: framework reseeds the diff/link-derived entries fresh each round, then unions in the reviewer's prior-round extensions (dedup by file+section)_
- **`scopeLevel` includes `hld`, `lld`, `plan`, `task` among its values (deepest artifact only) — ancestor fields are purely optional and the per-review-type validator checks only whichever ancestor chain actually exists for that review instance, with no separate standalone variants** — What is the actual value set for depth, given that a standalone design.story/plan (triage feature/small path) has no DEF/HLD ancestors at all, while an epic-chain artifact can have the full DEF→HLD→LLD→PLAN→TASK ancestry? (Superseded structure: this depth question is answered by the `scopeLevel` half of the two-axis `scopeType`/`scopeLevel` pair from decision 3, not by a single combined `scopeDepth` enum.)
  - Ruled out: _Enum pairs depth with chain shape explicitly (`def-hld`, `def-hld-lld`, `def-hld-lld-plan-task`, plus standalone variants `hld-standalone`, `lld-standalone`, `lld-plan-task-standalone`)_, _Enum stays full-chain-only (`def-hld`, `def-hld-lld`, `def-hld-lld-plan-task`) and a standalone review reuses the deepest-matching value with its absent ancestor fields simply left undefined_, _Single combined `scopeDepth` enum naming the deepest artifact only (superseded by the two-axis scopeType/scopeLevel design)_
- **Add a `def` value to `scopeLevel`** — DEF is a mandatory review target too (the shallowest design artifact, with no ancestor at all), but the agreed scopeDepth enum only has hld/lld/plan/task. How should a DEF review's ReviewContext express its depth?
  - Ruled out: _Treat DEF review as depth `hld` with the `hld` field left unset_, _DEF review doesn't use ReviewContext at all — it gets its own lightweight context shape outside this model_
- **Explicit top-level `round: number` field, stamped by the framework each time it builds a ReviewContext for a new attempt** — Does ReviewContext carry an explicit field stating which round of review this instance represents, or is the current round only inferable from the Comments list?
  - Ruled out: _Implicit: current round = comments.length + 1, no separate field_, _No round concept in ReviewContext at all — round tracking lives entirely in workflow/session state outside this type_
