# Spec: Show background task progress in chat.

**Category:** requirements

## Intent

Show background task progress in chat.

Provide trustworthy progress feedback for long-running work inside its originating conversation, so users can follow reviews and test sweeps without repeatedly asking whether they are still running. Support insrc VS Code chat and native Claude Code, Codex and Vibe chat through capability-specific delivery. Use task-specific delegates, a shared runtime progress coordinator, and separate client delivery adapters.

## Product requirements

R1 — Inline conversation ownership. Associate every observed task with its project/repository, conversation, originating tool invocation, task identity and execution attempt. VS Code renders one task message in the normal transcript, updating it in place while running and retaining a compact terminal result. Multiple concurrent tasks remain distinguishable. Progress continues on the associated message when subsequent conversation turns occur; switching conversations never routes an old task's progress into the newly active chat.

R2 — Delegate pattern. Supply separate DesignReviewDelegate, CodeReviewDelegate and TestDelegate implementations. Delegates attach to their existing executors or managed processes and translate execution events into a common progress contract. Each delegate exposes a progress() method that returns the relevant task-specific progress details, not merely a lifecycle status or a generic running message. It supplies task-specific phase, measured counters, meaningful milestones, health information and supported controls. The shared coordinator owns task identity, authoritative snapshots, bounded history, ordering, subscriptions and delivery cadence. Delivery adapters own presentation and transport; delegates contain no client-specific rendering or agent narration. Extending to another task type must not require rewriting existing delegates or client renderers.

R3 — Truthful progress. Distinguish execution state, observation connectivity, task progress and worker liveness. Model execution states include queued, running, waiting, paused, completed, failed, cancelled, interrupted and unknown where evidence requires them. A live heartbeat does not establish forward progress or reset the last-meaningful-progress timestamp. Unknown totals remain unknown. Display measured phase counts rather than an invented overall percentage, and show newly discovered follow-up work separately. No unsupported ETA, fabricated counter, success inferred from output silence, or completion inferred from a disconnected client is permitted.

R4 — Native delivery without agent tokens. Instrumented executors emit structured events directly to the coordinator. VS Code consumes events and updates its chat message without a model call. MCP delivery maps the same state to supported progress notifications and human-readable labels. Normal native progress must not enter model conversation context, trigger additional agent turns or require agent polling. Durable storage retains bounded snapshots and useful milestones rather than every heartbeat or output fragment.

R5 — Capability-specific CLI delivery. Treat MCP tool connectivity, progress-token use, user-visible message rendering, background lifetime and scheduled observation as separate capabilities. Select a delivery mode per client/version/session based on evidence. Do not present protocol connection as proof of rendering. Source inspection is dated evidence; native rendering requires a repeatable live qualification. MCP Tasks is optional and experimental, never the baseline requirement. A normal tool-call progress token is not reused after its valid request/task lifetime.

R6 — Optional agent polling fallback. Where native progress is not visibly supported, allow explicit opt-in to low-frequency agent status polling. Clearly state that this mode consumes agent tokens and can produce occasional ordinary chat messages. It must remain optional and must not be silently substituted for token-free native delivery. The runtime calculates not-before/next-poll guidance and returns a compact snapshot or meaningful delta; agents do not run tight polling loops or regenerate summaries from raw logs. Repeated unchanged snapshots produce no repeated user-facing narration. Heartbeats alone do not count as reportable progress. Authorized fallback status snapshots are the explicit exception to excluding progress from model context: each poll may consume input/output tokens and an agent decision turn even when nothing changed. The no-silence/waiting-call non-goal prohibits separate model calls just to narrate silence or implement a timer; it does not claim that an unchanged authorized poll is free. Runtime timers and native notification delivery require no model calls.

R7 — Fixed 60-second fallback scheduling. While observation is enabled, the client can schedule it and the transport is healthy, poll each task on a constant 60-second cadence. This is a user-required interval, not a tunable adaptive default: unchanged status, elapsed duration and heartbeat-only updates must never increase it. Return an initial snapshot when observation attaches, then schedule follow-up polls every 60 seconds. Keep one shared per-task observation schedule across observers and a stable cursor; unchanged replies suppress duplicate narration without slowing the next poll. Bounded status waits may return meaningful changes earlier but must fit within the next scheduled interval and client timeout. Schedule from the polling cadence rather than adding a further 60-second sleep after a status wait. Avoid overlapping calls and catch-up bursts; a request or unavailable agent that prevents the cadence must be reported as degraded observation, not silently converted to slower polling. Terminal/error/action-required updates are discovered on the next healthy scheduled poll, at most one polling interval later plus transport and rendering latency. Execution deadlines still apply. Explicit rate limiting or transport loss moves observation into a visible degraded/suspended state honoring retry-after; it is an error condition, not an adaptive healthy cadence. Restore the fixed cadence on recovery. Host code performs timer waiting when a suitable scheduler exists. An active agent may continue an authorized bounded observation loop using supported wait facilities, but native clients with no scheduler cannot be promised autonomous polls after a turn ends or the session exits. If observation cannot continue, show that limitation once rather than claiming a watcher exists.

R8 — Stop, suspend and cancellation semantics. End fallback polling at terminal execution status; suspend it on an observation pause, repeated transport errors or lost session capability. Retry failed transport in host/runtime code with bounded error-recovery backoff where supported; this does not change the required 60-second healthy polling cadence, and impaired observation must be reported. An explicit user request to stop updates stops observation; it does not cancel the task. Task cancellation is a separate explicit action, exposed only where the delegate/executor supports it. A cancellation request remains pending until execution termination is confirmed. Client disconnect, polling pause and daemon restart never imply successful cancellation.

R9 — Delegate-specific measurements. Design reviews report the artifact and review stage, known check/chunk counts and meaningful milestones. Code reviews report dimension/stage, known initial chunks, active chunk, follow-up work and retries separately; progress instrumentation must not alter review findings, approval gates or execution scheduling. Tests report discovered/running/completed suites or tests, pass/fail/skip counts, elapsed time and the active suite when available through a supported reporter. Aggregate counters use a declared unit and prevent double counting suites, nested tests, retries and attempts. A reporter failure, aborted process, incomplete output or nonzero exit cannot become a completed successful sweep. Raw command output is available through a separate bounded details/log surface, not used as model narration input.

R10 — Reconnect and restart. Reopening or reattaching the same authorized chat restores the latest durable task snapshot and useful milestones, then resumes observation from a cursor. Duplicate/reordered events cannot move the UI backwards, duplicate messages or overwrite a newer attempt with an older result. A task may continue without observers. On daemon restart report interrupted or unknown until the execution owner verifies that work survived or was genuinely resumed; never automatically restart a review/test command merely because observation reconnects. Preserve completed/failed/cancelled outcomes across client reloads and distinguish observation failure from task failure.

R11 — Bounded and scoped delivery. Coalesce frequent progress updates and rate-limit subscribers while ensuring terminal outcomes are retained. Preserve the latest authoritative snapshot when a client falls behind; expose an explicit history-gap/resync condition instead of silently losing ordering. Scope reads, subscriptions, logs and controls to authorized task/conversation/project ownership. Sanitize task labels and reporter output for presentation; do not publish prompts, credentials, raw model responses or environment values as progress. Poll responses stay bounded and refer to detailed results rather than embedding full review reports or TAP logs.

R12 — Existing-system integration. Reuse or extend existing review progress producers, the MCP forwarding bridge and VS Code chat/tool surfaces where suitable. Keep the feature decoupled from repairs to the review engine occurring in another branch. Do not change configured model providers, approval requirements, runtime execution ownership or third-party CLI installations to enable progress. Polling/reporting cannot approve a workflow artifact, fabricate an independent review or automatically retry expensive work.

R13 — Concurrent-chat lifecycle integration. Integrate with the existing extension-local concurrent-chat session store, active-chat list, detached observer, pending-request handling and turn lifecycle rather than introduce another independent chat-status writer. A terminal agent turn or cleared liveTurn is not a terminal background task. Project conversation status from all relevant live turns, queued continuations, unresolved action requests and delegated tasks: waiting-input has precedence when an explicit user decision is unresolved; otherwise live turns/continuations or authoritatively owned queued/running/dependency-waiting tasks keep the chat working; done is permitted only when those obligations have ended. Task-specific failures/interruptions remain visible on their task entries even where the existing chat-level projection uses done. Paused/unknown tasks require an explicit bounded retention/recovery policy; they must not become fabricated completed tasks or immortal working chats.

R14 — Runtime-owned session activity and retention. Register a separate, renewable task-activity/retention association with the owning conversation and execution attempt before work is detached. Its presence protects that conversation from idle classification, active-list aging and capacity eviction while verified associated work remains nonterminal. The execution owner renews this association and the appropriate session activity signal through runtime code even during a long silent model call/test, without producing chat text, agent turns or model tokens. Meaningful task progress, worker liveness and session-retention activity are separate clocks: a valid owner heartbeat can keep the session active without advancing progress counters, resetting the no-progress clock, changing user-activity time or changing the fixed fallback-poll cadence. Merely subscribing, polling status, repainting the UI or running the observer is not execution activity. Do not emulate activity by continually calling setStatus(working), which could overwrite waiting-input or newer state. Where an actual session owner evicts by inactivity, integrate an explicit task-aware retention exemption or renewal with that owner; do not assume a status read touches it. Specify renewal cadence, lease TTL and idle-window safety margin in design: renewal must precede every applicable expiry with room for missed ticks, independently of the fixed 60-second agent-poll cadence. With no observers or while a different chat is selected, verified work must remain active until terminal outcome or loss of authoritative ownership evidence. Stop renewals on verified terminal outcome, explicit association release or stale/lost ownership, and reconcile stale leases after a bounded grace rather than retaining dead work forever. Pure user-activity, meaningful-progress and retention timestamps remain separately explainable.

R15 — Identity, ownership and concurrency. Preserve explicit mappings between the extension conversation ID, optional daemon chat-pool ID, provider-native session ID, turn/tool invocation, task ID, executor identity/epoch and attempt. These IDs are not interchangeable. Route updates and task-originated action requests to the originating conversation even after chat switching or another turn begins. One task terminal event releases only its own retention association; it cannot mark a chat done while another task/turn/request remains. Recompute from authoritative current state and attempt/event versions; a newer heartbeat timestamp alone cannot authorize a stale writer. Multiple windows may observe the same task, but observation does not acquire execution ownership, duplicate retention renewals, steal or extend a CLI process lease, or multiply fallback polling. Task retention is separate from repository queue and native turn execution locks, so keeping a background task active does not by itself block unrelated chats or new turns. Closure/removal of a conversation must define the task's detach/cancel disposition explicitly; ordinary chat switching only detaches presentation.

R16 — Lifetime and completion boundaries. Observation adapters and the detached observer must consult task ownership/retention alongside provider terminal/death evidence before completing or evicting a conversation. Completion, setup error, Stop, process death and observer reconciliation paths all need the same task-aware status projection, not just the foreground event path. A terminal CLI process with a still-running delegated daemon review remains an active conversation. Task completion updates session activity once and starts the existing done-chat aging window only when every associated obligation has ended; late heartbeat/replay messages must not extend terminal retention indefinitely. Preserve unread output/progress checkpoints and unresolved action payloads during active work and capacity pressure. Native third-party CLI session activity is a separately qualified capability: maintaining an insrc conversation association does not claim to prevent a vendor CLI's own idle timeout, retain a dead process, schedule an unavailable agent or keep credentials alive. If that client cannot be kept active through a supported runtime path, report the limit and preserve the task/results for later reattachment.

R17 — Delegate progress() contract and detailed responses. Every initial task delegate implements progress() for a specific authorized task/execution attempt. The method returns a bounded structured snapshot of the relevant progress known by that executor, including a stable meaningful-progress revision, measurement/as-of time, current phase/activity, measured completed/total counts with declared units and unknown totals where appropriate, last meaningful progress time, and applicable task-type details. A status-only response such as running is insufficient when task progress details are available. Lifecycle status, connectivity and worker heartbeat accompany the progress details as separate coordinator metadata; they do not substitute for them.

The DesignReviewDelegate returns the artifact/review target, current review stage, known checks or chunks completed/remaining, active check when available, retries and recent meaningful milestones. The CodeReviewDelegate returns the dimension/stage, initial chunk counts and current chunk, separately identified follow-up/relation checks, retries and relevant completed-work milestones. The TestDelegate returns discovery/execution phase, active suite/test when known, discovered/completed counts, pass/fail/skip counts, retries/attempts and elapsed time. Report only facts available from instrumentation; unsupported measurements must be explicitly unknown rather than invented. Partial findings or test failures may be provisional; only the executor's verified terminal result is authoritative. Detailed logs, prompts and complete review reports remain separate references rather than progress payloads.

The coordinator obtains or refreshes the snapshot through the appropriate delegate's progress() method, and normalizes it into the same task progress model for direct delivery and each fixed-60-second fallback response. Implementations may cache the last authoritative snapshot and refresh on executor events; progress() must not start/restart work, advance counters, invoke an LLM, generate narration or count a status read as execution activity. Change detection uses meaningful progress fields/revision, not lifecycle status alone: advancing from chunk 5 to chunk 6 is reportable even while state remains running. Heartbeat-only changes and the snapshot query time do not increment the meaningful-progress revision or trigger repeated narration. Poll replies include a compact current progress snapshot and meaningful-change indicator/cursor even when the lifecycle state is unchanged. When no progress changed, return unchanged with the last known details and their original measurement freshness; do not replace them with a bare status.

If progress() fails or its source is temporarily unavailable, report progress observation unavailable/stale with the last verified snapshot and its age when available. Do not invent fresh details, renew execution activity merely because the query succeeded, or mark the execution failed/completed merely because details could not be read. Validate scope, task/attempt identity, snapshot consistency, bounded payloads and presentation safety at the delegate/coordinator boundary. Method argument types, synchronous versus asynchronous mechanics, caching implementation and exact transport schema are downstream design details; the named method and its detailed observational behavior are required.

## Acceptance scenarios

A1: An instrumented long-running review updates its originating VS Code chat message during execution, including after the user sends another message. Updates require zero additional model calls. A completed review retains one compact terminal message with access to its result.

A2: Design and code review delegates report their respective stages/counts through the same coordinator and renderers. When follow-up work is discovered, the displayed progress remains truthful without an artificial overall completion percentage. A quiet model call displays elapsed/health evidence without pretending another chunk completed.

A3: A managed test run reports structured counts, its active suite when available, and a verified terminal result. Failures, retries, nested tests, malformed reporter output and process termination are represented accurately. Existing test commands retain their intended execution/exit behavior.

A4: A live-qualified native MCP client displays deterministic progress without extra model calls. Missing progress tokens, unsupported rendering, request completion and background transitions are tested as distinct cases. Unsupported clients do not receive a false native-support claim.

A5: With fallback disabled, no agent polling is introduced. With fallback explicitly enabled on an unsupported client with scheduling support, a fake-clock test verifies follow-up polls at a constant 60-second interval across repeated unchanged status and heartbeat-only replies. Only meaningful changes produce concise chat updates; suppressing duplicate narration never slows polling. A terminal result or action request arriving just after a poll is returned at the next healthy scheduled poll. Token-consuming polling is visibly identified. Error-recovery/rate-limit scenarios surface degraded or suspended observation and resume the 60-second cadence after recovery; a bounded wait must not add another interval of delay or cause overlapping requests.

A6: A fallback host with no usable scheduler reports that automatic observation cannot continue after the current turn/session. Neither the task nor its execution state is changed by this limitation. No test may count a fake autonomous timer or agent busy-wait loop as supported progress delivery.

A7: Two observers or repeated tool retries do not multiply the per-task agent polling cadence, duplicate the task execution or emit duplicate final messages. Authorization and attempt correlation prevent cross-chat updates and stale-attempt finalization.

A8: Reload/reconnect restores the latest task state without replaying every tick or starting the task again. Daemon restart yields a truthful interrupted/unknown state unless continued/resumed execution is verified. Lost observations, gaps, duplicate events and terminal outcomes have deterministic recovery behavior.

A9: Stopping updates leaves execution running; explicit cancellation reports pending until termination is verified. A disconnected client, unsupported cancellation or stale task identity cannot be reported as successful cancellation.

A10: Instrumentation verifies bounded delivery/history, redacted labels/output, correct project/conversation isolation, and zero extra model invocations for native progress. The fallback is measured separately for poll frequency and payload size; no token-free claim applies to it.

A11: Start a review or managed test in chat A, finish its launching agent turn, switch to chat B and advance beyond the configured session idle/purge window while A's execution owner remains healthy. A stays working/retained and its task message remains associated with A without any agent poll, visible progress tick or user input. B's status and activity remain independent. Repeat under session-cap pressure and with no attached observers.

A12: A has two background tasks and an unresolved action request. Heartbeats and ordinary progress keep retention current but preserve waiting-input. Ending one task or an older turn does not clear the request, overwrite the newer turn, release the other task's association or mark A done. Only resolution plus termination of all work permits done; done-chat aging then follows the existing configured window and history remains intact.

A13: Kill or lose the execution owner, expire its activity lease, restart the daemon/extension and deliver delayed heartbeats/terminal events from the prior attempt. The system reconciles to an honest interrupted/unknown/terminal outcome, bounds stale retention, preserves checkpoints and never resurrects the prior attempt or claims that another window's observer proves execution is alive. Reattachment does not relaunch work.

A14: Disable or pause agent polling, or make the client temporarily unable to observe. Runtime-owned activity still protects supported insrc session owners independently. Tests verify separate last meaningful progress, worker liveness and session-retention activity; receipt of a heartbeat changes neither measured progress nor the required 60-second healthy polling cadence. A task/status read alone does not keep unrelated daemon sessions alive.

A15: Two extension windows observe the same task while a newer user turn and another background task run in its conversation. A stale observer, cancellation outcome or task-terminal event cannot set done or remove newer state. Native turn/repository queue ownership remains with its existing owner, and task retention does not prevent another conversation from running. Unsupported native CLI keepalive is reported as a capability limit, not a passing test.

A16: For each design review, code review and test task, the coordinator exercises the delegate's progress() method and the delivered/polled response contains that task's relevant structured measurements. A running-to-running update with advancing counts or a changed phase produces meaningful progress even without a lifecycle status transition. Repeated unchanged measurements retain detailed last-known progress without duplicate narration; an as-of query timestamp or heartbeat alone cannot fabricate change. Polling remains fixed at 60 seconds.

A17: Direct client delivery and agent polling receive consistent task/attempt-bound progress from the same delegate snapshot model. A stale, failing or unavailable progress() source is surfaced honestly with measurement age and last verified details when available, without manufacturing progress, changing execution outcome or extending activity solely because a poll occurred. Tests verify no model calls, execution side effects or raw-log/report dumps occur in progress().

## Proposed defaults and qualification

The user explicitly requires a constant 60-second healthy polling cadence; do not increase it when status is unchanged. The earlier proposal to back off to two or three minutes is superseded. Polling remains optional and token-consuming, and client scheduling/transport limits must be reported honestly. A suggested native UI update cadence is at most once per second per running task, with retained terminal outcomes delivered promptly after receipt. Worker heartbeats may be emitted independently; a stale heartbeat changes observation/health messaging and must not authorize killing execution. Final heartbeat intervals, stale thresholds, quotas, retention duration, native transport wait bounds and storage representation are downstream design choices that must be explicit and bounded before implementation.

Native client evidence recorded during the brainstorm on 2026-11-04: Claude Code 2.1.310 is newer than the reported background-progress fix in 2.1.283; Codex 0.165.0's inspected handler logs progress without forwarding it to the chat renderer; Vibe 3.0.4's inspected MCP call path has no progress callback. None of these observations substitutes for a live end-to-end client acceptance test, and future versions require refreshed evidence. Native CLI limitations do not block implementing direct updates in insrc-owned VS Code chat or the optional polling fallback.

## Concurrent-chat build impact (source inspection, 2026-11-04)

The parallel build E202611031bd72813:S001 adds extension-local working/waiting-input/done status, a 30-minute active-list aging window for done chats only, and a 60-second detached-output observer. Source inspection at project HEAD 1b6727f69 found activeChats in vscode-plugin/src/chat/session-file-store.ts filters only aged done entries; evictBeyondCap protects persisted working/waiting-input chats and unresolved requests. This protects correctly classified ongoing chats but does not yet represent delegated background tasks after liveTurn ends. Foreground reevaluateChatStatus and detached-observer terminal handling currently derive done from turn/request state; the proposed feature must integrate with those projections. No new idle timer is requested merely to simulate user conversation.

The daemon ChatSessionPool in src/daemon/chat-sessions.ts is a separate random-ID registry with a 30-minute idle timeout, one-minute cleanup, and a most-recent-session exception. Its get method touches activity, but status/list are pure reads; extension chat IDs are not automatically daemon session IDs. An MCP status poll or extension heartbeat therefore cannot be assumed to renew that pool or a provider-native CLI session. Requirements R13–R16 make identity mapping, task-aware retention and independent session activity explicit, while preserving the distinction between liveness and real task progress.

The concurrent-chat build is still evolving. This is an impact assessment of inspected source and its pending design, not a claim of live UI validation, a code-review verdict for that stream, or implementation of these requirements.


## Scope boundary

This is a requirements specification for progress observation and delivery inside regular chat, not authorization to implement the feature. Required first-release task delegates cover design reviews, code reviews and managed test runs. Proposed first-release test boundary: tests launched through an instrumented managed execution path; arbitrary existing processes, automatic PID discovery and process attachment are deferred and are not claimed as user-selected exclusions. Future delegates may extend the framework.

In scope are the shared progress contract and coordinator, client delivery adapters, inline VS Code chat presentation, native CLI MCP progress where verified, explicit optional agent polling at a fixed 60-second healthy cadence, truthful lifecycle/health/counter reporting, bounded state/history, scoped details, reattachment and observational restart behavior. Scheduling mechanisms, durable storage implementation, final bounded quotas and reporter adapters are downstream design choices.

Out of scope are insrc TUI changes, third-party CLI patches, repairing/rebuilding review execution, a general-purpose job scheduler, guaranteed automatic polling in unsupported hosts, arbitrary process discovery/attachment in the proposed initial release, automatic task restart on reconnect, fabricated progress or ETAs, and making experimental MCP Tasks a universal dependency. The user has accepted the token cost of optional fallback polling; native progress remains free of additional agent calls. Spec approval is still required before routing into implementation workflows. Concurrent-chat integration includes explicit task-aware session activity, retention and aggregate status, with runtime-owned renewal independent of agent polling. This updates the pending requirements only; it does not modify the parallel build, its approval state, or third-party CLI idle behavior. Each task delegate must expose progress() returning relevant structured details; direct and fixed-60-second polling responses consume this contract rather than returning lifecycle status alone.

## Non-goals

- Implementation in this request.
- Changes to the insrc TUI.
- Patching third-party CLIs or repairing review execution.
- Using MCP Tasks as a required baseline; it remains optional and experimental.
- Adding progress telemetry to model conversation context or making extra model calls for native progress delivery.
- Token-free claims for agent polling, model invocations solely for silence or waiting, agent busy-poll loops, or unsupported autonomous polling promises.
- Fabricated progress percentages or ETAs, automatic execution restart on reattach, or cancellation merely because observation stops.
- Claims of universal native CLI progress support based solely on MCP support or unvalidated source inspection.
- Adaptive healthy polling that increases the interval beyond 60 seconds when status is unchanged.
- Lifecycle status alone as the task progress response.

## Decisions

- **Use a constant 60-second interval for enabled, healthy fallback agent polling.** — User explicitly rejected a three-minute wait and required constant 60-second polling. Silence may suppress duplicate messages, but cannot slow observation.
  - Ruled out: _Adaptive healthy polling that increases the interval beyond 60 seconds when status is unchanged._
- **Require a progress() method on every task delegate and include relevant task-specific progress details in responses.** — User explicitly requires delegate-provided progress details rather than a status-only reply.
  - Ruled out: _Lifecycle status alone as the task progress response._
