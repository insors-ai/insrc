# Anchor standalone features on their LLD so their plans build task by task

## Reproduction

1. Triage a change that sizes as a feature. Triage routes it to a standalone design.story, which mints its own epic hash <h> and writes LLD-<h>-S001. Approve it.
2. Run plan for that story. It writes PLAN-<h>-S001 with its tasks. Approve it.
3. Call insrc_build_step with phase 'implement' and target 'S001/t1' or 's1/t1' (both accepted by LABEL_RE, src/workflow/tracker/resolve.ts:512, /^([sS]\d+)(?:\/(t\d+))?$/) with epicHash <h>, or the hierarchical id 'E<date><hash8>:S001:T001'.

Expected: the build tool admits task t1 of the approved plan and returns its prompt, as it does for a story under an Epic or a sized bugfix.
Observed: every form returns 'unresolved-target: could not resolve target ...'. Seen on 2026-10-11 on d9f85b3cc8cc966b (an approved 10-task plan). A point-in-time snapshot on 2026-10-11 (list .insrc/artifacts/*.json, take the hash from each name with ^([A-Z]+)-([0-9a-f]{16}), group by hash) found 28 hashes with a PLAN-* file and no DEF-* or ISSUE-* file. The counts are illustrative; the fix does not depend on them.

Two further symptoms share the cause:
- One story's documents land in different folders: d9f85b3c's LLD is under docs/standalone/implement-approved-spec-77932eaa1a85819b-docs-standalone-E20261011d9f85b3c/ and its PLAN under docs/standalone/decompose-approved-lld-d9f85b3cc8cc966b-s001-shared-E20261011d9f85b3c/, each named from the opening words of that stage's focus text.
- The SPEC a feature was brainstormed from is never linked: triage has no specHash input, so the LLD is never stamped seededFromSpec and the SPEC looks orphaned (the same snapshot found 15 hashes whose only artifact is a SPEC-*).

## Root cause

A standalone feature has no epic-level anchor artifact, and three parts of the workflow assume one.

1. Task resolution. resolveWorkflowRef (src/workflow/tracker/resolve.ts:526) finds epics through listEpicHashes (resolve.ts:150), whose only filename filters are DEF_RE and ISSUE_RE (resolve.ts:155 and :159, matching DEF-<hash16>.json and ISSUE-<hash16>.json); it has no branch for LLD- or PLAN- files. It builds a reference through readEpicIdentity (resolve.ts:174), which reads epicSlug and createdAt only from DEF-<hash>.json then ISSUE-<hash>.json (resolve.ts:175-178) and returns null otherwise (resolve.ts:181). The standalone feature route writes neither: finalizeStandaloneLld (src/workflow/orchestrator.ts:2279) writes LLD-<h>-S001 and finalizePlan (orchestrator.ts:2551) writes PLAN-<h>-S001, and triage routes a feature straight to design.story, so finalizeDefine and finalizeIssue never run for it. resolveByHier (resolve.ts:426) and resolveByLabel (resolve.ts:444) therefore find no epic, and resolveTaskRef (src/mcp/build-step/render.ts:54; message built at :60), called from the implement phase (src/mcp/build-step/phases/implement.ts:61, failure returned as 'unresolved-target' at :62) and the validate phase (phases/validate.ts:212, returned at :213), fails. The identity those resolvers consume is EpicIdentity (resolve.ts:118-122): epicSlug, createdAt and an optional tracker block, read at resolve.ts:308 and :430.

2. Folder naming. A folder is named <slug>-E<date><hash8>. Three finalizers derive the slug from their own focus text with no inheritance: finalizeBrainstorm (orchestrator.ts:716), finalizeIssue (:888) and finalizeDefine (:1182), each via safeDeriveSlug (orchestrator.ts:1880), which wraps deriveSlug (src/workflow/slug.ts:40): a mechanical cut keeping the first MAX_TOKENS = 6 non-stopword words (slug.ts:25), with no model involved. The other sites inherit and use the focus only as a fallback: finalizeDesignEpic (:1781) and finalizeDesignStory (:2112) use the parent DEF's epicSlug, finalizeDefineExtend inherits from the DEF (orchestrator.ts:1291, define.meta.epicSlug ?? s1.target?.epicSlug ?? epicHash), and finalizeStandaloneLld (:2298) and finalizePlan (:2583) call inheritedEpicSlug (src/workflow/storage.ts:223), which reads the label through readEpicDefinitionCore (storage.ts:367-375). That second definition reader also consults only the DEF then the ISSUE artifact, so the fix must cover it as well as readEpicIdentity. The remaining finalize* functions do not name a work-item folder: finalizeArtifact and finalizeByWorkflow are dispatchers, finalizeStub writes under docs/stub, and finalizeTracker takes epicSlug from its step output (the DEF). For a standalone feature there is nothing to inherit, so both of those fall back to their own focus text and the LLD and PLAN folders diverge. A SPEC (finalizeBrainstorm) is always named from its focus text. A standalone LLD is recognisable by meta.standalone: true, stamped by finalizeStandaloneLld (orchestrator.ts:2351); epic-story LLDs omit the field (137 of the 200 LLDs on disk carry no flag), so an absent flag means an epic LLD or a legacy standalone one written before the flag existed.

3. SPEC link. Standalone design.story already supports seeding: the start phase resolves params.specHash through resolveStageFocus (src/mcp/workflow-step/phases/start.ts:63) and finalizeStandaloneLld stamps meta.seededFromSpec from it (orchestrator.ts:2320, :2354). But the triage tool never supplies it: a grep scoped to src/mcp/triage-step and src/workflow/triage finds zero specHash references, and the design.story call it builds (src/mcp/triage-step/phases/classify.ts:42-59, forwarding storyTitle/storySpec/sizeClass) carries no specHash.

## Fix intent

Implement the design approved as SPEC-34d7bb72df47a5e5, with no new artifact kind:

- A standalone feature's LLD serves as its identity anchor, alongside DEF (epic) and ISSUE (bugfix), supplying the same identity a DEF or ISSUE does (label and anchor date), so the build tool can admit its plan's tasks one at a time from both the implement and validate phases. Any LLD for a hash with no DEF or ISSUE qualifies, including items written before the standalone flag existed.
- Triage accepts an approved SPEC's hash and passes it into the standalone design.story it routes to, so the LLD records the SPEC it came from and shows a reference to it.
- A work item's folder is named from its head artifact's title (an LLM-written title produced in the same synthesis pass, or triage's storyTitle for a standalone LLD), and every downstream document (PLAN, BUILD, TESTS, CR) inherits that name from the anchor instead of deriving its own. The finalizers that already inherit from a DEF keep doing so.
- Existing anchorless items become buildable, and their already-split documents are consolidated into the anchor LLD's folder by extending the existing docs-tree migrator (dry run first).

This supersedes ISSUE-b2e05b043846451c, which framed the fix as adding a definition artifact; that option was ruled out in SPEC-34d7bb72.
