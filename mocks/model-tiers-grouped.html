What changed vs. today: the native VS Code Settings page lists 9 free-text fields (core.runner, core.model, core.effort, mid.…, cheap.…) in one flat group, each repeating the same long description. There's no visual separation between tiers, no indication of the model's cloud/local hosting, and no inline "this won't run" warning — you only find out when a run fails.

What this mock proposes: a dedicated panel (likely a webview, opened via a command or the gear icon next to Insrc in the status bar) with one card per tier, real dropdowns sourced from the daemon's model definitions (like the existing insrc: Set model tier picker already does), inline hosting badges, and the "not supported" state shown in place rather than discovered later.

Open questions for round 2: (1) does this replace the native settings fields, or sit alongside them as a friendlier front-end that still writes the same config? (2) is a full webview worth it, or would a grouped insrc: Set model tier QuickPick — one list showing all three tiers at once, each with its current value — get most of the benefit for far less work? (3) where does this panel live — a command, a sidebar view, or the existing Settings UI's "edit in settings.json" link replaced with a button?
