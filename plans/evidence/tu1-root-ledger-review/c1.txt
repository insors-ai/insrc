Roll up only through the ownership tree. corrects , dependencies and evidence links are navigable, non-additive relationships. A model attempt has exactly one callId , one charged artifact and one owning work item. A logical request may have multiple attempts; each attempt is a different physical call and counts. invocationId groups a CLI run or provider invocation. It is not a second charge. parentCallId expresses a causal relationship, not an ownership or summation edge. Workflow stage, exact step ID, run ID, review round, requested model and actual reported model travel with capture context. If a model request is shared and cannot be attributed to one child, charge the nearest explicit common activity once. Do not split a single count by guesswork. An unresolved target is held in a visible unassigned/pending bucket until explicitly reconciled. Ambiguous identities, multiple parents or cycles produce notices and conservative partial totals; never recurse indefinitely or join by title. 05 / ROOT USAGE LEDGER CONTRACT Keep usage outside artifact documents. Each epic, standalone work item or issue has one canonical root artifact. Store one append-only Avro object container file at <project>/.insrc/usage/<root-artifact-id>/events.avro . All usage for the root and its descendants goes into this file. Individual LLD, PLAN, TASK and BUILD JSON documents contain no usage event arrays. TU1 must implement and validate a usage-root resolver over canonical work-item identities, stored ownership links and explicit dispatch bindings. Existing ArtifactIds.parentOf covers TASK/TASKS/DIAG → STORY and STORY → EPIC; it does not resolve every document kind or establish whether a story is standalone. Do not guess a root from a title, hash prefix or missing link. .insrc/usage/EPIC-a17c42e69d035b81/events.avro root DEF and HLD authoring + reviews descendant LLD + PLAN + TASK + BUILD activity .insrc/usage/ISSUE-<id>/events.avro independently rooted issue and descendant activity Use the actual canonical root ID: EPIC for an epic work item; STORY for an independently rooted standalone story; ISSUE or SPEC only where it is the canonical independent root. DEF and HLD documents charge their epic root. A linked issue remains in its own root ledger when the relationship is only a reference. A non-root issue writes to its existing root. Every record carries rootArtifactId , charged artifactId , event/call identity, schema version and a root-local append sequence. Start records also carry workflow, model and attribution context; outcomes and corrections retain the same root/charged identity. Storage grouping does not change charging: a design review still charges its reviewed LLD. Avro is the proposed live format because its header/schema and record blocks support an append-oriented writer. Parquet has column chunks and trailing file metadata, so reserve it for optional derived snapshots/exports, not the authoritative live append path. Neither format alone provides transactions, deduplication, locking or durable acknowledgment. TU1 must prove these behaviors. Logical JSON export schema Example ledger export The JSON schema describes decoded events and API/export data, not artifact JSON or Avro bytes. The physical Avro schema and library are finalized and tested in TU1 design. The file header fixes its writer schema; evolve compatible reader contracts and nullable/defaulted fields. Any incompatible writer-schema migration needs an explicit recoverable migration plan before acceptance. DuckDB reporting over Avro Use the existing daemon-owned, in-memory DuckDB engine for filtering, grouping, time/model/step summaries and hierarchical reports. DuckDB’s core avro extension supports read_avro for one or multiple files. The current project driver instead decodes Avro into a derived Parquet cache before querying it; its pool disables automatic extension installation/loading. Direct Avro scanning therefore requires explicit trusted extension provisioning, offline/version/platform qualification and setup before pool lockdown. TU1 exposes committed per-root snapshots and compatible schemas; TU4 owns reporting queries. Do not scan an uncontrolled live append tail or claim that a SQL sequence filter alone provides a physical file snapshot. Use a bounded committed-prefix snapshot or coordinated reader lease, record a watermark per root, then apply the shared effective-event reducer before aggregation. Corrections, duplicate events and overlapping invocation/call observations are not additional usage. Match SQL results against reducer golden fixtures. DuckDB tables, indexes and any Parquet caches are rebuildable; Avro remains authoritative. Use explicit root allowlists resolved by the daemon for reports, including cross-root reports. Keep clients on IPC; do not expose arbitrary file paths or install extensions from user-supplied SQL. Extension unavailability produces a visible reporting outcome, not a complete zero. See DuckDB Avro documentation . Append and recovery boundary The daemon is the only writer. Serialize by repository and root ID, append complete Avro blocks, and acknowledge only after the block and required filesystem metadata are durable. A transient journal or checkpoint in the same root directory may support recovery but cannot become a second final ledger. On restart, validate the completed prefix, detect and isolate an incomplete tail, and recover staged events using stable IDs. Corruption inside committed history is an explicit failure, never silent skipping. A root can reserve its stable ID and create its usage ledger before a valid artifact body exists. Child events can target reserved stable child IDs under that root. Reconcile pending identities when documents are created without copying usage into them, fabricating design content or rerunning inference. A missing root cannot be guessed: block dispatch/report recovery until a valid root reservation can be established. Read to an acknowledged root watermark while appends continue. Artifact regeneration, approval and deletion do not rewrite the ledger. Keep all original observations; corrections and attribution transfers append new facts. Cross-root transfers reference the original event and are coordinated recoverably: do not copy a second charged call into the destination ledger. Root deletion/retention and branch imports are explicit ledger operations, not ordinary artifact JSON merges. One live file per root is the initial contract. Set measurable size/read-recovery limits in TU1; do not silently rotate, truncate, compact or introduce multiple authoritative files. Derived indexes and Parquet exports are disposable and identify the source root watermark. Directory creation and root IDs must be validated against the registered repository; clients cannot supply arbitrary filesystem paths.
