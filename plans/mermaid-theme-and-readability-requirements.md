# Mermaid Theme and Readability Requirements

Status: Draft requirements  
Date: 27 October 2026

## Purpose

Improve the appearance and readability of Mermaid artifacts generated by insrc through a shared visual theme, legible initial presentation, appropriate diagram density, and consistent viewing controls. Readers must be able to understand diagrams without guessing at low-contrast labels or repeatedly zooming into an oversized graph.

The shared light and dark themes must follow the Insors brand palette and Poppins typography specified below. Brand styling applies to the complete artifact viewing surface, not only Mermaid nodes.

This covers design companions and graph-generated documentation. It is a requirements proposal, not authorization to implement or approve a workflow artifact.

## Current foundation

- [Design companion shell](../src/workflow/artifacts/companion/shell.ts) initializes Mermaid with the neutral theme and fits the rendered diagram into its viewport. Its surrounding page uses fixed light colors and already supplies pan/zoom controls.
- [Docgen shell](../src/docgen/render/shell.ts) also initializes Mermaid with the neutral theme and provides fit/pan/zoom behavior.
- [Vendored runtime manifest](../src/assets/docgen/runtime.json) identifies Mermaid 10.9.1 and svg-pan-zoom 3.6.2. Artifacts inline the runtime for offline use.
- [Mermaid theme configuration](https://mermaid.js.org/config/theming) documents built-in themes and custom themeVariables using the base theme. Features described in current documentation must be checked against the runtime insrc actually ships.

The neutral setting explains the monochrome default. It does not by itself establish the cause of every unreadable artifact. Visual validation must also inspect scaling, density, clipping, typography, and label/background interactions.

## Scope

The initial release must cover shared theming and readability behavior across both rendering paths, including flow/component, sequence, ER, and class/type diagrams where supported by those paths. Maintain the structured definitions and graph-derived models as the source of truth.

No new diagram notation, replacement diagram engine, cloud rendering dependency, or hand-edited companion HTML is required. Regeneration must apply the improvements consistently. Existing pan/zoom features should be reused and corrected where needed rather than duplicated.

## Functional requirements

### Shared theme

**R1 — Central visual policy.** Both rendering paths must consume the same versioned Insors-branded diagram theme policy using the brand basis above. Centralize exact brand tokens, derived surface tokens, typography, border/connector styling, background treatment, and diagram-specific overrides. Keep presentation separate from model semantics and authored labels. Remove conflicting hard-coded neutral/blue styling from the generated shell rather than layering inconsistent themes indefinitely.

**R2 — Light and dark presentation.** Supply coordinated light and dark variants covering diagram elements and the surrounding page, viewport, toolbar, legend, and notes. Support automatic color-scheme selection with an explicit light/dark override. Re-render safely where Mermaid requires it; preserve the chosen mode and avoid losing the reader's position unnecessarily. Define persistence behavior during design. A standalone artifact must remain usable without IDE theme APIs.

**R3 — Deliberate contrast.** Explicitly set foregrounds and backgrounds for nodes, clusters, edge labels, actors, messages, ER attributes, notes, and other supported diagram elements. Do not rely on a generic primary color to style every diagram type correctly. Ensure arrows, cardinalities, dashed lines, and borders remain distinguishable in both variants.

Include explicit ER relationship-label foreground/background overrides: pale green label boxes must not inherit white dark-mode text. Audit table headers, attribute row stripes, sequence numbers, notes, badges, source links, focus indicators, and hover states against their actual surfaces. Do not use Pear or a light green as small text on white unless the required contrast is demonstrated.

**R4 — Semantic color where grounded.** Use a small consistent palette to distinguish roles such as internal components, data stores, external systems, and notes when those roles are available in the structured source. Do not infer architectural roles from arbitrary names or invent classifications for decoration. Diagrams without role metadata still receive a coherent default style. Include a legend when color carries meaning, and retain textual or shape distinctions so color is not the only signal.

**R5 — Runtime compatibility.** Use settings supported by the shipped Mermaid version. Evaluate whether a runtime update is necessary; do not make upgrading a prerequisite merely to obtain a newer built-in look. Any upgrade must preserve offline packaging, existing diagram syntax, strict rendering policy, and relevant companion/code-reference behavior.

### Typography and layout

**R6 — Readable typography.** Use Poppins as the primary font with explicit diagram text sizes, including diagram-specific text styles. Package regular, semibold, and bold font resources with the offline artifact/runtime under appropriate redistribution terms; no Google Fonts/CDN request or dependency on an unrelated local checkout is permitted. Wait for font readiness before Mermaid measures labels and before initial framing. Supply a readable sans-serif fallback and a recovery path if font loading fails. At the default desktop viewing position, ordinary labels must target at least 16 CSS pixels after viewer scaling. If the full graph cannot fit at that readable scale, use a readable partial view with clear navigation rather than shrinking all text to fit. Expose fit-to-view as a separate overview action. Include a supported narrow-viewport behavior in the design.

**R7 — Preserve label content.** Wrap long labels where supported without clipping, overlap, or loss of meaning. Size nodes and row spacing for their contents. Use a documented abbreviation/detail mechanism only when the full text remains accessible. Preserve ER attributes, relationship labels/cardinality, sequence messages, and code references.

**R8 — Control density.** Choose orientation, spacing, and grouping appropriate to the diagram type and source structure. For graphs too dense to read, provide coherent subdiagrams or an overview plus linked details when supported by the generation model. Preserve all modeled relationships through those views and disclose any actual truncation. The readability policy must never silently drop entities, edges, or messages to make a picture attractive.

**R9 — Stable presentation.** Equivalent source and renderer/theme versions should produce consistent styling, classification, and grouping. Responsive viewport changes may change framing, but must not change the diagram's meaning. A theme switch must not rewrite the underlying definition.

### Viewing and export

**R10 — Consistent controls.** Provide clear, keyboard-accessible zoom in/out, fit overview, readable/default scale, and reset controls. Support a larger/full-screen viewing mode where the host allows it, with a clear exit and a usable fallback where it does not. Fit, reset, and readable scale must have distinct documented behavior. Pan/zoom must not swallow ordinary page navigation or trap keyboard focus.

**R11 — Useful initial state.** Show the diagram at a readable initial scale. If it extends beyond the viewport, make navigation and an overview action discoverable. Avoid blank, off-screen, or tiny initial renderings. Recalculate framing after layout/font readiness and meaningful viewport changes without repeatedly overriding a user's manual zoom.

**R12 — Export parity.** Offer SVG export with the selected theme and sufficient embedded styling to remain readable outside the viewer. Export the complete diagram rather than only the visible viewport. Use an explicit, stable background treatment so exported text does not become unreadable on a different host background. If a multi-view diagram is offered, clearly identify what each export contains and provide access to all views. Additional bitmap/PDF export is optional.

Preserve the Insors palette and Poppins typography in supported export viewers through properly licensed embedded resources where supported. Declare and verify any font fallback; exports must not depend on fonts served from the preview server or local machine. Account for font metrics when checking clipping and layout outside the browser.

**R13 — Honest failure and fallback.** Rendering errors must show an actionable message and a way to inspect the diagram source and explanatory text. A theme/configuration failure must not produce a success state with an empty or illegible diagram. Preserve existing source/element descriptions and reference navigation.

### Integration and history

**R14 — Regeneration and versioning.** Newly generated artifacts record the relevant theme/renderer version for diagnosis. Existing saved self-contained HTML files remain readable; they do not update automatically. Provide a documented regeneration route for applying the new policy to old artifacts. Regeneration that only changes presentation must not silently change approved model semantics or approval history.

**R15 — Scope presentation changes.** Apply diagram styling to the diagram and its shell without leaking CSS into unrelated host content. Never execute author-supplied theme CSS, scripts, or arbitrary configuration as part of this feature. Keep any configurable theme surface constrained to validated settings and retain existing escaping and strict Mermaid security configuration.

## Validation and acceptance criteria

Use representative flow/component, sequence, ER, and class/type fixtures, including long names, multiline labels, dense relationships, nested groups, notes, cardinalities, and source links. Include narrow and desktop viewports and both light and dark variants. Test the same applicable fixtures in both renderer paths.

1. Both renderers use the shared policy and show a visibly coherent family of diagrams rather than independent defaults.
2. Labels, attribute rows, sequence messages, connectors, and notes meet the contrast targets and are readable at the initial scale or through the clearly identified detail view.
3. A large diagram opens at readable scale with accessible navigation; fit overview remains available without becoming the mandatory tiny default.
4. Long labels and nested/grouped structures do not clip or overlap in the agreed fixture set. Any necessary abbreviation exposes the full label.
5. Light/dark switching styles the complete viewing surface and preserves semantic content and usable navigation.
6. Semantic colors are consistent, have a legend when needed, and are never the sole way to distinguish meaning. Missing role metadata does not lead to invented roles.
7. Keyboard controls, focus, full-screen exit/fallback, and reset/fit/readable-scale actions work as described.
8. SVG export opens independently with complete content, intended styling, background, and readable text.
9. Offline use makes no remote runtime or font requests. Errors expose source/text access instead of an empty success state.
10. Repeated generation from unchanged definitions preserves modeled content, valid references, and the existing approval history.
11. Both modes use the six exact brand tokens and documented derived surfaces, with Poppins across the shell and diagrams. No unrelated blue/navy styling or remote-font request remains in the affected presentation.
12. ER relationship labels retain dark text on pale green boxes in dark mode; notes, attribute stripes, sequence numbers, links, controls, and interaction states satisfy measured contrast targets.
13. Artifacts opened without Poppins installed still load the packaged font offline. A simulated font failure retains readable content, and successful font loading does not leave clipped labels from earlier fallback measurements.

Validation must include actual rendered inspection, not only assertions that theme strings appear in HTML. Keep before/after fixture images and record viewport, runtime, and theme versions. Use automated checks for structural preservation, configuration, contrast pairs, and interaction behavior, supplemented by visual inspection for clipping, scaling, and density. If rendering cannot be performed, report that limitation and do not claim visual acceptance.

## Decisions for design

- Final mapping of the specified brand tokens and derived surfaces to semantic roles and diagram-specific elements. The brand palette and Poppins choice are established requirements, not open technology choices.
- Licensed font packaging, export embedding/fallback behavior, and brand-appropriate interaction states.
- Shared policy ownership and how both offline shells consume it.
- Readable-scale calculation, density/view-splitting policy, and supported viewport/diagram-size envelope.
- Theme preference persistence, safe re-rendering, and export serialization.
- Runtime upgrade need, version stamping, and regeneration workflow for saved artifacts.

Implementation must follow insrc's tracked workflow, independent review, and explicit approval discipline. Existing diagram-review requirements remain applicable. The brand direction is established here; exact production mappings, readability behavior, and export results still require design and rendered verification.
